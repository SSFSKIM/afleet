# Area 22 / 47 / 40 — goals & scheduling, git & GitHub, workflows

TUI-vs-headless gap inventory for a native GUI hosting the unmodified `claude` binary over
the headless stream-json protocol. Classes: **P** parity via protocol, **R** rebuild
client-side (data reachable), **D** data gap (needs protocol addition or workaround),
**X** unreachable interactive-only path, **T** terminal-specific.

Three protocol facts established by reading `Cu` (the wire filter) and confirmed against the
live 2.1.259 handshake, because almost every row below depends on them:

1. **The `system` branch of the wire filter ends in `default: return`**
   (`chunk-2rhzyjym.js:172491-172516`). Only `status`, `init`, `notification`, `api_retry`,
   `model_refusal_*`, `memory_recall`, `thinking_tokens`, `compact_boundary`,
   `model_fallback`, `model_consent_fallback` survive that switch. **Every other `system`
   subtype the TUI generates internally — `scheduled_task_fire`, `file_snapshot`,
   `stop_hook_summary`, `turn_duration`, `post_turn_summary` — is dropped.** The frames
   listed in the brief as "internal surfaces" (`vcs_state_changed`, `code_change_published`,
   `task_*`, `hook_*`, `informational`, `local_command_output`, `files_persisted`, …) reach
   stdout on a *different* path: they are pushed straight onto the output queue by `hu`
   (`chunk-sct99ax9.js:669202`), bypassing `Cu`.
2. **`active_goal` frames are `CLAUDE_CODE_REMOTE`-only.** `Cu` drops `active_goal`
   unconditionally (`chunk-2rhzyjym.js:172559`); the only producer is inside
   `if (a.CLAUDE_CODE_REMOTE)` in `runHeadlessStreaming`
   (`chunk-2rhzyjym.js:175366-175368`). A local GUI that does not set that variable never
   receives one.
3. **Meta user messages DO reach the wire** as ordinary `user` frames carrying
   `isSynthetic: true` (`lwe = isMeta || isVisibleInTranscriptOnly || isCompactSummary`,
   `chunk-1kg58a1a.js:92740`; emitted at `chunk-1kg58a1a.js:92982`). `TLe`'s `user` case
   applies no `isMeta` filter. This is the single most useful lever in this area: the goal
   kickoff message, the Stop-hook feedback line, every resolved loop-tick reminder, the goal
   check-in bodies and the no-op-fold turn companion all arrive as readable text.
   Only `attachment` messages are filtered hard — `el()` forwards **only**
   `hook_system_message` attachments (`chunk-2rhzyjym.js:172613-172619`), so `goal_status`
   attachments never reach the wire.

Live 2.1.259 `initialize.commands` (102 entries) contains `goal`, `loop` (alias `proactive`),
`schedule` (alias `routines`), `effort` (argumentHint includes `ultracode`), `deep-research`,
`workflow-authoring`, `workflow-launch-exec`, `__remote-workflow`, `worktree`. It does **not**
contain `diff`, `workflows`, `loops`, `install-github-app`, `branch` or `commit-push-pr`.

## 47-A. Branch, repository and worktree detection — what the chrome shows

| Feature | TUI behaviour (SPEC §) | Headless equivalent | Class | Notes |
|---|---|---|---|---|
| **The git branch name in the footer** | **The TUI does not render it.** §41.15.4 states explicitly: "The working directory, the git branch and the model name are not native footer segments — they reach the terminal only through a user-supplied `statusLine` command." | n/a | R | So the honest answer to "how does the TUI get it": it doesn't. The branch reaches a terminal only if the user wrote a `statusLine` script that shells out to git. A GUI should read the branch **itself**, the same way the CLI does internally: `al()` with no argument is a pure filesystem read — resolve the git dir, parse `HEAD`, return the branch or the literal `HEAD` when detached (§47.2.3). No subprocess needed. Do **not** rely on `vcs_state_changed`: that frame is emitted only after a detected `git commit` / `push` / `merge` / `rebase` in a Bash tool call (§47.7.3), so it is a *change* notification, not a state source. Correct design: read `HEAD` yourself, and additionally watch `<gitdir>/HEAD`, `<commondir>/config`, `<commondir>/refs/remotes/origin/HEAD` and the current branch's ref file — exactly the four paths the CLI's own git-state cache polls at 1000 ms (`chunk-v6tef322.js:753630`) — plus refresh on any `vcs_state_changed`. |

## Top gaps in this area

Ranked by how much user-visible capability is lost and how hard the workaround is.

1. **The workflow phases view has no live wire representation.** The TUI's per-agent grid is fed by an in-process progress stream that reaches stdout only as one throttled `tool_progress` line per 10 s. *Fix:* poll the `background_tasks` control request while a `local_workflow` task is running; its record carries the full `workflowProgress` array, `progressVersion`, `agentCount`, `totalTokens` and `totalToolCalls`. This is a rebuild, not a data gap — but it is the largest single build in this area. (§40.17)
2. **The worktree exit dialog does not exist headless, and it is not a `request_user_dialog` kind.** A headless session that exits inside a worktree silently leaves the worktree and its branch on disk. The GUI must run the three probes itself and drive `ExitWorktree` before ending the session, including the TUI's "clean and untitled → remove without asking" rule. (§47.12.7)
3. **`active_goal` frames are `CLAUDE_CODE_REMOTE`-only.** Goal state must be tracked client-side from `/goal` sends, the kickoff meta message, and `hook_response` frames. Setting `CLAUDE_CODE_REMOTE` to unlock the frame is a bad trade — it also strips the `gitStatus` block from the system prompt. (§22.21, `chunk-2rhzyjym.js:175366`)
4. **The no-op streak fold and `scheduled_task_fire` are entirely absent from the wire.** A long quiet dynamic loop produces an unbroken run of turns with no tick markers and no fold. The GUI must rebuild both: use each `ScheduleWakeup` call's `noop` argument as the fold key and the seven veto conditions from §22.18, and treat the `[N prior /loop wakeup(s) found nothing actionable…]` companion line as the streak signal. (§22.17–§22.18)
5. **The dynamic-loop keepalive is TUI-only.** It lives in the `useScheduledTasks` React hook; the headless scheduler wiring never sets `tickInFlightPrompt` and never arms the 1200 s fallback. Headless dynamic loops therefore stop silently if the model forgets to re-arm. The GUI must arm its own fallback timer. (§22.12 vs `chunk-2rhzyjym.js:176851`)
6. **The branch name has no source on the wire and never had one in the TUI either.** Read `HEAD` from the filesystem the way the CLI does, watch the four ref-related paths at 1 Hz, and use `vcs_state_changed` only as an invalidation trigger. `vcs_state_changed` fires solely after a detected commit/push/merge/rebase in a Bash call. (§41.15.4, §47.2.3, §47.7.3)
7. **The PR badge poller is disabled headless** (`ppo` skips when `vt()`). No PR status reaches the GUI at all. Reimplement using either the direct REST+GraphQL recipe or `gh pr view --json …`, reusing the token precedence, the adaptive interval ladders and the check-state folding from §47.8.
8. **Per-agent skip / retry / pause inside a running workflow have no control request.** `stop_task` stops the whole workflow; the three per-agent verbs are internal helpers. This is a genuine protocol gap with no workaround. (§40.17.4, §40.18.5)
9. **The rate-limit checkpoint never runs headless** — `non_interactive` is its first gate. No `refs/claude/checkpoint-*` ref, no `.claude/RESUME.md`, no safety net when a session hits a usage limit. A GUI that wants the protection must build the whole pipeline. (§47.19.7)
10. **`file_snapshot` frames are dropped**, so a GUI cannot enumerate which messages have file checkpoints even though `rewind_files` itself is a working control request. Workaround: read `file_snapshot` records from the session JSONL, or probe with a dry-run rewind. (`chunk-1kg58a1a.js:99529` vs `Cu`)
11. **`/loops` — the one surface that would show cron jobs and goals together — is dead in the binary and absent headless.** It is also the clearest opportunity to exceed the terminal: build the panel from `scheduled_tasks.json` plus locally tracked goal state. (§22.20)
12. **`/diff`, `/workflows` and `/install-github-app` are all `local-jsx` and unreachable.** Two have clean data substitutes (`get_workspace_diff`; `background_tasks` + run snapshots); `/install-github-app` needs a full reimplementation, for which §47.9 gives every command, URL, template and error string verbatim.
13. **The `ultracode` keyword veto (`alt+w`) has no stdin representation.** A GUI can show the "requested for this turn" notice but cannot suppress the trigger for a prompt that contains the word. Best available workaround is to help the user reword. (§40.20.1)
14. **Session-only cron jobs are invisible from outside the process.** `CronList` requires a model turn; `scheduled_tasks.json` covers only durable jobs. Acceptable, since session-only jobs die with the session, but it means a GUI's job panel is necessarily partial. (§22.5, §22.10)
15. **Attribution suppression via CLAUDE.md is model persuasion, not configuration**, and the settings path has a precedence trap: `attribution.commit` alone plus `includeCoAuthoredBy: false` yields the custom trailer *and* the default PR footer. A GUI exposing an attribution switch must write both `attribution.commit` and `attribution.pr`. (§47.5.1)

## Unverified

* **`/commit-push-pr` absent from the live 2.1.259 handshake.** SPEC 47 §47.10.1 says it is registered unconditionally as a `prompt` command with no `isEnabled` and no `disableNonInteractive`, and the string is present in the 2.1.259 Mach-O binary (5 occurrences), yet it does not appear in the 102-entry `initialize.commands` list — and neither do the bundled `commit` and `pr` skills. I traced the projection (`MY` → `ryt` → `hTr`: `userInvocable !== false && !vk(e)`) but did not trace what populates `os` inside `runHeadlessStreaming`, so I could not determine whether the cause is a per-command availability rule, an operator settings override turning it "off", or a change between 2.1.257 and 2.1.259. Treat the row's class (P) as provisional.
* **Whether an `interrupt` control request cancels a pending dynamic-loop wakeup headless.** §22.12 wires `s9t()` (which ends the loop with `user_abort`) to the Esc handler and the remote-interrupt path, both cited in `chunk-bq8epagv.js` — the REPL chunk. I did not confirm the headless interrupt path reaches it.
* **Whether `goal_status` attachments survive compaction**, and therefore whether a goal set before a compaction is restored after one. SPEC 22's own Open questions flags this; compaction record retention is ch. 13's territory and I did not verify it.
* **The exact throttling behaviour of the workflow `onSdkEmit` `tool_progress` re-emission in practice.** I read the code path (`ar = 10000` ms, suppressed unless the batch is purely `state:"progress"`) but no live workflow was run, so I could not measure how often a GUI actually receives one.
* **That `background_tasks` returns the full `workflowProgress` array.** I inferred this from the task record shape in §40.18.1 and the fact that `gin()` merges progress into `task.workflowProgress`; I did not read the `background_tasks` control-response projector to confirm the field is not stripped. This underpins the recommended workaround for gap 1, so it is worth confirming empirically before building on it.
* **`stats` field names in the `get_workspace_diff` response.** I read `{filesCount, linesAdded, linesRemoved}` and `perFileStats` entries `{added, removed, isBinary, isUntracked}` from the diff collector (`chunk-1kg58a1a.js:59734-59820`) rather than from the response serialiser itself; the serialiser spreads them through (`stats: e.stats`, `perFileStats: Array.from(e.perFileStats, ([m,y]) => ({path: m, ...y}))`), so the names should carry, but no live response was captured.
* **Whether meta user messages are suppressed anywhere downstream of `TLe`.** I confirmed `TLe`'s `user` case applies no `isMeta` filter and that `isSynthetic` is set from `isMeta`, which strongly implies they reach stdout; I did not observe one on the wire, and several rows above (goal kickoff, Stop-hook feedback, loop tick reminders, check-ins, ultracode reminders) depend on it. This is the single highest-value thing to confirm with one live turn.
