# Area 24+21 — Permission system, plan mode, and questions: TUI-vs-headless gap inventory

Chapters covered: `SPEC/24-permission-system.md` (complete), `SPEC/21-plan-mode-and-questions.md`
(complete), plus `SPEC/45-headless-and-sdk-protocol.md` §45.19 (`can_use_tool`) for the wire
side. Classification letters per BRIEF: **P** parity via protocol · **R** rebuild client-side ·
**D** data gap · **X** unreachable · **T** terminal-specific.

Three facts established here govern most rows below and are stated once:

1. **The only permission surface a headless host gets is `can_use_tool`.** The SDK/stream-json
   dialog dispatcher `K_` [`cli.pretty.js:174428-174444`, chunk-2rhzyjym] forwards
   `request_user_dialog` for exactly four kinds — MCP url-elicitation (`mcp_url_elicitation`),
   `refusal_fallback_prompt` [`cli.pretty.js:64169`], `fable_overage_consent_prompt`
   [`cli.pretty.js:68575`] and the Slack-connect kinds — and returns each other kind's declared
   `default` **without sending anything**. All twelve `permission_*` dialog kinds of SPEC 24
   §24.14.2 (`permission_prompt`, `permission_bash`, `permission_powershell`, `permission_file`,
   `permission_webfetch`, `permission_browser`, `permission_skill`, `permission_monitor`,
   `permission_ask_user_question`, `permission_enter_plan_mode`,
   `permission_exit_plan_mode_v2`, `permission_workflow`) and `ultraplan_launch` therefore never
   cross the wire, regardless of what the host declares in `initialize.supportedDialogKinds`.
   Their per-kind payload extras (`command` + `classifierState`, `filePath` + `operationType`,
   `hostname`, `verbPhrase`, `skill`, `intervalMs`, `questions`, `plan`, `script`) are lost; a
   GUI must re-derive the dialog variant from `can_use_tool.tool_name` + `input`.
2. **`decision_reason` is redacted before it leaves the process.** `oze` [SPEC 24 §24.11.2,
   `chunk-1kg58a1a.js:70416-70433`] emits *nothing* for reason types `rule`, `mode`,
   `subcommandResults`, `permissionPromptTool`, and nothing for the `outsideReadsBlocked` safety
   check. Those are the four most common escalations. The host gets `decision_reason_type` only.
3. **Empirical ground truth (2.1.259, `/tmp/afleet-gap/init-dump.json`):** the `initialize`
   response's 102-command list contains **no** `permissions`, `allowed-tools`, `add-dir`, `plan`
   or `ultraplan`. Every user-facing permission/plan slash command in these two chapters is
   `local-jsx` (SPEC 24 §24.19, SPEC 21 §10.1, §11.1) and is refused headless (SPEC 28 §22).

Ranked by how much they cost a GUI aiming to match or beat the TUI.

1. **`/permissions` is unreachable and must be rebuilt from `get_settings`, and only `localSettings` is writable through the protocol.** The command is `local-jsx` and is absent from the live 2.1.259 headless command list; `update_settings` accepts only `source: "localSettings"` (45 §45.22.8). Project and user scope are reachable only opportunistically, via `updatedPermissions` `destination` on an open `can_use_tool` allow (24 §24.15.1/§24.15.4), or by writing the settings file on disk and relying on hot reload (24 §24.8.5). There is no control request that removes a rule or a working directory at all. **X + D.**
2. **No permission dialog kind ever crosses the wire.** `K_` [`cli.pretty.js:174428-174444`] forwards only elicitation, `refusal_fallback_prompt`, `fable_overage_consent_prompt` and Slack kinds; every `permission_*` kind resolves to its local default. The GUI must reconstruct the Bash / file-diff / WebFetch / MCP / Agent / skill / plan / question dialog variants from `tool_name` + `input`, and loses `classifierState`, `operationType`, `verbPhrase`, `intervalMs` and the rendered tool-use line entirely. **R + D.**
3. **`decision_reason` is redacted for the four commonest escalation types.** `oze` emits nothing for `rule`, `mode`, `subcommandResults`, `permissionPromptTool`, nor for the `outsideReadsBlocked` safety check (24 §24.11.2). The GUI must rebuild the consent banner from `decision_reason_type` + `matched_ask_rule` + the mode it already tracks, and cannot render the TUI's per-subcommand "the following N parts require approval" list. **D.**
4. **Reject-with-feedback changes semantics on the wire.** The TUI's rejection is a *soft* `{behavior:"ask"}` carrying `Wk`/`I3`-prefixed text and is not booked as a permanent decision (24 §24.14.5); the wire only offers `{behavior:"deny", message}`, which *is* booked into `result.permission_denials`. The GUI must compose the full model-facing string itself (24 §24.20.3, four variants by subagent × feedback) and decide `interrupt` to reproduce the abort. Getting this wrong changes what the model does next. **R.**
5. **Accept-feedback, reject `contentBlocks` and `userModified` have no wire fields.** "Yes, but do X", images pasted into a rejection, and the "the user modified your proposed changes" signal on an edited Edit/Write are all unexpressible (45 §45.19.2; call site reads `Ot.userModified ?? false` at `cli.pretty.js:114831`). Plan editing is the exception — `input.plan` round-trips and drives `## Approved Plan (edited by user):`. **D.**
6. **Clear-context plan approvals cannot be done in one step.** `Yes, clear context (<N>% used) and …` resolves as a deny plus an internal context clear and re-seed (21 §7.5); headless there is no clear-context control request. The GUI must deny, send `/clear`, `set_permission_mode`, then send the fully-specified seed message, and fetch `get_context_usage` for the `<N>%` label. Reproducible, four operations, easy to get subtly wrong. **D with workaround.**
7. **Auto-mode availability is not on the wire.** `isAutoModeAvailable` / `canAutoClassifierRun` / the gate are context-internal (24 §24.3), so the GUI cannot know whether to offer `auto` in the mode ring, in the permission dialog's auto row, or in the plan-approval dialog's `Yes, and use auto mode` option. Probing via `set_permission_mode` costs a round trip and, on success, actually switches the mode. **D.**
8. **Subagent permission asks arrive with an opaque `agent_id`, not a name.** The TUI names the agent via `requestSource` (24 §24.14.2); the wire has only `agent_id` (45 §45.19.1). There is no documented join key back to the `Agent` `tool_use` that spawned it (`--forward-subagent-text` gives `parent_tool_use_id`, a different identifier). **D.**
9. **All permission-rule validation and warning text is client-side.** The 16 validation checks, the two warnings (wildcard-before-command; rules on tools the file checks ignore), the four startup warnings, dangerous-rule stripping and workspace-trust gating all go to the debug log in a non-interactive session (24 §24.9.1–§24.9.3, §24.8.4). A GUI rule editor must reimplement `ORe`, `zd` and `TCe` or it will let users write rules that silently never match. **D + R.**
10. **The denial-limit fallback and its auto-deny countdown are invisible.** No `can_use_tool` field carries `denialLimitFallback`; headless the limits instead abort the agent with `Agent aborted: too many classifier denials in headless mode` (24 §24.10.8). A GUI must count `system/permission_denied` frames itself against 3-consecutive / 20-total and warn before the abort. **D.**
11. **`localDisplayOnly` asks are answerable but not renderable.** They arrive flagged `requires_user_interaction: true`, but the consent disclosure the approval depends on never crosses (24 §24.11.1, §24.16.2). The only honest GUI behaviour is to say the session must be opened interactively. **X.**
12. **The bypass-permissions disclaimer must be rebuilt, and the "vouched" form needs a user-settings write.** No dialog headless; without the accepted flag the mode silently downgrades to `default` with a stderr-only notice (24 §24.2.6, §24.17.3). `eL()` accepts `localSettings`, so `update_settings` unlocks the basic form, but `YQe()` needs policy or user settings — a disk write. **X + R.**
13. **`AskUserQuestion` previews are off by default for SDK-shaped clients.** The preview section of the tool prompt is omitted for client types beginning `sdk-` and for `claude-desktop`/`local-agent`/`remote` (21 §12.4), so the model never emits previews unless the GUI sets `CLAUDE_CODE_QUESTION_PREVIEW_FORMAT`. Cheap to fix, invisible if missed. **D with workaround.**
14. **`/plan`, `/add-dir` and `/ultraplan` are all absent headless** (verified against the live 2.1.259 command list). `get_plan` and `add_directory` cover two of the three; ultraplan has no substitute short of building on ch. 37 directly. **X.**
15. **The GUI must handle its permission dialog being cancelled out from under it.** The `PermissionRequest` hook chain races the host request; a hook win aborts the request and sends `control_cancel_request` (45 §45.19.4), and a late answer is discarded. Answering a cancelled request yields the TUI's `The request this approval was for had already been withdrawn; the answer applied to nothing.` (24 §24.14.5). **P, but a correctness requirement rather than a feature.**

## Unverified

Everything below was inferred, or read from code rather than from a spec section, and should be confirmed before it is built on.

1. **`add_directory` control_response contents.** I asserted that the §24.12.2 validation messages (`<p> is not a directory. Did you mean to add the parent directory <parent>?` etc.) are echoed by the `add_directory` control request. SPEC 24 documents the messages and SPEC 45's request table lists the request, but I did not read the `add_directory` handler. The messages themselves are verbatim from §24.12.2; only the delivery channel is inferred.
2. **Whether `afkTimeoutMs` and `response` survive `updatedInput` schema validation.** The `AskUserQuestion` input schema is built with `tt(...)` — a strict-object builder — over `{questions, answers?, annotations?, metadata?}` [`cli.pretty.js:110887`], and `response`/`afkTimeoutMs` appear only on the **output** schema. Yet `call` reads `e.response` and `e.afkTimeoutMs` from the input [`cli.pretty.js:111008`], and the TUI's submit path does put `afkTimeoutMs` into `updatedInput` (21 §12.8). Either `tt` is not strict in the way I assumed, or a different schema is used for the §24.20.6 `updatedInput` check. Until this is settled, a host should mirror the TUI's exact `updatedInput` shape and be ready for `The permission handler returned updatedInput for AskUserQuestion that failed schema validation`.
3. **The classifier "explain" affordance.** The brief names one; I found none in chapters 24 or 26. What ships is the decision-reason banner `$g` (24 §24.14.3) and the `/permissions` → `Recently denied` tab with per-item approve/retry (24 §24.19). If an "explain" button exists it is in ch. 26's auto-mode setup surfaces, which I did not read.
4. **Whether `task_started` / `task_updated` / `task_notification` frames carry `agent_id`.** If they do, the `agent_id` → agent-name gap (top gap 8) downgrades from D to R. SPEC 45's frame list mentions these subtypes but I did not read their schemas; they belong to another agent's area.
5. **Whether plan-mode `<system-reminder>` attachments are filtered before the wire.** The BRIEF's §45.9.2 drop-list does not include meta user messages, and `--replay-user-messages` is in afleet's launch line, so I assumed they arrive as `user` frames the GUI must suppress. I did not read the meta-message filter.
6. **The exact delivery of launch-time mode warnings.** I classified them as stderr/debug-only based on 24 §24.9.2 ("printed to the user when the output format is interactive; otherwise they go to the debug log"), which is stated for permission-rule warnings specifically. The bypass-downgrade and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` notices are documented as stderr in §24.2.6 but I did not confirm they never appear as `informational` frames.
7. **`--permission-prompts host` semantics on 2.1.259.** Read from `claude --help` on the installed binary (verbatim: `Who answers permission prompts with --print: "host" (the SDK host or --permission-prompt-tool) or "none" …`). The flag does not exist in the 2.1.257 SPEC, so its interaction with `--permission-prompt-tool stdio` (redundant? conflicting?) is inferred, not read.
8. **`decisionClassification` consumers.** SPEC 24 Open questions records that no consumer of the field was found in the chunks read. I treated it as pure telemetry provenance per the 45 §45.19.2 schema text.
