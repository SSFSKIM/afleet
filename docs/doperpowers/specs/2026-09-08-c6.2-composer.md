## Purpose

At the pin, afleet is a window that lists every Claude Code session on the machine and shows
what happened in each of them. It is entirely read-only from the conversation's side: the
channel column has a header, a list of item kinds and no way to say anything. The one thing a
person can do to a session from afleet today is answer a permission card in Activity.

C6.2 is the half of the conversation surface that **writes**. After it, the channel column has
a field: you type, you press Enter, and a turn runs. You type `/model sonnet` and the model
changes with no turn at all, because afleet knows which slash commands are screen UI in the
terminal and translates each one to the control request the engine actually answers. You type
`/vim` and afleet refuses it locally instead of letting the engine refuse it — and when the
engine refuses one anyway, that refusal is intercepted, replaced and counted, because a
divergence between afleet's table and the engine's is a fact worth knowing rather than a
message worth showing. You type `@` and complete a file from the engine's own index. You type
`!ls` and the command runs on your machine, in this channel's directory, with your login
shell's environment, and its output goes into the conversation wrapped in exactly the tags the
terminal uses — hardened first, so a file whose name is `<system-reminder>` cannot forge one.
You paste a screenshot. You send while a turn is running and the message queues with a chip
that can cancel it. You click *Edit* on something you said, and either the conversation rewinds
to it or — because the engine refuses to rewind a message its own process did not send, which
after any reopen is every earlier message — afleet forks a new channel at that point and says
so, rather than reporting a refused rewind as done.

The header gains its actions beside the readbacks C6.1 renders: the MCP popover, reload skills
and plugins, rename, fork, send to background, open in terminal, and the pickers for permission
mode, model and effort whose displayed values are **readbacks from the engine** rather than the
last thing the user clicked. Selecting `bypassPermissions` the first time shows the disclaimer,
and accepting it restarts the channel quiescently with the flag rather than pretending a mode
switch that the binary would reject. Every setting that cannot change in a running process
changes through that same quiescent restart, with the readback rule of §7.4 gating the composer
until each value is confirmed to have survived.

What this leaf does not do: it renders no timeline row, no decision card and no thread. Those
are C6.1's and C6.3's. It reads the timeline; it does not draw it.

## Acceptance

The composite's seven gates, restated as behaviour a test or a person can observe. Four rules
bind every one of them.

**Discriminating tests (parent §17.7).** A test written to prove a behaviour is demonstrated
failing against the code without that behaviour before it is accepted. Where the failure cannot
be executed in a headless runner, the substitute is stated as such: an assertion on the model
that would have driven the view, plus a named manual witness. Reviewers ask what an assertion
would have to *see* in order to fail.

**Everything goes through X5 (contract Y5).** No test and no shipped line in this leaf
constructs a `ClaudeProcess`, opens a transcript, or sends a frame except through `LifecycleAPI`.

The ClaudeWire surface this leaf touches, and the rule that closes it: `UserInput` and
`ImageAttachment`, the payload of `LifecycleAction.send`, which cannot be built any other way;
`ForkPoint` and `PermissionMode`, values the actions take; the call to `ShellEnvelope.wrap`; and
**a control-request spec whenever ClaudeWire types one** — `FileSuggestions`, `ReloadSkills`,
`ReloadPlugins`, `RenameSession`, wrapped in `AnyControlRequest` and sent through X5. Amended at
Task 4 from a flat list of five: a typed spec is C2's own statement of a subtype and its keys, and
a leaf spelling the subtype and payload itself is a second opinion about a shape C2 owns. The raw
`AnyControlRequest(subtype:payload:)` form is reserved for a subtype ClaudeWire does not type —
`cancel_async_message` is this leaf's only one (tracker 142).

**Nothing is written under a config home (X9).** Not by the leaf, not by a test. The default
suite's trees live under `FileManager.default.temporaryDirectory`; the live gate uses
`/tmp/afleet-fixtures/config-home` under C5's `ScratchLiveGate` and runs C5's recursive
`ConfigHomeWitness` before and after, attributed against the spawned child. G5 additionally
asserts through C5's `AppFileWrites` seam that the bypass path performs **no write at all**
outside afleet's own store — `settings.json` is the CLI's and afleet never touches it.

**Reports emit counts (parent §6.3, §11).** Every gate report, test failure message and
diagnostic states counts, sizes, durations and identifiers — never a path, a title, a session
id, a slug or an environment. Test inputs use invented identifiers. In particular no assertion
in this leaf compares an aggregate that transitively reaches a `ResolvedEnvironment`,
`ChannelContext`, `ChannelKey` or `IndexEntry` (C5's rule, its Task 8 finding).

### G1 — the router UI over every row of X10 (required, no engine)

`ComposerRouterTests` drives the composer's model over a `LifecycleAPI` double that records
every call, with a scripted handshake and `system/init`.

- **Every local row.** For each of the twenty-seven rows of `RouterTable.local`, a typed line
  produces the `Routed` case the table names and the composer dispatches it to the matching X5
  member: `.controlRequest` → `send(_:on:)` — and, for the two rows a picker displays, the
  `get_settings` the dispatch table's own "then re-read the readback" clause asks for, added by
  the 2026-09-08 fix wave — `.strategy` → `run(_:arguments:on:ui:)`,
  `.lifecycle` → `perform(_:on:)`, `.restart` → `perform(.quiescentRestart(_):on:)`, `.text` →
  `sendPrompt(UserInput:on:)`, `.native` → the named surface opens and **nothing reaches the
  lifecycle**. The enumeration is over `RouterTable.local` itself, not over a list written in
  the test, so a row added to the table fails this gate until the composer handles it. The
  comparison is two-directional: an unexpected call fails as loudly as a missing one.
- **Terminal-only.** With `system/init.terminal_slash_commands` carrying an invented name, that
  name is absent from autocomplete and typing it produces `.refusedLocally`, rendered inline in
  the composer, with the text `RouterTable.explanation(forTerminalOnly:)` returns **verbatim**
  and nothing reaching the lifecycle. The composer writes no copy of its own (X10). See the
  `[parent-impact]` below: the sentence that table currently returns contradicts §7.7, and this
  gate asserts fidelity to the table rather than blessing the sentence.
- **Pass-through.** A command in the handshake's `commands` that is in neither the local table
  nor the terminal-only list is sent as text, unmodified, as one `sendPrompt`.
- **The drift interception.** An assistant frame whose whole text is
  `/<name> isn't available in this environment.` is intercepted through
  `RefusalInterceptor`, the replacement is what the composer shows in place of the frame, and
  the drift count rises by exactly one. The same sentence embedded in a longer assistant message
  is **not** intercepted and the count does not move — the negative arm is required, because an
  interceptor that fires on a substring rewrites answers the engine meant.
- **Both refusal shapes.** Since the X10 corrective (`6abd4a0`) the engine's second refusal —
  the interactive-panel one at 2.1.263 `cli.pretty.js:540305` — is a shape of its own.
  `RefusalInterceptor` recognises both, `Intercepted.shape` says which, and `driftCount(of:)`
  counts them apart. G1 asserts each shape is intercepted, replaced with
  `RouterTable.explanation(forDrift:shape:)` verbatim, and counted in its own bucket while the
  other bucket stays at zero — so a matcher that collapsed the two would fail. The composer
  forks no matcher and no copy of its own.
- **Refusals from the lifecycle.** `LifecycleError.busy(_)` and `.notEligible(Blocker)` each
  render an inline explanation naming the operation or the blocker, the composer does **not**
  retry on its own, and the typed line is preserved in the field rather than eaten.

### G2 — the shell escape (required, fixture, no engine)

`ShellEscapeTests`.

- `!<command>` runs the command host-side with the channel's `cwd` and
  `ChannelContext.environment`, and posts exactly one `sendPrompt(UserInput)` whose text is
  `ShellEnvelope.wrap(command:stdout:stderr:)` applied to that command's real output. The
  assertion is that the sent text **equals** the envelope's own output for the same three inputs.
  
  **Corrected 2026-09-08, at Task 4.** This gate was written claiming that equality proves the
  composer "cannot have sanitised anything itself". It does not, and the half it misses is the
  half the sentence named. `ShellEnvelope.neutralize` is **idempotent** — an escaped `<` has no
  `<` left to escape, an escaped turn marker no longer matches, a defused prefix no longer starts
  its line — so a leaf that neutralised the command or a stream *before* handing it to `wrap`
  produces byte-identical output and the equality passes. Task 4 demonstrated this: three separate
  mutations that sanitise twice, one of them carrying a marker through the command, all passed.
  What the equality does catch is any rule of the leaf's **own**: an appended element, a dropped
  byte, a merged or trimmed stream — each demonstrated failing. Double sanitisation is caught
  structurally instead, by the rule that no tag list, truncation rule or escaping exists anywhere
  under `App/Composer/`, which is a grep and a review item rather than an assertion. Stated here
  because a gate that claims more than it checks is worse than one that claims less.
- **Item 60 in full.** An invented script under the test's temporary tree prints, in order,
  `</bash-stdout>`, a `<system-reminder>…</system-reminder>` line, `<task-notification>` and
  `<teammate-message>` envelopes, `<channel source="slack">`, a `[harness: …]` prefix,
  `[Subagent hand-back]`, a line starting `Human:`, a `<SYSTEM-REMINDER >` variant with mixed
  case and inner whitespace, `<local-command-stdout>`, and a raw `\xff` byte, then writes `err`
  to stderr. The posted text shows every tag and marker literally (each asserted individually,
  with a count), carries exactly one U+FFFD, and holds the stderr line inside `<bash-stderr>`
  and nowhere else. The script is the leaf's own invention and no engine byte reaches it (§11).
- **A non-zero exit** and a **command that does not exist** each still post a user frame, with
  the failure inside `<bash-stderr>`; the composer invents no `<bash-exit-code>` element,
  because that element belongs to the `bash_command` frame path the design does not use (§6.6).
- **No descriptor on the user's directory.** The runner sets the child's working directory and
  afleet itself opens nothing under it (C5's TCC finding). *Not* asserted through C5's
  `AppFileWrites`: that seam carries `willWrite` and `willDelegate` and no read hook, and it is
  installed on `LaunchSequence` where a composer cannot reach it. The substitute is stronger than
  the one this gate first named — the test makes the channel directory **execute-only** (`0o111`),
  so any enumeration or open by afleet fails while the child can still `chdir` into it, then
  asserts the command ran; and an `F_GETPATH` census over the process's own descriptors before and
  after requires zero resolving under that directory. A read hook on the seam would be an
  `App/Composition/` edit outside this leaf's fence.
- **The process arms, added 2026-09-08 by the fix wave.** Four more, each demonstrated failing
  against the code it replaced. *Ownership:* with the channel held elsewhere in the double, a
  command whose only job is to leave a mark under the temporary tree runs nothing and leaves no
  mark, and the refusal is the send's own. *The retention bound:* `yes` under an injected cap
  returns in about a second of a sixty-second budget, retaining no more than the cap. *The tree:*
  `sleep 30 & wait` under a half-second budget leaves a descendant whose pid the command wrote
  down, and it is gone by the probe. *Cancellation:* `stop()` while a command runs returns the send
  and reaches no lifecycle member. The pid and the counts are all these messages carry (§11).

### G3 — the queue chip (required, fixture, no engine)

`QueueChipTests` replays a `command_lifecycle` sequence through `fake-claude` into a real
`ChannelTimeline`.

- The chip's rows follow `Overlay.queue.queued` in arrival order and disappear as each id
  reaches a terminal state; a `started` id is not offered for cancellation as *queued*.
- Cancelling a row sends exactly one control request of subtype `cancel_async_message` naming
  that id, through `LifecycleAPI.send(_:on:)`, and the composer removes nothing optimistically —
  the row leaves when the engine's next `command_lifecycle` says it did.
- A send while a turn is running produces one `sendPrompt` and the chip appears; a send with
  no turn running produces one `sendPrompt` and no chip. Both arms are asserted, so a chip
  that is always on cannot pass.

### G4 — edit, rewind and *Fork from here* (required, `rewind-turn`, no engine)

`EditAndRewindTests`, over the `rewind-turn` fixture's two recorded legs.

- **Honoured.** `rewind_conversation {target_message_uuid}` answering
  `{rewound: true, targetMessageUuid, prefillText, precedingAssistantUuid}` prefills the
  composer with `prefillText` **as the engine returned it**, not reconstructed.
- **Refused.** The recorded refusal is a `control_response {subtype: "success"}` whose body is
  `{rewound: false, prefillText: null, precedingAssistantUuid: null, error: "stale target"}`.
  The composer reads the **body**, not the envelope, falls back to
  `perform(.fork(at: ForkPoint(entryUUID:dropsTurn:)))`, and shows a visible note saying the
  conversation was not rewound and a fork was opened instead. A test that mutates the composer
  to decide from the envelope must fail this gate.
- **Every request carries `last_seen_user_message_uuid`**, and its value is the **newest** user
  message the composer has rendered — asserted on the payload, together with the arm that it is
  **not** the edit target's own uuid. That arm is the one that matters: the probe measured the
  field naming the target itself answering `"unseen later turn"`, so a composer that reached for
  the obvious value would be refused on every edit of an older message and would fall back to a
  fork every time, looking correct in a smoke test while the feature was gone.
- **`"unseen later turn"` takes the fallback**, injected through the double, since `rewind-turn`
  was recorded without the field and can only produce `"stale target"`. A third arm covers an
  unrecognised body-level `error`, which must also fall back rather than report success.
- **The fork point comes from the transcript.** The refusal's `precedingAssistantUuid` is
  `null`, so the fork point is resolved from the channel's own items: `entryUUID` is the **last
  record** of the assistant item immediately preceding the edited user message — the item's key
  names only its first — `dropsTurn` is that user message's `promptUUID`, and the prefill is that
  item's `text`, placed in the **fork's** field and not the source's. Asserted against
  the fixture's transcript, including the negative arm — an edited message with no preceding
  assistant record offers no fork and says why.
- **No file rewind.** Across both legs the lifecycle double records **zero** `rewind_files`
  requests. The composer's *Edit* is not `/rewind`: it never previews or applies files (§8.5,
  §7.7 `/rewind`, 2026-09-06).

### G5 — the bypass gate exactly as §8.6 (required, lifecycle double)

`BypassGateTests`.

  `perform(.quiescentRestart(RestartRequest(allowBypass: true)))`; then exactly one

- **X9.** Across every arm, C5's `AppFileWrites` seam receives zero paths under any config home

### G7 — every picker's value is a readback (required, `control-shapes`, no engine)

`PickerReadbackTests` replays `control-shapes`.

- The model picker's options come from `list_models` (`{models: [{value, resolvedModel,
  displayName, …}]}`) and its **selected** value comes from `get_settings.applied.model`,
  compared after resolving an alias through the handshake's `models[].resolvedModel`.
- The effort picker's selected value comes from `get_settings.applied.effort`, with

- The permission-mode picker's selected value comes from the handshake's

- **The discriminating arm:** after a `set_model` whose readback reports a *different* model

  and the test fails if the picker shows the click. `apply_flag_settings` answers with no

  `get_settings` shows nothing — that arm is asserted too.
- A restart-required change follows §7.4: the composer is disabled until every readback matches,
  and a mismatch raises a banner naming the setting and keeps it disabled. Both arms on the double.
  **Two glyphs, not one** (corrected at Task 10's audit, which read this clause as claiming one).
  The connecting glyph is shown while the process is being replaced; once `quiescentRestart` returns
  the process is back and only the readback is outstanding, so the field stays disabled behind the
  *waiting* glyph. `confirmReadback` therefore clears `isRestarting` before it re-reads, which is the
  design and not a deviation — the original wording conflated the two phases. What the tests assert
  is `isDisabled` and the banner across both arms; the glyph transition itself is asserted only for a
  refused restart (`HeaderActionTests`), so which of the two glyphs is drawn during the readback wait
  is unasserted.

## Gate audit — the clauses a reader should not assume (Task 10)

Every gate's tests pass and the leaf's fourteen suites executed exactly the 115 test methods they
declare. This section records only where a clause is **thinner than its wording**, because a gate that
claims more than it checks is worse than one that claims less (the rule G2's first clause already
applies to itself). Nothing here is a failing test; each is a clause a merge reviewer should read as
narrower than written.

- **G1, every local row.** The enumeration over `RouterTable.local` is real, two-directional and
  floored at 27 rows, but it compares X5 **member names** only. `.restart` reaching
  `.quiescentRestart` specifically, `.lifecycle` reaching the named action, `.controlRequest` carrying
  the row's subtype and `.strategy` naming the row's strategy are all unpinned — five rows collapse to
  `["route","run"]`, so a cross-wiring inside that family passes. The double already records every one
  of these (`actions`, `sentSubtypes`, `strategies`, `labelledSequence`); the assertion simply does not
  read them.
- **G1, the drift replacement.** Interception, verbatim replacement text and the per-shape counts are
  asserted and correct. "*The replacement is what the composer shows in place of the frame*" is not:
  `interceptedReplacements` has no reader, and `RefusalSurface` draws the replacement as an additional
  label beside the field rather than substituting for the assistant row. The substitution site is a
  timeline row, which is C6.1's directory — filed on tracker 153 rather than fixed here.
- **G1, refusals name the operation or the blocker.** Asserted as
  `refusal == ComposerModel.explanation(of: error)` — the production function itself, so it proves the
  composer used its own copy and not that the sentence interpolates anything. The no-retry arm is
  genuinely discriminating (a success is staged behind the failure).
- **G2, the channel's `cwd` and environment.** Not asserted anywhere. No test runs `pwd` or reads a
  variable out of the context's `ResolvedEnvironment`, so a composer handing `HostShellRunner` the
  process's own directory and inherited environment passes every arm — including the execute-only
  descriptor arm, whose premise is that the child chdirs into the channel directory. Production does
  pass both (`ShellEscape.swift`); nothing pins it. This is the gap the blocked live item 12 would
  otherwise have closed.
- **G3, the two send arms.** Neither arm puts a turn in flight: the chip appears because the test
  pushes a `queued` frame whose uuid is unrelated to the send, and the no-chip arm reads `rows` with no
  settle, so at that instant no implementation could have a row. The real discriminator is
  `testPromptSentPutsNoRowInTheChip`, which inverts the same bounded wait and floors it with a
  `command_lifecycle` arm. The clause as worded — chip *iff* a turn was running — has no test, and may
  not be reachable: the chip is fold-only and the queueing decision is the engine's.
- **G3, the replay mechanism.** The `ChannelTimeline` is real and the frames go through the production
  decoder and reducer, but the `command_lifecycle` sequences are built in the rig, not replayed from a
  fixture, and `fake-claude` is not used. Recorded sequences hold one id queued at a time, so the
  multi-row ordering arm needs invention — the deviation is defensible and is declared here rather
  than left for a reviewer to discover.
- **G4, "shows a visible note".** Every arm is asserted on `ComposerModel.editNote`, which no view
  reads. Tracker 153, as above.
- **G4, the fork point's `entryUUID`.** The expected value is computed by a copy of production's own
  `precedingAssistantKey(before:)` walk, so the test compares production against itself. The fixture's
  honoured body carries an independent `precedingAssistantUuid` that was available and unused.
  `dropsTurn` and the prefill *are* checked against fixture-derived values, and the negative arm is
  properly floored.
- **G4, "reads the body, not the envelope".** The clause's literal mutation is unrepresentable:
  `LifecycleAPI.send` returns the body and the envelope is unwrapped below the composer. The
  behaviourally equivalent defect — treating "did not throw" as success — *is* caught, because the
  refusal is staged as a `.success`.
- **G5, the decline arm's drain.** The 200-yield drain exists to catch a decline that writes from a
  detached `Task`, but the lifecycle log is read *before* the drain runs; only the store-write check is
  taken after it. The clause holds for store writes and is scheduling-dependent for lifecycle members.
  One line moves it.
- **G5, "across every arm".** The X9 aggregate — zero config-home paths *while* the seam saw a
  non-zero number of writes, with a discrimination arm proving the comparator non-vacuous — is
  complete and is the clause's real evidence. Three of the seven arms assert only the zero half
  locally, which is vacuous on its own.

## Design

### The shape: two models, one seam

`App/Composer/` holds `ComposerModel`, a `@MainActor @Observable` model per channel, and the
views over it. `App/Header/` holds `ChannelHeaderActionsModel` and its menus. Both take
`any LifecycleAPI`, a `ChannelKey`, the channel's `ChannelTimelineModel` and the channel's
`ChannelContext`; neither holds a process, a frame stream it opened itself, or a store key
outside afleet's and FleetKit's own namespaces. They are separate models because they have
different lifetimes — the composer's state (the draft, the attachments, the pending rewind, the
ghost text) survives a header action, and a header action that restarts the channel must be
able to disable the composer without owning its draft.

The **one seam between them** is `ChannelSurfaceState`, a small observable the two share: the
composer is disabled while a restart is in flight and while a readback is unconfirmed (§7.4),
and the header's restart-required actions are what set that. Nothing else crosses.

Both models subscribe to `LifecycleAPI.events(of:)` for the channel — the same shape C5's
`ChannelEventPump` already uses. That is how the composer sees `prompt_suggestion`,
`command_lifecycle` (via the timeline's overlay), the drift refusal text, and the handshake and
`system/init` fields the router needs. It is not a reach around X5: `events(of:)` **is** X5.

### The field

A markdown-aware `NSTextView`-backed field. Shift+Enter inserts a newline; Enter and Cmd+Enter
both send (§8.5, §8.7). Esc interrupts the running turn; Shift+Tab cycles permission mode;
Cmd+Shift+Esc is *Stop everything* behind its confirm. Those four keys are exactly the ones C5
left undeclared for this leaf, and this leaf declares them and no others.

Sending is always one `sendPrompt(UserInput)` and never anything else — X5's `sendPrompt` **is**
`perform(.send)`'s path (same preconditions, same refusals), answering the uuid the supervisor minted
so the composer can raise `HostSignal.promptSent` for it; §8.5's "always `perform(.send(UserInput))`"
names that path. The draft is cleared
only when the action returns without throwing; a `LifecycleError` leaves the text in the field,
because a composer that eats a message on a refusal has lost the user's words.

### The router UI

A line beginning `/` goes to `route(_:on:)` and the composer dispatches the `Routed` case:

| `Routed` | What the composer does |
|---|---|
| `.controlRequest` | `send(_:on:)`, then re-read the readback the table's row names |
| `.strategy` | `run(_:arguments:on:ui:)` with the composer as `StrategyUI` |
| `.lifecycle` | `perform(_:on:)`, behind a confirm for `stopEverything`, `backgroundAll` and `logout` |
| `.restart` | `perform(.quiescentRestart(_):on:)`, then §7.4's readback wait |
| `.text` | `sendPrompt(UserInput(text:))` |
| `.native(surface)` | opens that surface (`modelPicker`, `effortPicker`, `tasks`, `agents`, `switcher`); nothing reaches the lifecycle |
| `.refusedLocally(explanation)` | renders the explanation inline above the field |

Autocomplete is `CommandRouter.autocomplete(handshake:systemInit:)` verbatim: the engine's own
commands merged with the local table, minus everything the engine declared terminal-only. The
composer writes no list of its own and no copy of its own — X10 makes the table the single
source, and the leaf that renders it is not allowed a second opinion.

The composer holds one `RefusalInterceptor` per channel and passes every complete assistant
message text through it. A hit replaces the rendered message with the interception's
replacement and increments the drift count that C5's diagnostics already record. A miss does
nothing. The interceptor's whole-string match is C4's and is not re-implemented.

`StrategyUI` is the composer: `open(url:)` hands a URL to the Browser tab through the channel
context's `LinkRouterCapability` as a `WorkspaceLink.url`, and `confirm(preview:)` presents
`/rewind`'s dry-run counts and returns the user's `RewindChoice`. Those are the two things a
multi-step strategy needs and the only two the protocol asks for.

### `@` and `!`

`@` opens a completion popover fed by `file_suggestions {query}` through `send(_:on:)`,
debounced, cancelled on each keystroke, and never spawning a process or reading a directory
itself. The engine owns the index; afleet asks it. The answer is
`{suggestions: [{path, score?}]}` and the CLI omits `score` (2.1.263 `cli.pretty.js:452318-452323`,
schema `:94598`); the request takes `query` and nothing else — no `limit`, no `cwd`.

`!` is host-side. The composer runs the command with the channel's `cwd` and the
`ResolvedEnvironment` from `ChannelContext.environment` (X11's single capture, not a fresh
one), collects stdout and stderr separately, and posts one
`sendPrompt(UserInput(text: ShellEnvelope.wrap(command:stdout:stderr:)))`. The sanitiser is
C2's and is **called**, never copied: the composer neither adds a tag to the neutralised list
nor trims a stream, because `ShellEnvelope` already caps each stream at 64 KiB with a
byte-count notice and replaces invalid UTF-8. The `bash_command` frame is not used (§6.6): its
output never reaches the model or the transcript, which is the entire point of the `!` path.

afleet opens no descriptor on the channel's directory — the runner sets the child's working
directory and nothing else touches it (C5's TCC finding).

### Attachments

Paste and drop attach image blocks, becoming `ImageAttachment(mediaType:base64:)` on the
`UserInput`. Non-PNG/JPEG images are converted to PNG; the composer caps an attachment set at
**eight images and 8 MiB each after conversion** and refuses beyond that with an inline note.
This is validation at a system boundary (the pasteboard and the drag pasteboard are user input),
which is exactly where the simplicity rule permits it; a 60 MB screenshot base64-encoded into a
single stdin line is a real failure mode and not a hypothetical one.

### The queue chip

The chip reads `Overlay.queue.queued` out of `StreamIngestion.timeline`, the one-read view of
durable, overlay and preview state that C3's host-signal corrective landed (`2e85ac0`). It follows
`Effect.changes` off `effects`, which now carries overlay and preview changes as well as durable
ones, and it derives nothing of its own: **the ingestion holds the channel's only reducer, and
nothing in the app folds the wire** (X4 as amended). Each row's label is resolved by matching the queued
command uuid against the timeline's `userMessage` items (`ItemID.key`), so the chip says what
is queued rather than how many; a uuid with no item yet shows as an unlabelled row rather than
being hidden, because a queued message the user cannot see is worse than an unlabelled one.

Cancel sends `AnyControlRequest(subtype: "cancel_async_message", payload: ["message_uuid": …])`
through `send(_:on:)`. The key is snake_case and the answer is `{cancelled: Bool}` (2.1.263
`cli.pretty.js:452054-452063`, schema `:94598`, declared in the request table at `:94602`).
ClaudeWire carries no typed spec for this subtype; the raw form is the sanctioned route
(`AnyControlRequest.raw` is a `RawControlRequest`, whose wire subtype is per-instance) and needs
no C2 edit. Tracker entry 142 records it so C2 can type it at the next typings pass.

`cancelled: false` means the message **was not in the queue** — the engine's own schema note —
so it is the queue's equivalent of §8.4's `{backgrounded: false}` rule: the chip refreshes from
the overlay and the row disappears without a banner, because the message already started. The
chip removes a row only when `command_lifecycle` says the id left the queue: no optimistic
removal, because a cancel the engine declined would otherwise vanish a message that is still
going to run.

**Host signals.** A host-side move reaches the fold through `ChannelTimelineModel.signal(_:)`,
which forwards to `StreamIngestion.signal(_ HostSignal) async -> Effect`. Raised **after** the X5
call succeeds — never before, so a refused action leaves no preview behind; both signals assert
that arm. The composer raises two: `HostSignal.rewound(toUUID:)` after an honoured rewind, and
`HostSignal.promptSent(uuid:at:)` after `sendPrompt` returns, carrying the uuid it minted,
lowercased, which is the spelling the engine echoes and every timeline item is keyed by.

`promptSent`'s observable is `TurnAttribution.prompted(uuid:)` on the next `result` frame, not
anything the queue chip can read — see the resolved filing below. So the chip is unchanged by it,
and a test asserts that absence with the `command_lifecycle` arm as its floor rather than leaving
the claim untested.

### Edit, rewind and *Fork from here*

*Edit* on a past user message sends `rewind_conversation` directly through `send(_:on:)` — not
the `/rewind` strategy, which is a different thing that also moves files. The payload **always** carries both
`target_message_uuid` and `last_seen_user_message_uuid`, the latter being the `promptUUID` of the
**newest** user message the composer has rendered for this channel.

That field is what makes *Edit* work. The probe `spike_rewind_last_seen` (`77a0d62`, zero turns,
three forks of a scratch session on 2.1.263) measured all three arms: with the field naming the
newest user message the engine **honoured** a rewind to a message from before the running
process; with the field omitted the same target answered `"stale target"`; with the field naming
the target itself it answered `"unseen later turn"`. The engine's predicate is a later-turn scan
under two names (`:452145-452153`), not a test of which process sent the message. So the rewind
is the ordinary path and **the fork fallback is the rare one** — which inverts the weight §8.5
originally gave item 13, and is now recorded on the parent (`81a3dca`).

The value matters as much as the presence: naming the target rather than the newest message
turns every edit of an older message into a refusal, and the fallback would hide it.

The composer reads the **body**:

- `rewound: true` → prefill the field with `prefillText` as returned.
- `rewound: false` → do not report it as done. **Both** `"stale target"` and
  `"unseen later turn"` trigger the same fallback; so does any other body-level `error`, because
  the engine has ten of them and the composer's contract is that a refusal is never shown as a
  success. Resolve the fork point from the channel's own items (the refusal's
  `precedingAssistantUuid` is `null` on the recorded leg): `entryUUID` is the `ItemID.key` of the
  assistant item immediately before the edited message, `dropsTurn` is the edited message's
  `promptUUID` — `entryUUID` being that item's **last** record, since `ItemBuilder` keys a merged
  assistant item by its first. Then `fork(at:on:)`, prefill the **sibling's** field from that
  message's own `text`, select it, and say in the source's composer that the conversation was not
  rewound and a fork was opened. With no preceding
  assistant record there is no fork point, so the composer offers nothing and says why.

The note's **wording** distinguishes the two strings — a later turn the composer had not seen
reads differently from a target the engine cannot reach — while the **path** is identical. Both
wordings ship; the fixture leg pins `"stale target"` because `rewind-turn` was recorded without
the field, and `"unseen later turn"` is driven through the double.

No `rewind_files` request is ever emitted on this path, in either direction. Files move only
through `/rewind`'s strategy, which the executor already orders correctly (conversation first,
files only after an honoured rewind and only when the sheet asked for them).

### Ghost text

When *Prompt suggestions* is on for the channel, the `prompt_suggestion` frame after each turn
renders as ghost text that Tab accepts. The text is the frame's `suggestion` key (2.1.263
`cli.pretty.js:451213`, schema `:94598`), and `--prompt-suggestions` is valid only with
`--print` and `--output-format=stream-json` (`:295247`), which is how afleet launches. C3's
reducer deliberately drops that frame — it is not
a timeline item and adding one would touch the differential invariant — so the composer reads
it off `events(of:)` directly. That is an *observation*, not a second fold: the composer runs no
reducer, keeps no projection and writes nothing back into the timeline, so X4's one-fold rule is
untouched. `events(of:)` hands out a fresh fan-out per call by contract, and C5's
`ChannelEventPump` is already a second consumer of the same stream. Turning the setting on or off is a `RestartRequest(promptSuggestions:)`,
a quiescent restart, because `--prompt-suggestions` is a launch flag (§7.7's matrix; the field
already exists on `RestartRequest`). The control is **per channel** and lives in the header's
settings menu, not in C5's app-global Settings screen, because the flag is per process and item
40's acceptance reads per channel.

### The pickers, and readbacks over clicks

Three pickers: permission mode, model, effort. Each shows a **readback**, never the last click:

| Picker | Options from | Displayed value from |
|---|---|---|
| Model | `list_models.models[]` (`value`, `displayName`, `supportsEffort`) | `get_settings.applied.model`, alias-resolved through `models[].resolvedModel` |
| Effort | `models[].supportedEffortLevels` for the current model, minus `max` mid-session | `get_settings.applied.effort`; `null` means the default |
| Mode | `PermissionMode.allCases`, `bypassPermissions` gated as below | the handshake's `current_permission_mode` |

A click issues the request, then re-reads. `apply_flag_settings` answers with no `response` key
at all, so the readback is always a fresh `get_settings` and never the answer. A readback that
disagrees with the click leaves the readback on screen and raises the disagreement; it does not
silently re-issue.

### The bypass gate

Exactly §8.6, and the order is the whole content:

1. `bypassPermissions` appears in the picker only when `get_settings` leaves
   `disableBypassPermissionsMode` unset or false. Unset means allowed — that is the parent's
   wording and the engine's default shape.
2. First selection shows the disclaimer. **Declining** leaves the mode unavailable, restarts
   nothing and writes nothing.
3. **Accepting** writes the acceptance to `FleetKitKeys.bypassAccepted` in the `fleetKit`
   namespace (§7.8 puts it there; afleet never writes the CLI's user settings), then performs
   one `quiescentRestart(RestartRequest(allowBypass: true))`, then sends `set_permission_mode`.
   Not the other order: the binary's validator refuses the mode outright when
   `isBypassPermissionsModeAvailable` is false, which is set from the launch flag alone (2.1.263
   `cli.pretty.js:750921-750931`), so a mode switch before the restart is a request that cannot
   succeed. The validator has three refusal arms — a restricted session, the settings disable,
   and the missing launch flag — and the composer renders whichever error string comes back
   rather than guessing which fired.
4. A later selection on a channel already launched with the flag sends `set_permission_mode`
   and restarts nothing.

`settings.json` is never touched, by anything, on any arm.

### The quit-time clause (§7.4 *Quit*, tracker 71)

**What "busy" means here, and the one narrowing.** Assembled from the two places the app already
reads it, with nothing new invented: a running turn is `ChannelState.presence == .busy` (what the
supervisor sets and the sidebar shows), and running local shells are the live task ids over the
channel's timeline — the same list the *Send to background* confirm names. `isDormantEligible` is
deliberately **not** used: it is wider than the clause, covering pending decisions, queued input and
armed-but-unstarted tasks, and a quit dialog that named those would warn about channels the clause
does not cover. The narrowing: a channel the user never opened has no timeline model, so at quit it
is judged by presence alone. Building one at quit was rejected — constructing a composer and its
ingestion for every owned channel at the moment the app is asked to stop starts work rather than
ending it. A live-task count on `ChannelState` would close it (tracker 71).


The composite defers §7.4's *Quit* clause to whichever leaf first ships a busy indicator the
dialog can name. This leaf ships one: the composer already knows whether a turn is running and
whether the channel has live shells, because that is what disables it and what the queue chip
reads. **This leaf therefore takes the clause**: on `applicationShouldTerminate`, if any owned
channel has a turn running or running local shells, afleet asks once, naming those channels by
title, then on confirmation runs `terminate()` on each owned channel with a process, then
`Fleet.shutdown()`, then exits; foreign and background-job channels are untouched. This is
recorded here rather than executed silently, because it is the composite's open owner question
and the architect may prefer it in C6.3 or C6.4 — see *Questions for the architect*, Q3.

## `[parent-impact]` — X5 publishes no unconditional terminate, and §7.4's *Quit* clause needs one

§7.4's *Quit* clause says: on confirmation, "it runs `terminate()` on each owned channel that has a
process, then `Fleet.shutdown()`, then exits". Through X5 that is `perform(.reap)`, and `Fleet`
gates the reap on dormant eligibility **on purpose** (`Fleet.swift:362-371`: "the reap the *user*
asked for must not end a child with a decision on screen or a background shell still working").

The two clauses collide exactly where the clause matters. The channels the quit dialog warns about
are, by definition, the ones with a running turn or running shells — which is precisely the set the
eligibility gate refuses. So the confirmed arm, implemented literally, would terminate nothing for
the channels it just warned the user it was ending. `ChannelSupervisor.reap()` is the unconditional
teardown and is deliberately not reachable through the facade.

**What shipped, and why it may be the better behaviour rather than a workaround.** A refused reap
is escalated through `.stopEverything` — interrupt the turn, `stop_task` each running task — and
then reaped again. Only X5 verbs; nothing reaches around the facade. And it is arguably what the
clause *wants*: §7.4 says elsewhere that a bare `terminate()` "would kill shells and background work
`--resume` cannot restore", which is the reason X9 requires the warning in the first place. Having
warned the user and been told to proceed, stopping the work explicitly and then reaping ends the
same channels while leaving the engine's own teardown a quiescent one, rather than closing the pipe
under running shells and letting stream-close wind-down do it implicitly.

**The architect's ruling is needed on which of the two the parent means.** If the literal text, X5
needs an unconditional terminate for this one caller and C4 adds it. If the escalation, §7.4's
*Quit* paragraph should say so, because "runs `terminate()`" currently reads as the bare form and
the next reader will implement it that way and find it does nothing. Recorded on tracker 71 with
the call site documented.

## Decision Log

- **Two models, one shared surface state.** The composer's draft must survive a header action,
  and a header action must be able to disable the composer. One model would have made the draft
  and the restart the same object's problem; three would have needed a coordinator.
- **The composer subscribes to `events(of:)` directly.** It needs `prompt_suggestion`, which is
  deliberately not in the timeline, and the handshake fields the router reads. Rejected: asking
  C3 for a reducer change, which touches the differential invariant for a value that is not an
  item; and asking C4 for a new X5 query, which X5 already answers.
- **The queue chip labels from timeline items, not from a new X5 query.** `perform(.send)`
  returns a `ChannelState` and drops the uuid `ChannelSupervisor.send` mints, so labelling by
  what afleet sent would need an X5 amendment. `Overlay.queue` plus `ItemID.key` answers the same
  question with what exists.
- **The fork point comes from the transcript, not from the refusal.** The recorded refusal's
  `precedingAssistantUuid` is `null`, so a design that read it would have worked on the honoured
  leg and produced nothing on the leg it exists for.
- **`cancel_async_message` goes out raw.** A typed spec is C2's file and this leaf does not edit
  ClaudeWire; the raw request is the sanctioned route and carries the same bytes.
- **The prompt-suggestions control is per channel.** It is a launch flag on one process and item
  40's acceptance restarts one channel; putting it in app-global Settings would make it a
  preference that silently restarts every open channel.
- **Attachment caps are stated.** The pasteboard is a system boundary, which is where validation
  belongs; the numbers are in the design so a reviewer can argue with them rather than discover
  them.
- **The `!` escape owns its child's process group (2026-09-08, fix wave).** `Process` cannot ask
  for one, and a `!` line is the one place in afleet where the *user* writes the command, so
  descendants are the ordinary case: `!sleep 30 &` leaves the shell exiting on `SIGTERM` while the
  `sleep` survives, and a run the UI reports as stopped has left a process behind. The escape
  therefore spawns with `posix_spawn` + `POSIX_SPAWN_SETPGROUP`, signals `-pid`, escalates
  `SIGTERM` → `SIGKILL`, and defers the reap until the escalation is done — C7.3's `ToolRunner`
  arrangement, copied rather than shared, because the App may not import a panel core for its
  composer.
- **Retention is bounded during the run, and the envelope's dropped-byte count is knowingly
  approximate (2026-09-08, fix wave).** `ShellEnvelope`'s 64 KiB cap applies to what `run` returns,
  so until it returns a `!yes` grows an unbounded `Data` for the whole budget. Capture is capped at
  the envelope's per-stream cap plus an 8 KiB margin and the tree is then ended. The margin is what
  keeps §6.6's truncation shape: the envelope emits its byte-count notice only for a stream longer
  than its cap. The consequence is accepted rather than fixed — the notice then counts the margin
  rather than what the command produced, which is unknowable because those bytes were never read —
  so the composer says so in its own sentence instead of leaving the undercount to speak.
- **Eligibility is asked before the spawn, not inferred from the send (2026-09-08, fix wave).** A
  `!` on a channel held by the user's terminal used to touch the filesystem and *then* have its post
  refused, which is the one ordering that cannot be undone. The escape asks `LifecycleAPI.state(of:)`
  and refuses on the three origins `ChannelSupervisor.send` refuses `heldElsewhere` on. A key the
  fleet owns no supervisor for answers nil and is **not** refused: the send would build one and
  apply its own guards, and nothing is known here that would justify refusing ahead of it.
- **`stop()` ends a running `!` (2026-09-08, fix wave).** The run is cancellable
  (`withTaskCancellationHandler` ends the group; the continuation answers nil) and a cancelled run
  posts nothing. A released composer that kept running would post into a channel the user has left.
- **The escalation is owed to the *group*, and settling is not paying it (2026-09-09, second fix
  wave, scalpel-3#1).** The shell's exit and the group's quiescence are two facts, and the run can be
  answered while the tree is still alive: a cancellation signals, the shell dies on the `SIGTERM`, a
  descendant that ignores it does not, and the budget then expires *inside* the grace — reaping the
  shell and handing the caller its result. Keying the `SIGKILL` on "has this run settled" skips it
  exactly then, which is the case the group signalling exists for. The escalation is therefore keyed
  on whether it has run, `beginTermination` is conditioned on `terminating` alone, and both
  escalation blocks hold the child strongly: they are one second apart, not two minutes, and a weak
  capture would hand the group's fate to whether `run` happened to return first.
- **A process group outlives the leader's reap; a pid does not (2026-09-09, second fix wave,
  scalpel-3#1 and #2).** The child's pid and the group it leads are recorded separately. `waitpid`
  releases the first — after which `kill(pid, …)` may name a stranger — and releases nothing of the
  second, because the kernel will not reuse a pid that still names a group with members. So
  `kill(-group, …)` is issued whether or not the leader has been reaped: it either reaches this
  command's survivors or answers `ESRCH`. Only the single-process fallback is still gated on the
  reap. This is what lets settlement's own last pipe pass end a tree it has already reaped.
- **A final drain that overruns the cap ends the tree like any other pass (2026-09-09, second fix
  wave, scalpel-3#2).** A shell that exits leaving a descendant on its stdout is reaped by the exit
  handler, and the run's last bounded pass over the pipe can be the one that fills the retention cap.
  Reporting an output-limited stop and then declining to signal — because the run has settled, or
  because the leader is gone — reports a stop that never happened. Neither is a condition on the
  termination any more.
- **`ShellChild` is internal, for the same reason `HostPipeDrain` is (2026-09-09, second fix wave).**
  Both orderings above live between four things sharing one serial queue — the exit, the budget, the
  escalation and the last drain — and through `HostShellRunner.run` the windows that separate them
  are tens of microseconds wide. Driven directly, a test chooses when `finish` is called and how long
  the grace is, so the ordering becomes the arrangement rather than a race the machine wins or loses;
  each arm asserts that its arrangement held (`timedOut` false, `outputLimited` true) before it
  asserts what the arrangement was written to catch. The grace is per instance for that reason and no
  other; the budget and the cap stay where they were.
- **The run handle is registered before the ownership question, not after its answer (2026-09-09,
  second fix wave, scalpel-4#4).** The view launches the send from a `Task` it does not retain, and
  the first suspension point in a `!` is `state(of:)`. A handle registered after that answer leaves
  the whole await with nothing for `stop()` to cancel, and the far side of it spawns a shell for a
  composer that is already released and posts through the lifecycle it has left. The question now
  runs *inside* the registered task, which re-reads its own cancellation before it spawns: a run
  released before it spawned starts nothing, explains nothing and posts nothing — the same silence a
  cancelled run already answers with, and for the same reason.
- **X5 gains `fork(at:on:)`, and the fork's prefill belongs to the fork** (2026-09-08, fix wave,
  scalpel-2#8). `perform(.fork(at:))` answers the *source's* state and names the sibling nowhere,
  so the fallback wrote the edited message into the composer of the conversation the user was
  editing away from. `LifecycleAPI` gains `fork(at:on:) -> ChannelKey` in `sendPrompt`'s pattern —
  same preconditions, same refusals, a value instead of the state — and `perform(.fork)` stays for

- **The fork point is the preceding assistant's last record, not its item key** (2026-09-08, fix
  wave, scalpel-2#7). `ItemBuilder` merges an assistant message's records into one item keyed by the
  first of them; `entryUUID` is the last record the fork keeps, inclusive, so the item key cut the

- **A prefill is written only over the words the edit began with** (2026-09-08, fix wave,
  scalpel-2#6). The rewind is one await and the field stays live across it. Keeping the user's own
  typing and saying why the edited message did not come back is smaller than disabling the field,
  and it never discards input the user can see. Filed: tracker 199, the way back to the dropped
  prefill.
- **Sent attachments leave the tray by identity** (2026-09-08, fix wave, scalpel-2#4). The tray is
  live across the send's await, so "drop the first N" deleted whatever was in front of it — an image
  attached and not sent — while the one that travelled stayed.
- **A drop is a path as often as it is bytes** (2026-09-08, fix wave, scalpel-2#14). Finder offers a
  file URL and nothing else, so the intake resolves it and reads the file under a source bound of
  64 MiB; the 8 MiB cap still applies to what travels, after conversion. The source needs its own
  bound because a decoder's input is not its output.
- **An input method's Return is not the composer's** (2026-09-08, fix wave, sweep#15). With marked
  text the keystroke goes to AppKit's input context untouched. The product's first users type
  Korean, where a field that read the key code first would submit an unfinished word on every
  phrase.

- **No copy of X10's table.** Including the sentence this leaf believes is wrong: it is filed,
  not forked.
- **2026-09-08 — the channel switch is answered where the key is, not by a view identity.** The
  channel subtree keeps its SwiftUI identity across a selection change, so a composer that
  subscribed in `onAppear` and a header that adopted there were both wrong for a switch between two
  channels of the same mode. Keying the subtree with `.id(row.key)` would also have fixed it, and
  was rejected twice over: it tears down and rebuilds the list on every switch, and no test in this
  tree can see a view's identity — the mounts are asserted by opening bodies. So each mount resolves
  its channel's model as part of drawing it, `start()` and `adopt(row:)` being idempotent, which is
  both the behaviour and the thing a test can fail on.
- **2026-09-08 — quitting re-reads the owned set instead of raising a spawn barrier.** The census is
  one suspended read and is not atomic with the terminations that follow it. Rather than lock the
  lifecycle at the moment the app is stopping, the clause repeats the census after each termination
  pass and terminates whatever now has a process, bounded to three passes; each channel is
  terminated once, so "exactly one `.quit` per owned channel with a process" still holds. What lands
  after the last census is ended by the exit closing its pipe (tracker 196).
- **2026-09-08 — the in-flight quit lives on the delegate.** Production `makeGuard` answers a fresh
  `QuitGuard` per request, because a guard captured before `bindWorkspace` would hold no fleet, so
  the guard's own flag can never coalesce two requests. The delegate is the only thing both share,
  and a second request while one is deciding is deferred on the first one's answer.
- **2026-09-08 — a cancelled prompt is retired from the fold across the seam.** `HostSignal` gains
  `promptCancelled(uuid:)`, applied by `WireReducer` by dropping the uuid from `outstandingPrompts`,
  and the queue chip raises it only on `{cancelled: true}`. `false` means the message was not in the
  queue — it may already be running — so its prompt is still owed a turn and nothing is retired.
- **2026-09-08, the fix wave: a restart is judged by the epoch its answer carries, and a queued
  one is reported rather than waited for.** `perform(.quiescentRestart)` answers as soon as the
  change is recorded — a busy channel keeps it for the dormant timer, and a change asked for
  while a restart runs merges into that pending one — so "it did not throw" was never a claim
  that the process had been replaced. The surface now compares the answered `ChannelState`
  against the one the channel was running: a new epoch with nothing pending is a restart that
  ran, and anything else re-opens the field and says the change is pending. Rejected: waiting on
  `LifecycleAPI.updates`, which is one stream with one consumer (the sidebar) and cannot be
  joined by a second; and blocking on the channel's next handshake, which for a queued change may
  be minutes away and would hold the field shut for all of it. What that leaves undone — nobody
  resumes the readback when the timer eventually runs the change — is tracker 205.
- **2026-09-08: every path to a setting the pickers own goes through the picker.** A routed
  `/model`, `/effort` or `/permissions <mode>` is dispatched into `SettingPickersModel`'s own
  click path rather than sent from the router. §8.6 binds the bypass mode to the disclaimer,
  the acceptance write and the prerequisite restart whichever surface asked for it, and §7.4
  binds the other two to a readback; two call sites for one setting would have been two chances
  to forget. The router still decides *what* the line means — the picker matches on the subtype
  and payload C4 built and re-parses nothing (X10).
- **2026-09-08, the second fix wave: §7.4's gate is one state machine, and one method opens the
  field.** Six of the round's findings were holes in the same machine, so the states were written
  down before any of them was patched:

  | state | field | what holds it |
  | --- | --- | --- |
  | *open* | editable | nothing |
  | *restarting* | closed | `restartsInFlight > 0` — a process is being replaced |
  | *queued* | whatever the rest of the machine says | the change was recorded for the dormant timer |
  | *owed* | closed | `awaitedRestart` — a replacement exists and has not reported |
  | *outstanding* | closed | `restartFailures`, or a setting the **fleet** still names |

  `beginRestart` opens an operation and `confirmReadback`, `noteQueuedRestart`, `cancelRestart` and
  `restartFailed` each close one; `releaseOrHold` is the only place `surface.isDisabled` goes back
  to false, and it consults all four holders. The count is what makes a second change merging into a
  running restart harmless — it answers exactly like a queued one and must not release the first's
  gate. `restartFailed` reads the channel: `quiescentRestart` spawns the replacement *before* it
  restores and re-reads the flag settings, so an error can arrive with a new process connecting, and
  cancelling there would let a send into its queued input with no readiness transition to flush it.
  An unread readback is *owed* rather than forgotten — the snapshot is retained and the next
  handshake re-runs the comparison — because clearing the outstanding list left nothing for a
  recovered readback to confirm against and nothing for a pick to act on.
- **2026-09-08, the second fix wave: the mode readback is asked of the fleet, not of the
  subscription.** The mode's only readback is a handshake, and this model's copy arrives through the
  composer's `events(of:)` loop while the confirmation runs the moment `perform` returns. The
  comparison now reads X5's `engineReports(of:)` — the handshake the fleet has **retained** for the
  channel, which after a replaced epoch is the replacement's — and holds the gate when the fleet has
  none to report, rather than releasing on a match with the old process's mode. The epoch check
  stays where it was, in `replacedTheProcess` at the caller, which is what establishes that the
  retained handshake is the new one. This closes tracker 208.
- **2026-09-08, the second fix wave: the surface answers the fleet's banner rather than asking the
  user to pick twice.** The fleet resolves its unresolved settings strictly in order, so a
  correction made out of that order applies the value and leaves the fleet's list where it was;
  resolving the head afterwards advances the fleet's banner onto a setting the user has already
  answered, with nothing of the surface's own left to hold the field. The release therefore consults
  the channel's banner, and each setting the fleet still names that has already been corrected here
  is re-answered with the value **the engine now reports** — never a click — bounded by the three
  settings this model owns. Rejected: opening the field and trusting the fleet's own connecting
  glyph to explain it, which is the defect; and holding the field until the user picks the same
  setting a second time, which is correct but makes the banner's promise false.
- **2026-09-08, the second fix wave: one bypass acceptance at a time.** §8.6 writes the acceptance
  *first*, so a second selection arriving across the restart finds it recorded and takes the "later
  selection" arm — the mode alone — to a process the prerequisite restart has not replaced. Moving
  the store write after the restart was rejected: the order is the gate's whole content and a
  restart that ran with an unrecorded acceptance is a launch flag the next spawn would not carry.
  The second selection is refused while one acceptance is in flight instead, and told so.
- **2026-09-08, the second fix wave: the pickers read the engine as part of being drawn.** The same
  answer the composer's mount already gives, for the same reason: the header's slot keeps its

- **2026-09-08, the second fix wave: a slash rewind writes its prefill on *Edit*'s terms.** The

  unchanged since the command was issued; otherwise the typing is kept and `typedAheadNote` — the

## Surprises & Discoveries

- **`apply_flag_settings` answers success with no `response` key at all.** Not an empty object,
  not `null`. Every effort and flag change is therefore two round trips, and a composer written
  to read the answer would display nothing and look broken.
- **The rewind refusal is a *success* envelope.** Recorded in `rewind-turn`, and the two bodies
  are not even the same shape: the refusal lacks `targetMessageUuid`, which the honoured leg
  carries. Reading the envelope is the natural implementation and is wrong.
- **`set_cwd` back to the session's own directory still answers `transcript_relocated: true`.**
  A host cannot read that key as "the transcript moved".
- **`disableBypassPermissionsMode` is a string, not a boolean.** The engine tests it against
  the literal `"disable"` (`:455553`). A host reading it as `Bool` sees `false` for a setting
  that is switched on and offers a mode the binary will refuse.
- **There are two engine refusal sentences, and afleet's pattern matched one.** See finding 1b:
  the one it missed was the one containing the sentence §7.7 forbids. Both are matched since
  `6abd4a0`.
- **A rewind's reach is set by an optional field, not by which process sent the message.** The
  spec read `"stale target"` as a fact about process ownership; it is a later-turn scan whose
  result changes with `last_seen_user_message_uuid`. Supplying the newest user message honours
  targets the recorded fixture shows refused. The obvious wrong value — the target's own uuid —
  fails in the direction that hides itself behind the fallback.
- **`system/init` names its slash commands without a leading slash** while the composer's line
  and the local table always carry one. C4's `slashed(_:)` already normalises it; a surface
  comparing raw strings would silently offer the very commands the engine called terminal-only.

## Outcomes & Retrospective

**Landed.** The composer sends, routes, escapes to the shell, completes files, queues, edits,
suggests and picks; the header acts; the bypass gate holds; and quitting afleet ends what it owns
and nothing else. Ten tasks plus two correctives, each with its tests demonstrated failing first.

**Floor at the tip**, clean build: **1244 executed, 21 skipped, 0 failures** across 14 bundles;
**one** source warning, and it is not this leaf's (see below). `make check-imports` clean;
`make check-wiring` clean at 23 allowlisted, 0 findings. No suite executed zero tests — checked
per-suite declared-against-executed rather than from the summary, because a crashed bundle is
retried and then reports `Executed 0` at exit 0 (tracker 147, found here).

**Gates.** G1, G2, G3, G4, G5 and G7 pass. **G6's prompted half is blocked**, not failed: the
scratch account's organisation has Claude subscription access disabled for Claude Code, so items 2,
8 and 12's turns cannot run. **Zero of four budgeted turns were spent**, and no turn was spent
confirming a diagnosis another leaf had already made with a `result` frame. G6's zero-turn half ran
live and passed, non-vacuously on both sides.

**The fence held.** Four boundary edits, all declared: two mount call sites plus one threaded
parameter in `ChannelColumnView.swift`; the registry's registration and its four provider closures
in `AppModel.swift`; one `applicationShouldTerminate` hook in `AfleetApp.swift`; and one allowlist
line in `check-app-wiring.py`. Nothing else outside `App/Composer/`, `App/Header/`, `AppTests/` and
`docs/`. No commit carries an attribution trailer of any kind.

**What this leaf got wrong and had to correct in place**, which is the part worth keeping:

1. **G2 claimed more than it checked.** Equality against `ShellEnvelope.wrap` was said to prove the
   composer sanitised nothing itself. `neutralize` is idempotent, so sanitising twice is
   byte-identical and passes — three mutations proved it. The gate is narrowed and tracker 150
   records why, so no later reader re-derives the confidence.
2. **The `[parent-impact]` on `promptSent` was right about the gap and wrong about the payoff.** It
   said the missing uuid cost the queue chip its pre-echo preview. It did not: `promptSent` produces
   no `TimelineChange` at all. What it cost was **turn attribution** — every turn afleet reduced was
   `.unprompted` until X5's corrective landed. Corrected in place; tracker 154 leaves the preview as
   a C3 design decision.
3. **The *Quit* escalation was argued for on a false premise.** It claimed the bare terminate yanks
   the pipe under running shells while the escalation ends them quiescently. The engine's
   `end_session` already records `task_updated {status: "killed"}` and `task_notification
   {status: "stopped"}` and writes the trailing `last-prompt`, so the bare form is a recorded
   teardown — and the escalation's failure path exits with **no wedge record**, regressing §6.7. It
   optimised the happy path and left the failure path recording nothing. Withdrawn; X5 gained
   `.quit` and `liveTaskIDs(of:)` (`b86a73a`).
4. **Four gates were thinner than their wording**, found by auditing rather than by a failure: G1's
   row enumeration compared X5 member *names* only, so a cross-wiring inside a family passed; G2
   never asserted the channel's cwd or environment, so a composer using afleet's own would have
   passed every arm; G3's two send arms put no turn in flight and so could not fail; and G4 computed
   its expected fork point with a copy of production's own walk, comparing production against
   itself. All four are fixed and each fix is proved by mutation.

**The recurring lesson, stated once.** Every one of the above is the same failure: an instrument
that measures a proxy for the property, and reads green because the proxy is easy to satisfy. The
practice that caught them was cheap and mechanical — mutate the finished code, one line at a time,
and require the test to fail. Where a mutation *passed*, the test was not discriminating and was
rewritten (this happened three times: an image cap the arms derived from the constant, a guard whose
two flags always move together, and a decline arm that read a call log before a detached write
landed). A test whose failure nobody has witnessed is a claim, not evidence.

**What a human still has to witness by hand**, none of it reachable from XCTest: the quit `NSAlert`
itself — its copy, its button order, and that Cmd+Q with a busy channel raises exactly one;
`NSApplicationDelegateAdaptor` installing the delegate in the real scene, which SwiftUI resolves at
app launch and not in a test bundle; and the `.quit` verb ending a genuinely busy live engine. Plus
everything G6's prompted half would have shown: that an interrupt stops a live turn within two
seconds, and that a real model saw the `<bash-stdout>` envelope and could quote it back.
