## Purpose

The Terminal tab is where afleet stops being a client of Claude Code and becomes a place the
user can stand. Three of the app's hardest transitions end in a pane: a background job's
screen (`claude attach`), the raw-TUI hatch that hands a whole channel to the CLI's own
interactive client (`claude --resume`) and takes it back when the pane exits, and the trust
review that runs `claude` in a directory the engine has never been shown. None of them is
re-implemented; each is a CLI verb in a pty, which is what makes them correct by
construction.

Everything below the pane already exists. C7.1 shipped the pty layer, the `TerminalSurface`
protocol and the GhosttyKit adapter, and proved them against a real `claude attach`. C4
shipped X5's three pane requests and the exit that re-adopts a hatch. C5 shipped the host
that retains a session per (tab, channel) and routes a `PaneRequest` to a registered runner.
What is missing is the thing in the middle: an object that owns a pane's lifetime, maps one
contract onto the other in both directions, and renders.

So this leaf is small in code and load-bearing in seams. It closes the composite's items 15,
17 and 23, unblocks C6's item 47 action, and is the last leaf between the Workbench and
recomposition on the terminal axis.

## Acceptance

The composite's four gates, restated with the evidence each produces. Nothing here weakens
them; where a clause cannot be witnessed headlessly it is named as a human leg rather than
quietly reinterpreted.

### G1 — item 23 in the built app (required)

`pwd` in a Terminal pane prints the channel's cwd; `echo $PATH` matches the login shell's
PATH. The **human** leg is reading those two lines on a screen. The headless half, which is
what a regression would actually trip over, is:

1. A `TerminalPanelTests` case spawning a real child through the panel's own spawn path in a
   temporary directory with a crafted environment, reading `pwd` and `$PATH` back off the pty
   — the same shape as C7.1's G1a, but through `PaneSpawn` and the pane, not through
   `PTYProcess` directly, so the mapping is what is under test.
2. An assertion **by variable name** that the pane's child environment is exactly
   `ResolvedEnvironment.variables` plus C7.1's TERM overlay and nothing of the test process's
   own — names and set difference, never a dumped environment (§6.3, X11).
3. An assertion that the shell pane's cwd is `ChannelContext.cwd` and that a `PaneRequest`'s
   pane uses `request.cwd`, which is not always the same directory (a job's pane uses the
   job's cwd, §9.5).

### G2 — item 15's attach half and item 17 end to end with C4 (required)

Item 15: the Background section's *Attach* shows the job's screen in a pane and the detach
key returns. Item 17: *Open in terminal* releases the channel, the pane shows the interactive
prompt for the same session, the composer is disabled, and closing the pane makes the channel
owned again with the composer working.

Evidence, in three layers:

1. **Headless, with a lifecycle double.** The exit of an X5-originated pane reaches
   `LifecycleAPI.paneExited` with the request **echoed unchanged, `id` included**, and with
   `PTYTermination.paneExitCode`'s value; a pane the panel created itself reports nothing. A
   mutation that mints a fresh `id` fails the test, which is the only way this assertion can
   fail at all — C4 discards an exit whose id it is not waiting on, silently.
2. **Live, under the scratch config home, zero model turns** (`AFLEET_LIVE_CLI=1`,
   `CLAUDE_CONFIG_DIR=/tmp/afleet-fixtures/config-home`, through `make live`): a promptless
   `claude --bg --resume` job is started, `LifecycleAPI.attach` is asked for its request, the
   pane runs it, the pane's grid carries the client's own output, Ctrl+Z is written to the
   pane's ingress, the pane observes the exit, and the exit reaches the lifecycle. C7.1's S1
   proved the pty half of exactly this four times; what is new here is that it runs through
   the panel and reaches C4.
3. **Human.** The composer disabled while the hatch pane runs and enabled again after it
   exits, and the rendered attach screen, are read on a screen. The channel's return to
   *owned* is C4's and is asserted headlessly through the double.

### G3 — pane requests, exits and closes (required)

1. A `PaneRequest` with `purpose: .command` — item 47's terminal step, the shape C6 will emit
   — runs in a pane whose child's cwd is `request.cwd` and not the channel's, asserted by
   reading the child's own `pwd`.
2. A pane whose process exits shows the exit — the code or the signal, named — and offers
   *Restart pane* exactly where restarting is the panel's to do (Design §6).
3. Closing a pane whose process is alive asks first, and the hatch's question names what is
   waiting on it. Confirming terminates afleet's own child and reports the exit; declining
   leaves the pane. §7.8's never-kill rule is not in tension with this: no pane ever holds a
   session running in the user's own terminal, and a test pins that the only process a pane
   can signal is one it spawned itself.

### G4 — panes are per channel, and the tab pops out (required)

1. Two channels, each with panes, switched between: each channel's panes and their live
   children survive the switch, and neither channel sees the other's. The evidence is the
   host's retained `PanelTabSession` plus a live child still answering after the switch.
2. Pane count and cwd overrides persist under W6's key
   `panel.terminal.<configHomeHash>.<sessionId>` in the `workbench` namespace and restore on
   relaunch; an X5-originated pane is deliberately **not** restored (Design §7).
3. The tab pops out and keeps its channel; the pane's view is claimed by exactly one window at
   a time and the other window says so rather than blanking (Design §8). The pop-out itself is
   C5's machinery; what this leaf owns is that a pane survives it.

## Design

### 1. What this leaf is made of

Five types in `Workbench/Sources/TerminalPanel/`, and nothing in the app but glue.

```
TerminalPanelTab        PanelTab, id .terminal. Makes a session per channel, makes the view.
TerminalPanelSession    PanelTabSession. The channel's panes, the selection, the store
                        document, the restore. The host retains it; this is where a pane's
                        life is anchored, never in SwiftUI @State.
TerminalPane            One pane: a GhosttyTerminalSurface, a PTYProcess, the request it
                        echoes (or none), a state machine, the read loop.
PaneSpawn               The two mappings, as free functions: PaneRequest -> PTYSpawnRequest,
                        and (request, PTYTermination, Date) -> PaneExit.
TerminalPaneRunner      PaneRunning. Receives an X5 request, resolves the channel, hands it
                        to that channel's session.
```

`TerminalPaneView` and `PaneSurfaceView` (an `NSViewRepresentable`) render them. The app
registers the tab and the runner in `AppModel`, wires the sidebar's *Attach* and a new
*Logs*, and declares Cmd+Shift+T.

### 2. The pane's state machine

```
.starting → .running(pid)  → .exited(PTYTermination)
                           ↘ .stopped(signal)          (only under .report; see below)
          ↘ .failed(SpawnFailure)
```

`.stopped` is reachable only for panes spawned with `stopPolicy: .report` — every pane except
an attach pane. It is rendered as *Suspended*, with *Continue* (`SIGCONT` to the child's
group) and *Close pane*, because a user who typed Ctrl+Z into their own shell suspended a job
on purpose and a panel that answered with `SIGHUP` would be destroying their work. An attach
pane takes `.detach`, so a stopped attach client is answered by the pty layer with `SIGCONT`
then `SIGHUP` and the pane sees only the single `.ended` — which is C7.1's rule, and which S1
observed never to be needed because the client exits.

`.failed` exists because §10 is binding: "PTY failures: panel-local error states that never
take the channel down." A spawn that throws is a pane that shows why, not a thrown error that
reaches the channel. **An X5-originated request whose spawn fails is still reported as a
`PaneExit`**, with `code` 127 — the shell convention for "could not execute" — because C4 is
waiting on that id and a hatch whose pane never started would otherwise leave the channel
released for ever. This is the one place the panel synthesises a code rather than observing
one, and it is stated here because it is a deliberate departure from "the code the child
exited with".

### 3. The two mappings (`PaneSpawn`)

`PaneRequest → PTYSpawnRequest`: executable, arguments, cwd and environment pass through
unchanged; `size` is the surface's current grid; `terminal` is
`surface.terminalDescription`; `stopPolicy` is `.detach` for `.attach` and `.report` for
every other purpose, exactly as C7.1's hand-off says. Nothing else is touched — in particular
the environment is **not** merged with anything, because C4 composed it through
`LaunchConfiguration.childEnvironment` and X11 says that is the environment.

`PTYTermination → PaneExit`: `PaneExit(request: theRequestAsGiven, code:
termination.paneExitCode, observedAt: Date())`. `request` is the value the runner was handed,
stored and echoed; the panel constructs no `PaneRequest` of its own for an X5-originated pane
and edits no field of one. That `PaneExit` cannot tell `.signalled(7)` from `.exited(135)` is
C7.1's recorded observation and is accepted: X5's re-adoption keys on the event, not the
number.

### 4. The read loop, and back-pressure

S1's shape, promoted verbatim, because it is the only shape that has been measured: one task
per pane consuming `pty.events`, feeding the surface, then `await surface.awaitFeedCapacity()`
before pulling the next event; `onInput` and `onResize` going straight to `sendInput` /
`sendResize` with no `Task` per callback, since a task per callback delivers `ba` for `ab`
(C7.1, measured 3 of 3).

Two things S1 did not have to solve and a pane does:

- **The loop has a lifetime.** A pane closed, a session evicted by the host's LRU, or a
  channel removed from the index all end a pane. The loop is a stored `Task` cancelled on
  teardown, and teardown is `pty.teardown()` then cancel then `surface.processDidExit`.
- **The wait must be cancellable.** Tracker 93 says a host suspended in
  `awaitFeedCapacity()` has no way out, and names C7.4 as the owner "when a pane's read loop
  has a lifetime of its own". It now does. The closer is C7.1's own suggestion — resume the
  waiter under `withTaskCancellationHandler`, the way the pty layer's write gate already does
  — and it is a small edit inside `TerminalCore`'s adapter. It is made here rather than filed
  again, because filing it would leave a pane that cannot be closed while a renderer is wedged.
  This is the leaf's one edit outside its own targets in the package, and it is recorded as a
  *Parent revision* so the architect sees it at merge.

### 5. Which channel a pane belongs to — the seam gap

`PaneRunning.run(_ request: PaneRequest) async` receives a request and nothing else. It has
no `ChannelKey`, no `ChannelContext`, and therefore **no `reportPaneExit`** — the exit
reporter lives on `ChannelContext` and on nothing else. A runner that conforms to the shipped
protocol literally cannot discharge the obligation the same protocol's documentation comment
gives it: "Runs the request and reports its exit through the context's `reportPaneExit`."

This is not a preference about where a pane should land. It is a hole in W8's second bullet as
it was written into X7, and it is filed as `[parent-impact]` below with the amendment this
leaf recommends and the fallback it will take if the architect rules otherwise. Everything
else in this document is written against the amended seam; the fallback changes one
initialiser and no behaviour.

### 6. Restart, and what the panel is allowed to spawn

*Restart pane* is offered for panes whose existence is the panel's own: a shell pane, and a
pane from a `.command` request. It is **not** offered for `.hatch`, `.attach` or `.logs`.

The reason is W8, binding: "The Terminal panel never spawns `claude` for a session on its own
initiative." A restarted hatch would re-enter §7.2 rule 5's ownership transition from the
wrong side — by the time the pane exited, C4 had already begun re-adopting the channel, and a
second `claude --resume` would be a foreign holder of a session afleet is spawning into.
Attach and logs change no ownership, but restarting them still means the panel deciding to run
`claude`, and X5 mints a fresh request id per request precisely so that two runs are two
requests. So an exited job pane says where a new one comes from — the Background section's
*Attach* or *Logs* — and offers no button that would spawn one.

`.command` is restartable because a `.command` pane is a plain process the requester asked
for; if it happens to be `claude` (item 47's trust review is exactly that), restarting it is
the user re-running the action, and §6.11's "afleet re-reads the value when the pane exits"
fires again on the same terms. This asymmetry is deliberate and is the residue answer the
architect should read first.

A **shell pane** — the Cmd+Shift+T pane, and the pane a channel opens with — is not an X5
request at all. It runs `ResolvedEnvironment.shell` with `-i`, in `ChannelContext.cwd`, with
`ChannelContext.environment.variables`. `-i` and not `-l`: X11's capture *is* the login
shell's environment, so a login shell would re-source the login files and prepend PATH
entries a second time, breaking item 23's equality; an interactive shell still sources the
user's interactive rc file, which is what makes aliases and the prompt appear.

Because a shell pane is nobody's request, **its exit is not reported through X5**. The panel
reports a `PaneExit` if and only if the pane came from `PaneRunning.run`, echoing the request
it was given. Reporting a shell pane's exit would put a `.staleExit` diagnostic in C4's log
for every closed shell, which is a record of a mistake nobody made.

### 7. What persists (W6)

Key `panel.terminal.<configHomeHash>.<sessionId>` in the `workbench` namespace, where
`<configHomeHash>` is the first 12 hex characters of SHA-256 over `key.configHome.path` —
FleetKit's `ContentHash.sha256Hex`, which `TerminalPanel` can already reach, spelled to match
ClaudeWire's `RawCapture.configHomeHash` so two spellings of one hash never appear. A test
pins the spelling against a literal vector built from an invented path.

The document is `TerminalPanelState {schemaVersion: Int, panes: [PersistedPane {cwd: String?}],
selected: Int?}` — W6's "pane count and cwd overrides", and nothing more. **Only shell panes
are persisted.** A restored `.hatch` pane would be the panel spawning `claude` on its own
initiative at launch; a restored `.attach` or `.logs` pane would run a verb against a job that
may not exist; a restored `.command` pane would re-run a command the user did not ask for
again. So the restore opens N shell panes at their recorded directories, and a channel whose
panes were all X5's restores to one shell pane, which is what a Terminal tab looks like when
you open it.

The read-modify-write hazard W6's 2026-09-09 amendment exists to prevent does not return here:
this key has exactly one writer.

### 8. One pane, one window — the view claim

The host retains one session per (tab, channel) and hands it to **every** renderer of that
pair, which after a pop-out is two: the main window and the popped-out window both draw the
Terminal tab for the same channel. A pane's `NSView` can be in one view hierarchy at a time,
so a naive `NSViewRepresentable` returning the surface's view would move it to whichever
window laid out last and blank the other, silently.

The rule: a pane's surface has one **claim**, held by a claimant token the representable takes
on `makeNSView` and releases on `dismantleNSView`; the most recent claimant wins, and a
renderer without the claim draws a plain statement that this pane is showing in another
window. The pane's process, its read loop and its buffer are untouched by any of this — only
the view moves. The claim is a model-level property, so G4c is asserted without two windows:
two claimants, the second wins, the first reports itself unclaimed.

This is the honest shape rather than the clever one. Rendering one pty into two surfaces would
mean two grids diverging on the first resize, and refusing to pop the tab out would contradict
X7.

### 9. The app-side glue

Five files under `App/`, and `project.yml`. Each is small and each is required by a gate:

- `App/Composition/AppModel.swift`: register `TerminalPanelTab` and its pane runner beside

- `App/Views/SidebarView.swift` and `App/Fleet/FleetBrowserModel.swift`: *Attach* runs the
  request through `panels.run(_:)` instead of parking it in `ShellModel.pendingPane`, and a

  yet.
- `App/AfleetApp.swift`: Cmd+Shift+T as a menu item, which is where §8.7 puts it and where C5
  left it. It resolves the focused channel's context from the host, selects `.terminal`, and

- `project.yml`: `Workbench/TerminalPanelTests` in the scheme's test targets, so `make test`

Nothing else under `App/` is touched, and the fence is stated in the plan so a worker cannot
drift into C5's or C6's files.

### 10. What is deliberately not done

- **No W2 amendment.** Tracker 94 records that back-pressure lives on the concrete adapter;
  C7.4 holds the concrete type, so `TerminalPane` types its surface as
  `GhosttyTerminalSurface` and the question does not arise. Widening a binding protocol on a
  hypothesis is what the entry exists to prevent.
- **No paste-confirmation UI.** C7.1 handed the *policy* over with the adapter's default
  (user paste allowed, OSC 52 denied) and left any confirmation UI to this leaf. It is not a
  gate, it is not in §9.3, and it is filed as tech debt rather than invented here.
- **No split panes.** The composite defers "split panes and pane layouts beyond a stack".
  Panes are a stack with a pane bar.
- **No search, no scrollback export, no per-pane theme.** Appearance follows the system;
  `themeResolution` is read once into the pane's diagnostics so a future setting has a place
  to fail loudly.
- **No *Respawn* in the sidebar.** §17 C7's purpose lists it beside *Attach*, *Stop* and
  *Logs*, but it is an X5 job verb with no pty and therefore C5's row, not a pane. Recorded as
  an observation for the architect rather than taken.

## `[parent-impact]` — `PaneRunning` cannot report a pane exit

**The contradiction.** W8 (binding) says the panel "runs it and reports `PaneExit {request,
code, observedAt}` back through X5". X7 as shipped puts the reporter on `ChannelContext`
(`reportPaneExit`) and gives `PaneRunning.run(_ request: PaneRequest) async` no context, no
channel key and no reporter. `PanelHostModel.run(_:)` resolves the runner by tab id alone.
`PaneRunning`'s own documentation comment names the obligation — "reports its exit through the
context's `reportPaneExit`" — that its signature makes unreachable.

The same hole decides where a pane lands. A hatch for channel X must open in channel X's
Terminal session; the request names a cwd and a purpose, not a channel, and for `.attach`,
`.logs`, `.command` and `.shell` there is no channel recoverable from the request at all. A
pane placed in the wrong channel's session is not a cosmetic error: X5 released channel X and
is waiting on that pane's exit.

**Recommended amendment**, in C5's fence, three lines of signature and one of resolution:

```swift
// PanelHostAPI/PaneRunning.swift
public protocol PaneRunning: Sendable {
    func run(_ request: PaneRequest, in context: ChannelContext) async
}

// PanelHostAPI/PanelHost.swift — PanelHostError
case noChannelContext            // added

// App/Panels/PanelHostModel.swift — run(_:)
// resolve the focused channel's context; throw .noChannelContext when there is none;
// then select(tab) and await runner.run(request, in: context)
```

`PanelHostModel` already holds `selectedChannel` and `context(for:)`, so the resolution is two
lines. `ChannelHeaderActionsModel` already renders `PanelHostError` as an inline note and
gains a sentence for the new case. `make check-x7` and C5's spec §7 text are updated in the
same change, which is what that check exists for.

**Why not the alternatives.** Passing a `ChannelKey` instead of the context would still leave
the runner with no reporter and no cwd, and would make the panel ask the host for a context it
was about to be handed. Injecting a `() -> ChannelContext?` closure into the runner from the
app keeps X7 unchanged but moves the channel decision into an untyped closure with no test
that can see it, and leaves `PaneRunning`'s comment still describing something its signature
forbids.

**Fallback if the architect declines.** The closure injection above, entirely inside this
leaf's App glue and the `TerminalPaneRunner` initialiser, recorded as a Decision with this
section as the reason. No other part of this design changes.

## Decision Log

- Decision: A shell pane runs `$SHELL -i`, not `-l`, and its exit is not reported through X5.
  Rationale: X11's capture is already the login shell's environment, so `-l` would re-source
  the login files and break item 23's PATH equality; and a pane nobody requested has no
  request to echo, so reporting it would file a `.staleExit` diagnostic per closed shell.
  Rejected: `-l` (double capture); reporting every pane exit (a log of mistakes nobody made).
  Date/Author: 2026-09-09 / C7.4.

- Decision: *Restart pane* is offered for `.shell` and `.command` panes only.
  Rationale: W8 is binding — the panel never spawns `claude` for a session on its own
  initiative — and a restarted hatch would re-enter §7.2 rule 5's transition from the wrong
  side while C4 is already re-adopting. Attach and logs change no ownership but still mean the
  panel deciding to run `claude`; X5 mints a fresh id per request for exactly that reason.
  Rejected: restart everything; restart nothing (G3 requires the button where it is honest).
  Date/Author: 2026-09-09 / C7.4.

- Decision: A failed spawn of an X5-originated request is reported as `PaneExit` with code 127.
  Rationale: C4 is waiting on that id; a hatch whose pane never started would otherwise leave
  the channel released for ever, and §10 forbids the failure reaching the channel as an error.
  127 is the shell convention for "could not execute". Rejected: reporting nothing (a stuck
  channel); throwing (the channel takes the panel's failure).
  Date/Author: 2026-09-09 / C7.4.

- Decision: A pane's view is claimed by one window at a time; the loser renders a statement.
  Rationale: an `NSView` lives in one hierarchy, and the host hands one session to both the
  main window and a pop-out. Two surfaces over one pty diverge on the first resize; refusing
  the pop-out contradicts X7. Rejected: two surfaces; refusing to pop out; letting the last
  layout win silently.
  Date/Author: 2026-09-09 / C7.4.

- Decision: Only shell panes are persisted and restored.
  Rationale: restoring an X5-originated pane at launch is the panel spawning `claude` on its
  own initiative, against W8, and a restored job pane names a job that may be gone. W6 asks
  for pane count and cwd overrides, which is exactly what a shell pane is.
  Rejected: persisting the purpose and re-running it; persisting nothing (G4b asks for the
  restore).
  Date/Author: 2026-09-09 / C7.4.

- Decision: Cmd+Shift+T is a menu item in `AfleetApp.shellCommands`, driving
  `PanelHost.session(for:context:)`.
  Rationale: §8.7 lists it with the app's shortcuts and C5 left it unclaimed there by name; a
  shortcut declared inside the panel view would work only while the Terminal tab is already
  showing, which is not what a user pressing it from the Thread tab means. The host already
  vends the session, so no protocol grows a member.
  Rejected: a hidden button inside the tab view; a new `PanelHost` member.
  Date/Author: 2026-09-09 / C7.4.

- Decision: `TerminalPane` holds `GhosttyTerminalSurface` concretely, not `any TerminalSurface`.
  Rationale: tracker 94 already ruled that back-pressure lives on the concrete adapter because
  C7.4 holds the concrete type; the pane needs `awaitFeedCapacity()` on every read, so an
  existential would force the W2 amendment the entry exists to avoid.
  Rejected: `any TerminalSurface` plus a W2 amendment.
  Date/Author: 2026-09-09 / C7.4.
