## Purpose

At the pin, afleet is four Swift packages and a test suite. Nothing on this machine can be
launched and looked at. Everything the investigation established about the engine — that a
transcript can be read without owning the session, that a terminal's session can be watched
without being touched, that a fleet of sessions is a thing a person could browse — is true
only in tests.

C5 makes it a window. After C5 the user double-clicks an application, and every Claude Code
session on their machine is a row in a sidebar, grouped by project, marked with where it
lives: afleet's own, one running in their terminal, a background job, or a past transcript.
Clicking one shows what happened in it. A permission prompt waiting in any session appears
in one Activity list at the top of the sidebar and can be answered from there. A prompt that
arrives while the app is in the background raises a macOS notification carrying the engine's
own words. Cmd+K jumps to any session by name. Settings says which config home is in play,
which engine binary, which version, and what the environment resolved to — the four facts
that explain every surprise the app can produce. None of this requires the conversation
surface, which is C6's, so C5 ships the fleet browser and leaves a deliberately plain list
of item kinds where the conversation will go.

C5 also builds the two things the remaining children stand on. The first is the project
itself: an XcodeGen `project.yml`, an `Afleet` application target, a scheme, and a build
that runs from the command line, because until C5 there is no way to compile a line of UI.
The second is the **panel tab host** of contract X7 — the protocol by which C6 plugs in the
Thread and Agents tabs and C7 plugs in Files, Source Control, Terminal, Browser and GitHub.
Four of C7's seven leaves are blocked on it, and C6 is blocked on the whole shell. C5 is the
gate the rest of v1 comes through.

## Acceptance

The parent's four gates restated as behaviour a person or a test can observe, each with the
target that proves it. Three rules bind every one of them.

**Discriminating tests (parent §17.7).** A test written to prove a fix is demonstrated
failing against the pre-fix code before the fix is accepted. Where the failure cannot be
executed — a window that cannot open in a headless test runner — the substitute is stated as
such: a trace assertion on the model that would have driven it, plus a manual witness.
Reviewers ask what an assertion would have to *see* in order to fail.

**Nothing is written under a config home (X9).** Not by the app, not by a test. The default
suite builds its own scratch config home under `FileManager.default.temporaryDirectory`,
never the user's and never `/tmp/afleet-fixtures/config-home`. The one live leg (G1e) uses
`/tmp/afleet-fixtures/config-home` and runs a **recursive** before-and-after manifest of it —
relative path, size, mtime and inode for every file at any depth — diffed and then attributed
against a pinned allowlist of the paths a spawned `claude` legitimately writes. C4's G5 used a
top-level-name allowlist; that is not enough, because a defect that truncates `.claude.json`,
edits an existing transcript, or creates a file below an existing `projects/<slug>/` leaves the
top-level names unchanged. A filesystem diff also cannot say *who* wrote, since a legitimate
child is writing to the same tree, so the witness is paired with an app-side proof: every write
the app makes passes through one injectable file-operations seam, and a test asserts that seam
never receives a path under the config home while having received a non-zero number of writes
overall.

**Reports emit counts (parent §6.3, §11).** Every gate report, test failure message and
diagnostic in this child states counts, sizes, durations and identifiers — never a path, a
title, a session id or a slug from the author's home.

### G1 — it builds, and it lists the fleet (required)

**G1a — the build.** From a clean checkout of this branch:

```
xcodegen generate
xcodebuild -scheme afleet -configuration Debug build
```

prints `** BUILD SUCCEEDED **`. "Clean checkout" means a fresh `git clone` into a temporary
directory with no `DerivedData`, no `.build` and no generated `Afleet.xcodeproj`; the
generated project is not committed. This clause is also **every checkpoint's floor**: no
task in this child is complete while it fails.

**G1b — the suite.** `xcodebuild test -scheme afleet` runs the `AfleetTests` bundle *and*
the four packages' test targets in one invocation and reports zero failures. The scheme
names the package test targets explicitly (XcodeGen's `- package: <Package>/<TestTarget>`
form), so item 36's "`xcodebuild test -scheme afleet` passes" is one command rather than
five. `make test` is the same thing plus `make test-tools`.

**G1c — the listing, headless (default suite).** `SidebarModelTests` builds a scratch config
home holding a scripted set of transcripts across several project directories, with scripted
registry, roster and `agents --json` records, and drives `FleetBrowserModel` over a
`LifecycleAPI` double. Asserted: the set of listed channels equals the expected set;
`ListingPolicy`'s exclusions (a sidechain, a `continuedIn` transcript) are absent and each
absence names the rule that decided it; a teammate transcript is listed read-only; an
`entrypoint: sdk-cli` transcript — afleet's own, which the engine's own picker hides — is
listed; each row's origin glyph matches its `ChannelState.origin`; and the project sections
group by cwd with worktree sub-grouping. The set comparison is two-directional, so an extra
row fails as loudly as a missing one.

**G1d — first paint, opt-in measurement.** `LocalFleetPaintTests`, skipped unless
`AFLEET_LOCAL_INDEX=1`, reads the config home the environment resolves (read-only,
`O_NOFOLLOW`, no persisted snapshot) and measures the time from composition-root start to a
populated `FleetBrowserModel`, five runs, median under **five seconds**. It reports counts,
sizes and milliseconds only. Tracker entry 21 is the known hazard: the 365 ms index build C3
measured is warm steady state, and a genuinely cold page cache adds the read of some 380 MB
of heads and tails. The mitigation is in the design below (a persisted snapshot painted
first); this gate measures both the no-snapshot and the with-snapshot path and reports both
numbers.

*(Refined at Task 9, from a protocol fact measured there: an unprompted `claude` writes its registry
record and **no transcript**, and afleet lists channels from C3's index over `projects/`. The child is
therefore started as `claude --resume <session>` on a session the scratch home already holds a
transcript for, in that transcript's own directory — still interactive, still never prompted, still
zero turns. Writing a transcript to make a brand-new session listable would be a write under a config
home, which X9 forbids outright. See `## Surprises & Discoveries`.)*

**G1e — a foreign session, live, zero model turns.** `LiveForeignChannelTests`, skipped
unless `AFLEET_LIVE_CLI=1`, with `CLAUDE_CONFIG_DIR=/tmp/afleet-fixtures/config-home`: the
test starts an interactive `claude` as a child in a directory the scratch `.claude.json`
**already trusts**, read from that file the way C4's `LiveFleetTests.trustedDirectory(_:)` does
— entries under `/private/tmp/afleet-fixtures/` with `hasTrustDialogAccepted == true`, the
config home itself and anything beneath it excluded by code, the directory recreated if it is
gone and **trust never written**. A fresh temporary directory would be wrong: an interactive
session in a directory the home has never trusted sits on the workspace-trust dialog before it
writes any registry record, so the gate would fail or flake on the engine doing exactly what it
is designed to do — the same shape as the un-onboarded home sitting on the theme picker. The
test sends the child **no prompt**, and asserts that within five seconds the model lists that session with
origin `.foreignLive` and a presence read from its registry record; that afleet never
signals, stops or adopts it (a trace assertion that no termination path was entered, since
executing the break would kill the process the invariant protects); and that the scratch
config home's recursive manifest diff after the run contains **zero unattributed changes**:
every changed path matches the pinned allowlist of paths a spawned `claude` writes and is
attributed to the child the test started. The diff is not required to be empty — an unprompted
interactive session legitimately writes its registry record, and demanding emptiness would fail
the gate on the engine doing exactly what the scenario needs it to do. Emptiness is required
only of the app-write seam, which must receive no config-home path at all. The **manual witness
for item 14's UI half** is the same scenario driven from Terminal.app against the built app,
recorded as a count and an elapsed time.

### G2 — Activity, badges and notifications (required)

**G2a — Activity rows and answering (item 21).** `ActivityModelTests` replays `fake-claude`
against two scripted channels that each reach a `can_use_tool` decision, plus the
`rate-limited-turn` fixture and an `auth_status` frame. **The rate-limit row is driven by the
fixture's own `rate_limit_event`, never by a turn completing.** The installed 2.1.263 no
longer emits a per-turn event in the recorded scenarios (tracker entry 49, filed from the
2026-09-06 drift ritual), so a model that inferred a row from "a turn ended" would show rows
against a live engine that the fixtures never justified, and would show none where the engine
is quiet. The event is occasional; the row and the channel banner both live until the next
event replaces them, which is §7.6's rule. Asserted: Activity shows exactly
**six** rows with the expected `ActivityRow.Kind` values — two `.decision`, one
`.rateLimitRefused`, two `.failedResult` and one `.authProblem` — compared as a multiset in
both directions. Auth is in the set because the parent's §7.6 lists auth state among what
Activity queries and a gate without it would let an auth failure stay invisible.
*(Corrected at Task 6 from an earlier draft of this clause, which said four rows and typed the
rate-limit row `.rateLimitInfo`. Both were wrong against the corpus: `rate-limited-turn`'s
`rate_limit_event` carries `rate_limit_info.status: "rejected"`, so the row is a refusal, and
both of its `result` frames carry `is_error: true` beside `subtype: "success"`, so the turn
that looks successful contributes two failed-result rows. Verified against the fixture's own
bytes; see the Surprises entry on reading the field that carries the fact rather than the one
that names the envelope. `.rateLimitInfo` is asserted separately, where the corpus genuinely
produces it.)*
The `auth_status` frame carries an error, and a **second, healthy `auth_status` removes the
row**, which is the direction `ActivityQuery` already implements
(`FleetKit/Sources/FleetSessions/Activity/ActivityQuery.swift:123` appends and `:127` removes)
and which a one-directional test would not catch. **Answering the permission row from
Activity emits the control response** — the assertion is on the frame that left the host and
on the answering channel's `pendingDecisions` becoming empty, not on the row disappearing,
because a row can disappear for the wrong reason.

**G2b — badges (item 22).** A channel not in view with a pending decision carries a red
count badge and an unread dot; selecting the channel clears both, and the cursor survives a
model rebuild because it is persisted. Asserted over the model with a scripted clock.

**G2c — notifications (items 22 and 53).** The app posts through a `NotificationPosting`
seam. Asserted headlessly against a recording double: a pending decision in a channel not in
view posts one notification and the same decision in the selected channel posts none; the
`notification-hook` fixture's `hook_callback` for `afleet.notification` posts a notification
carrying the hook input's own `message` and `notification_type` **and** is answered with an
empty continue, so the engine is never left waiting. The **manual witness** is the built app
in the background raising a real macOS notification with the engine's text.

### G3 — the screens (required)

**G3a — the upgrade screen (item 33).** With the Developer binary override pointed at a
`fake-claude` that reports `2.1.200`, the app shows the upgrade screen naming the installed
version and the required baseline, and **opens no channel**: the assertion is that the route

**G3b — Settings (item 48).** With `CLAUDE_CONFIG_DIR` pointing at a scratch home holding

listed come from it and none from `~/.claude`, and the readouts named in §6.5 are present:

It also shows the count of symlinked project directories the index skipped

**G3c — the setup screen.** With no `claude` on the resolved PATH and no override, the app

### G4 — the panel host (required)

**G4a — the protocol and the order.** `PanelHostTests` registers stub tabs for several
`PanelTabID` cases in scrambled registration order and asserts the host presents them in the
canonical order (Thread, Agents, Files, Source Control, Terminal, Browser, GitHub); that
Cmd+1 through Cmd+7 select the Nth *registered and available* tab in that order; that a
second registration of one id is refused; and that a tab reporting itself unavailable for a
channel is absent for that channel and present for another.

**G4b — the channel context.** A stub tab reads every member X7 promises and asserts each:
the session id and cwd match the channel, the environment is the one ClaudeWire resolved,
the store handle writes and reads back under the `workbench` namespace **and cannot reach
another namespace**, a `WorkspaceLink` opened through the routing capability reaches the
registered target with the right `LinkDestination`, and the recent-URL feed returns the URLs
`ChannelTimeline.recentURLs(limit:)` returns for the same channel — asserted against a
timeline built from a fixture that contains URLs, so the feed is compared to a non-empty
expected list rather than to two empty ones.

**G4c — pop-out keeps its channel.** A placeholder tab pops out; the popped-out instance's
context resolves to the same channel; switching the main window to a different channel
leaves the popped-out window on its original one. Asserted over the pop-out registry and
context resolution headlessly; the window actually appearing is the manual witness.

**G4d — the pane seam (W8).** A `PaneRequest` handed to the host is delivered to the
registered pane runner **byte-for-byte unchanged, `id` included**, and the runner's
`PaneExit` reaches `LifecycleAPI.paneExited` with that same `id`. Asserted with a recording
lifecycle double; the discriminating clause is the `id`, because two requests with identical
other fields are two requests and C4 discards an exit whose id it is not waiting on.

## Live-cost statement

**C5's budget is zero model turns and zero dollars.**

- G2, G3 and the placeholder timeline are driven entirely by `Fixtures/` and
  `Tools/fake-claude`, which spend nothing.
- G1c and G1d read only. G1d reads the author's real config home, which is permitted —
  X9 forbids *writing* under a config home, not reading one — and is gated behind
  `AFLEET_LOCAL_INDEX=1` exactly as C3's G2 was, never runs in the default suite, and emits
  counts, sizes and timings only.
- G1e starts one real `claude` under the scratch config home
  `/tmp/afleet-fixtures/config-home` and **never prompts it**. An unprompted interactive
  session writes its registry record and ends without a `result` frame, so there is no turn
  and no cost. `AFLEET_LIVE_CLI_TURNS` is not read anywhere in this child; if a scenario ever
  needs a model turn, that is a scope change and goes back to the architect first.
- The scratch home is logged in and onboarded today (verified at the pin: `.claude.json`
  reports `hasCompletedOnboarding: true` and five projects). It lives under `/tmp` and dies
  with every reboot; the recovery step is one interactive `CLAUDE_CONFIG_DIR=/tmp/afleet-fixtures/config-home claude`
  run by hand, because `claude auth login` stores credentials without setting
  `hasCompletedOnboarding` (C4's finding, 2.1.263 `cli.pretty.js:265739-265749`). C5 expects
  this and G1e skips with that named reason rather than failing when the home is gone.

## Design

### 1. Packaging: `project.yml`, the app target and the scheme

`project.yml` at the repository root, generated but never committed
(`Afleet.xcodeproj/` is added to `.gitignore`, which already ignores `.build/`, `.swiftpm/`,
`DerivedData/` and `*.app`).

- **Project** `afleet`, deployment target macOS 26.0, Swift language mode 6 with complete
  strict concurrency on every target, matching the four packages.
- **Packages** `AfleetCore`, `ClaudeWire`, `FleetKit`, `Workbench` by relative path.
- **Target `Afleet`** (`com.apple.product-type.application`), sources under `App/`,
  dependencies on all four package products. It imports `Workbench`, whose umbrella
  `@_exported import`s `PanelHostAPI`, so the host protocol needs no product of its own.
- **Target `AfleetTests`** (unit-test bundle, `TEST_HOST` `Afleet`), sources under
  `AppTests/`.
- **Scheme `afleet`** — the name is the parent's, in G1 and in item 36, and is set as the
  scheme key rather than derived from the target name. Its build action builds `Afleet`; its
  test action lists `AfleetTests` and every package test target by
  `- package: <Package>/<TestTarget>`.
- **Signing**: ad-hoc (`CODE_SIGN_IDENTITY: "-"`, manual style, hardened runtime off, no
  entitlements file, so the app is not sandboxed and can read the user's config home and
  spawn processes under the resolved environment).
- **`Info.plist`** written by XcodeGen from `properties`: bundle identifier
  `com.afleet.app`, display name `afleet`, `LSMinimumSystemVersion 26.0`, no custom icon in
  C5.
- **`Makefile`** gains `generate`, `build`, `test` and `check-imports`. `test` is
  `xcodebuild test -scheme afleet` plus `make test-tools`; the per-package `swift test`
  invocations every earlier child used keep working unchanged.

**Contract X1's check.** The three existing packages each carry an `ImportGraphTests` that
greps their own sources against an allowed set with a floor assertion ("the grep found no
Swift files at all" and "the grep did not find the imports every file has"), so a silently
empty grep cannot pass. C5 adds two of the same shape: one over
`Workbench/Sources/PanelHostAPI` (allowed: Foundation, SwiftUI, AfleetCore, FleetKit and its
sub-modules; **ClaudeWire forbidden**, every panel target forbidden) and one over `App/`
(all four packages and system frameworks allowed). Both run inside `xcodebuild test -scheme
afleet`, which is X1's "CI check in C5 rejects a violating import" — this project runs no CI
service, so the merge gate's own command is the check.

### 2. The composition root

One `@MainActor` `AppModel` owns a state machine over four routes: `.launching`, `.setup`,
`.upgrade`, `.workspace`. Launch, entirely off the main actor except where noted:

1. `EnvironmentResolver().resolve(shell:)` through the login shell (§6.9, X11). Captured
   **once** per launch and handed to everything below, including every panel.
2. `ConfigHome.derive(from:)` — `CLAUDE_CONFIG_DIR` when set, else `<HOME>/.claude`.
3. **The write-root overlap check.** afleet has exactly two write roots,
   `~/Library/Application Support/afleet` for the store and `~/Library/Logs/afleet` for
   diagnostics. `CLAUDE_CONFIG_DIR` is an arbitrary path, so a home of `~/Library/Logs`, or any
   ancestor of either root, would put afleet's own files inside a config home and break X9
   before a child runs. `FileStateStore`'s `configHomes:` guard covers the store only; `Fleet`
   builds `FileDiagnostics` and `FileFleetDiagnostics` itself from the directory it is handed,
   eagerly and unguarded. So the check sits here, ahead of both: canonicalise all three paths,
   and if either write root is the config home or lies beneath it, route to the setup screen
   naming the collision and construct no store, no diagnostics and no `Fleet`.
4. `try FileStateStore(baseDirectory: <~/Library/Application Support/afleet>, configHomes: [configHome.root])`.
   The initialiser is throwing and its `configHomes` argument **is** the X9 guard: it
   canonicalises both paths and throws `StoreError.insideConfigHome` when the store would sit
   under a config home. Passing an empty array to make it compile would delete that
   protection, so the resolved config home is always passed. A throw routes to the setup
   screen naming the store error; a namespace whose document reports `SchemaStatus.newer`
   becomes a banner rather than a crash.
5. `BinaryLocator.locate(in:override:)`, the override read from the `afleet` namespace's
   Developer settings. `nil` → `.setup`, and no `Fleet` is constructed.
6. `VersionGate().check(binary:environment:)`. `.tooOld` → `.upgrade` naming both versions;
   `.unparseable` → `.setup` naming the probe's output; `.accepted` → continue.
7. `TranscriptIndex(configHome:storage: StoreIndexStorage(store:))`. `loadPersisted()`
   first — the sidebar paints from the previous launch's snapshot immediately, marked as
   restoring — then `build()` **in a detached task**, because C3 measured that an index build
   awaited from a main-actor-bound caller runs at about a third of the machine's width.
   `IndexSnapshot` replaces the painted rows when it lands. **The list may be stale; the
   glyphs may not.** A restored row's origin is not drawn from the snapshot: origins come only
   from `ChannelState`, which C4's holder observer seeds at supervisor build and refreshes on
   its five-second poll, so no origin outlives one poll. A restored row with no `ChannelState`
   yet renders without an origin glyph rather than with a remembered one. This is what closes
   tracker entry 21: the entry warns that the measured index cost is warm steady state, and
   the answer is that first paint no longer waits on the index at all.
8. `Fleet(configHome:environment:binary:store:diagnosticsDirectory: ~/Library/Logs/afleet)`
   and `start()`.
9. Registration, through the `WorkspaceCoordinating` seam (§3 below). The composition root
   drives it for the persisted snapshot, for the completed fresh build, and for every
   `IndexDelta` the watcher produces, **before** those rows are exposed as live — a channel
   `Fleet` has never been told about has no supervisor, and `events(of:)` returns nil for a key
   it does not know. A cold launch with no persisted snapshot must not finish with zero
   registered supervisors, which is the failure a warm-path-only wiring would hide.
10. `TranscriptWatcher(configHome:).start()`, its `changes` pumped into
   `index.update(changed:)` — whose `IndexDelta` patches the sidebar — and into
   `StreamIngestion.fileChanged(_:)` for the open channel. A Developer toggle leaves the
   watcher stopped, which is item 56's switch.

### 3. Registration, and the one open scale question

`Fleet.register(_ key:cwd:recent:)` tells the fleet a channel exists, spawns nothing, and
reads the recency later when `perform(.open)` runs. It needs a **real cwd** — C4 is explicit
that a key with no seed runs in the config home and every precondition then refuses it — so
the seed is `IndexEntry.cwd` (already the relocated cwd where one exists), and `recent` is
§8.2's thirty-day rule over `IndexEntry.mtime`. C4's `Fleet.build` seeds a new supervisor
with the observer's current holder snapshot precisely because C5 registers from C3's index
and a pre-existing holder is the ordinary case; that seeding is a detached task, so **the
app drives the sidebar from `updates` and never from a `state(of:)` read taken immediately
after registering.**

The design registers every listed entry. The unknown is cost: the author's config home holds
3,032 transcripts, and registration builds one `ChannelSupervisor` actor and one detached
seeding task each. **Spike S-C5-2** measures registration of the full local set against G1d's
five-second budget before Task 2 commits to it. Its named fallback, pre-authorised so the
spike's failure is not a re-cut: register eagerly only the channels a holder names plus those
recent by §8.2's rule, render the rest from `IndexEntry` alone with origin `.archived` —
which is exactly §7.1's definition of archived, "otherwise" — and register lazily on
selection or on a holder appearing. If the fallback is taken it needs a fleet-wide holder
feed that `LifecycleAPI` does not expose today, which becomes an ask to C4 rather than a
local workaround.

Tracker entry 37 (a fork whose resolved session id is already registered overwrites the
entry instead of refusing; "the resolution belongs with C5") is the collision this
registration model makes reachable. C5's part is to not create it: registration is keyed by
`ChannelKey` from the index's own session ids, which are unique by construction, and a fork
re-key that collides is C4's `Fleet.publish`. C5 adds the case to its own registration tests
and leaves the fix with C4 unless the spike shows the app can provoke it.

### 7. The panel tab host — contract X7, owned

Declared in `Workbench/Sources/PanelHostAPI/`, which may import Foundation, SwiftUI,
AfleetCore and FleetKit and **must not import ClaudeWire** (X1's edge for Workbench).

That last constraint is load-bearing and shapes the protocol. `LifecycleAPI`'s own signature
names `WireEvent`, a ClaudeWire type, so a `ChannelContext` that carried `any LifecycleAPI`
would drag ClaudeWire into Workbench. **The context therefore carries capabilities, not the
lifecycle actor**: narrow, host-provided closures and small protocols for exactly what a
panel may do. This is also the least-authority reading of W8's rule that the Terminal panel
never spawns `claude` on its own initiative — it cannot, because it is never handed anything
that could.

```
PanelTabID          a closed enum: thread, agents, files, sourceControl, terminal, browser,
                    github, in that canonical order, with a default title and system image.
                    Cmd+1…7 select the Nth registered-and-available tab in this order.

ChannelContext      key, session, cwd, environment (X11's single capture), a ScopedStore
                    bound to the workbench namespace, a LinkRouterCapability, a
                    RecentURLFeed, and a `reportPaneExit` capability. A value; the host
                    rebuilds it when the channel changes.

ScopedStore         read/write/remove/keys over one namespace, so a panel cannot reach
                    fleetKit's or afleet's documents.

RecentURLFeed       `current(limit:)` plus an updates stream, backed by
                    ChannelTimeline.recentURLs(limit:) — X4's query, so the Browser never
                    parses timeline items (X1).

LinkRouterCapability
                    register a LinkTarget for a WorkspaceLink predicate; unregister(tab:) to
                    drop every target a tab registered; open(link, from: .currentPanel |
                    .newWindow). The target's handler receives **both the link and the
                    destination**, because C7's W5 is binding and says so.
                    Cmd-click is .newWindow. C5's HostLinkRouter is the single registry in
                    the running app; when C7.2's LinkRouting target lands its reusable
                    registry the host delegates to it, and a second registry never exists.

PanelTabSession     @MainActor, AnyObject: the per-channel runtime state a tab owns — a
                    terminal's PTY and panes, an editor's open buffers and cursors. The host
                    retains one per (tab, channel).

PanelTab            @MainActor: id (an instance property, so `any PanelTab` can read it),
                    title, systemImage, isAvailable(in:), makeSession(for:) called once per
                    channel, and makeView(session:context:).

PanelHost           @MainActor: register(_:), unregister(_:) — async, because it awaits the
                    link-target withdrawal — available(for:) — the
                    registered tabs a channel can show, in canonical order — selected,
                    select(_:), selectIndex(_:), popOut(_:channel:), session(for:context:),
                    view(for:context:), registerPaneRunner(_:for:), run(_ request:
                    PaneRequest). Link opening is **not** a member: it lives on
                    LinkRouterCapability, which the host implements and hands into the
                    context, so a tab holds one routing seam rather than two. The host is
                    still what routes — .newWindow has to pop a tab out before the target
                    can deliver, and a tab cannot pop itself out — but it does so through
                    that conformance. **The canonical spelling of every member is the
                    source**, `Workbench/Sources/PanelHostAPI` — that is what C6 and C7
                    import — and `make check-x7` fails if this document names a member the
                    source does not ship, or omits one it does.

PaneRunning         run(_ request: PaneRequest) async — the Terminal tab's side of W8.
```

**The pane seam.** X5's `openInTerminal(key)`, `attach(job)` and `logs(job)` do the ownership
work and return a `PaneRequest`. The host routes it to the registered pane runner, selecting
or creating the Terminal tab, **unchanged, `id` included**. The runner reports the exit
through the context's `reportPaneExit`, which the host forwards to
`LifecycleAPI.paneExited(_:)` verbatim; C4 accepts an exit only when its `request.id` is the
one it is waiting on, and a late exit from an older pane is discarded. C5 neither invents nor
edits a request.

**Pop-out.** A SwiftUI `WindowGroup` over a `Codable, Hashable` value of tab id plus channel
key. The popped-out scene resolves its `ChannelContext` from the host by key, so the window
keeps the channel it was popped from when the main window moves on. Per-channel panel state —
which tab is selected, and Workbench's own `workbench.panel.<configHomeHash>.<sessionId>`
document — is the host's to key and the panel's to shape.

**One timeline registry for the app.** The recent-URL feed reads the same per-channel
`ChannelTimelineModel` the channel column renders, resolved from a single app-scoped
`ChannelTimelineRegistry` held on `AppModel`. Two registries would each ingest independently and
the Browser would watch a timeline nothing updated, which is the failure the feed exists to
prevent.

**Sessions are retained per tab and per channel; views are not.** C7's acceptance requires
that "panes and open editors are per channel and survive switching away and back". Caching the
`AnyView` *value* would guarantee nothing: SwiftUI owns `@State`, `@StateObject` and
representable coordinators through the rendered hierarchy and tears them down when a subtree
unmounts, so a tab holding its terminal in `@State` loses it whatever the host caches. The
contract is therefore a reference type — the host creates one `PanelTabSession` per
(tab, channel) on first render, retains it, and hands it back to `makeView` every time; a tab
puts its runtime state there. Each (tab, channel) also gets a stable SwiftUI identity so an
unrelated re-render does not discard the subtree.

**The session cache is bounded.** A host that retained a session for every channel a user
browsed would accumulate them across three thousand channels, and one that evicted on the
`.archived` origin would evict almost immediately, because `.archived` is the ordinary origin
of a registered channel with no live process — not a signal that the user is done with it. The
rule is therefore neither: sessions are held in an LRU of **sixteen** channels, with the
currently selected channel and every popped-out channel exempt from eviction, and a channel
removed from the index (an `IndexDelta.removed`) evicted at once. Sixteen is C4's live-process
cap of six plus room for the pop-outs and the recently visited; it is advisory and a measured
reason to change it is a Revision Note.

**Link routing is the host's, not the tab's.** `LinkRouterCapability.open(link, from:)` finds the most
specific registered target, and when the destination is `.newWindow` — which is what Cmd-click
maps to — pops that target's tab out for the current channel *first*, then delivers. A tab
cannot pop itself out, so the routing has to sit where pop-out lives. With no target
registered the fallback is `NSWorkspace.shared.open` for a `.url` and a diagnostic for
everything else, which is C7's W5 rule.

**`makeView` returns `AnyView`** because the host stores a heterogeneous list of tabs and an
`associatedtype Body: View` would make `PanelTab` non-existential. The cost is one type
erasure per tab per channel switch, which is not a hot path.

**Manifest.** C5 adds a `PanelHostAPITests` test target inside its own MARK fence in
`Workbench/Package.swift`, which W1 did not reserve. The fence is respected; the addition is
recorded as a Revision Note on the C7 spec so C7.1, which owns that file, knows the line
exists before its own branch opens.

## `[parent-impact]` — two writers cannot share the one diagnostics log §11 mandates

> **Ruled 2026-09-07 by the architect.** Resolved by the ruling on the second filing below:
> with §11's table amended to one log per event domain, there is **one writer per file**, so the
> interleaving and the rotation-rename races do not arise at all. The only fault left is the
> unlinked-inode one, and it lands as a C2/C4 corrective on `main` — both package sinks open
> `O_WRONLY|O_APPEND|O_CREAT` per write and close, so a deleted log is recreated on the next
> write. No `Fleet.init` signature change and no merged log. C5 does not wait for it. The
> analysis below is kept as filed, including the two corrections it went through, because the
> reasoning is what the corrective is built from.

Filed for the architect, not worked around locally. It blocks no C5 gate and no remaining C5
task; it blocks the first consumer in C6 or C7 that emits a diagnostic.

**The binding clause.** §11's owned-files table — binding under §17.3 — gives afleet exactly one
`~/Library/Logs/afleet/diagnostics.log`. C3 assigned the composition to this child in as many
words: "the app composes both sinks into the one metadata log under `~/Library/Logs/afleet`,
which is C5's to wire."

**Why it cannot be wired.** Three closed diagnostic enums live in three packages that cannot see
each other, so there are necessarily three sinks. Two of them write that file:
`ClaudeWire`'s `FileDiagnostics` (`FileDiagnostics.swift:25-26`) and `FleetSessions`'s
`FileFleetDiagnostics` (`FleetDiagnostics.swift:142-143`). Both do the same thing — open with
`FileHandle(forWritingTo:)`, `seekToEnd()` **once**, then track their own offset. Two instances
on one path therefore overwrite each other rather than interleaving, and each rotation races the
other's offset. `Fleet` constructs its own sink internally from the `diagnosticsDirectory` it is
handed, so the app cannot substitute a shared writer without a signature change.

Nothing writes through the wire and fleet sinks today, so no line has been lost yet.

**A second consequence, found at Task 3's fix wave.** *Delete diagnostics* in Settings unlinks
the log files. The app's own composer renews its three sinks afterwards, so it keeps writing —
but `Fleet`'s two internal sinks are unreachable and go on writing into **unlinked inodes until
the app relaunches**, so the user's next diagnostics are silently lost to a file with no name.
Same root cause: the app cannot reach sinks another package constructed for it.

**Recommendation, revised after the second consequence, and still smaller than the obvious
one.** Both sinks should stop holding a long-lived handle and instead **open the log with
`O_APPEND` for each write** — `open(path, O_WRONLY | O_APPEND | O_CREAT, 0o600)` wrapped in
`FileHandle(fileDescriptor:)`, written, closed. **Per write, not per flush**: `flush()` already
means `synchronize()` in both of these types, and "per flush" would be read literally by whoever
implements it. That single change fixes the two faults that matter: under `O_APPEND` the kernel
places every write at the current end atomically, so two writers interleave and neither needs to
know the other exists; and a sink whose file was unlinked recreates it on the next write instead
of writing into a dead inode, so *Delete diagnostics* needs no cooperation from anyone.
Diagnostics are low-volume metadata, so an open and close per write is not a cost worth
engineering around.

It does **not** fix everything. Losing the shared offset removes the offset race, but two sinks
that each rotate `diagnostics.log` to `diagnostics.log.1` still race each other's rename, and no
change confined to open modes can settle that — the rotation policy has to belong to one owner.
Stated because the earlier draft of this recommendation claimed the rotation race went with the
offset, and it does not.
It is a few lines in each of C2 and C4, changes no signature and breaks no child's API. The
store next door already works at this level (`DarwinStoreFileOperations`), so the idiom is not
foreign to the codebase.

My earlier recommendation — `O_APPEND` on a handle still held open across writes — fixed the
interleaving but **not** the unlink case, because a held handle keeps writing to the inode
whatever happens to the name, and **not** the rotation race either, as the paragraph above now
says. Recorded because the first version looked complete and was not, and because this sentence
went on claiming the rotation race was fixed for one revision after the paragraph above it
stopped claiming so — a document contradicting itself two paragraphs apart, which is how a
reader ends up believing whichever half they read first.

Rejected: changing `Fleet.init` to take the two sinks rather than a directory, which C5's
executor proposed. It works, but it is a public signature change to a merged child's API that
C6 and C7 would inherit, to solve a problem that `O_APPEND` solves without one. Also rejected:
giving each sink its own file, which contradicts §11's table and would need a parent revision
rather than a corrective.

## `[parent-impact]` — §11's owned-files table names one log file; there are four

> **Ruled 2026-09-07 by the architect: accepted as recommended.** §11's table is amended at
> merge to describe the directory — one metadata-only log per event domain (`diagnostics.log`,
> `fleet.log`, `timeline.log`, `app.log`), each rotated by its writer, the 50 MB budget applying
> across the directory, *Delete diagnostics* clearing all four, and the capture tree unchanged.
> C5's composer already flushes, deletes and reopens all four together, and the ruling names that
> uniform treatment as the right shape to keep.

Filed for the architect. It blocks nothing and breaks no rule; the table is simply narrower
than the design it describes, and the table is binding under §17.3, so C5 will not widen it
locally.

§11's owned-files table names exactly two paths under `~/Library/Logs/afleet/`:
`diagnostics.log` and `capture/<configHomeHash>/<session-id>.ndjson`. The directory in fact
holds **four** log files, and each is a consequence of a decision the parent itself made rather
than a liberty C5 took:

| File | Written by | Why it cannot be one of the others |
|---|---|---|
| `diagnostics.log` | ClaudeWire's `FileDiagnostics` | the table's own file |
| `fleet.log` | FleetSessions' `FileFleetDiagnostics` | C4 shipped it; `FleetDiagnosticEvent` is a closed enum in FleetKit |
| `timeline.log` | the app's sink for `TimelineNotice` | C3 declared the notice type and shipped no file sink, and assigned the composition to C5 |
| `app.log` | the app's `AppNotice` | nothing the app observes about its own machinery fits any of the three enums below it |

The cause is the one already recorded in this document's other `[parent-impact]`: three closed
diagnostic enums live in three packages that cannot see each other, so there are necessarily
three sinks, and the app's own notices make a fourth. §11 was written before that followed, and
describes the intent — *one metadata log, rotated, 50 MB* — rather than the shape the package
split forces.

**Recommendation.** Amend the table to describe the directory rather than the file: one log per
event domain under `~/Library/Logs/afleet/`, each metadata-only, each rotated, with the 50 MB
budget applying across the directory rather than per file, and *Delete diagnostics* clearing all
of them. C5's composer already treats them uniformly — it flushes, deletes and reopens all four
together, so the delete affordance is whole today.

Not recommended: forcing four event vocabularies into one file to satisfy the table's wording.
That would mean either a shared writer every package can reach, which is the signature change
the other `[parent-impact]` rejects, or the app re-encoding three packages' closed enums into a
fourth, which puts a translation layer between every diagnostic and its own meaning.

## `[parent-impact]` — `.claude.json` is not inside the config home, and three places say it is

## Surprises & Discoveries

- Observation, **and a correction to this spec and to the parent**: `.claude.json` is **not**
  inside the config home on an ordinary installation. §4 above and the parent both write
  `<configHome>/.claude.json`. The engine resolves the two independently — 2.1.263
  `cli.pretty.js:298330`, `Ot(e) { return { globalConfig: Xe(e || Mt(), ".claude.json"),
  userSettings: Xe(e || Xe(Mt(), ".claude"), "settings.json") } }` with `Xe` bound to `path.join`
  and `Mt` to `os.homedir` — so the document is `join(CLAUDE_CONFIG_DIR ?? homedir(),
  ".claude.json")` while the config home is `CLAUDE_CONFIG_DIR ?? join(homedir(), ".claude")`. The
  two coincide only when the variable is set; with it unset the document is the config home's
  *sibling* and `<configHome>/.claude.json` names a file that has never existed.
  Consequence, found at Task 5 by launching the built app for the first time: it routed to Setup
  with "this Claude Code config home has no signed-in account" on a machine that is signed in, so
  **G1 was unreachable for any user who had not set `CLAUDE_CONFIG_DIR`**. Three readers appended
  to the root. Two are C5's — the onboarding gate and `ClaudeProjects.order` — and are fixed by
  `ConfigHome.globalConfig`, which needs nothing from the environment because `ConfigHome.source`
  already records which derivation produced the root. The third is `TrustReader.isTrusted` in
  FleetKit, outside C5's fence, left alone as tracker entry 59; until it is fixed every project
  reads as untrusted, which C6 is the first child to feel.
  Why the suite was silent: every scratch config home in the tree is built the `CLAUDE_CONFIG_DIR`
  way, where appending to the root is correct, so the tested half was the correct half.
  `AppTests/GlobalConfigLocationTests.swift` now asserts both derivations, each with the clause
  that the other location is not read.
  **Both specs should replace the phrase `<configHome>/.claude.json` with "the engine's global
  config document" wherever it appears.**

- Observation: recovering `.claude.json`'s project order by searching the document for each key

  position. Reading keys from within the object cannot make that mistake, and the test that pins
