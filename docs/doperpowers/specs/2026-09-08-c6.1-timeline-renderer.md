## Purpose

At the pin, a channel's column is C5's proof that history reaches the screen: one row per item,
showing the item's category, its timestamp and a hundred-and-forty-character summary. Every
assistant message in every session on the machine renders as a grey word and a clipped line.

C6.1 makes it a conversation. After C6.1 a channel reads the way the session actually happened:
the person's messages and the model's, the model's with its badge; markdown with real headings,
real tables, real lists and real highlighted code; thinking folded into "Thought for N seconds"
with a live token estimate while it streams; tool calls collapsed into a labelled cluster that
opens; an `Agent` call as a chip that lands you on that run; a compaction as a divider; a turn's
cost and duration as a summary row; the engine's own hidden meta staying hidden. It streams at
the engine's pace without dropping a frame, and the header above it reads back what the channel
is actually running rather than what somebody last clicked.

It is the view C6.3's cards drop into and the view C6.4's per-run transcript reuses, so its shape
is three leaves' shape. Everything it draws is a `TimelineItem` or an overlay entry C3 reduced;
it adds no reducer, spawns nothing, and writes nowhere.

### G1 — S7, the native markdown path under load (required)

The ten-message corpus renders through the native path; a harness drives thirty updates per
second for sixty seconds into a hosted, on-screen list and the frame time stays under 16 ms at
the 99th percentile, sampled with `CADisplayLink` and bracketed with `os_signpost`. Promote the
native path, or adopt the `WKWebView` fallback behind `TimelineRendering` with a Revision Note on
the root spec's §15 S7 and on the composite.

- The corpus is **invented, not recorded** — see the `[parent-impact]` below; its cadence is
  taken from a real fixture's `stream_event` sequence.
- The measurement is of a real `NSWindow` on screen, not of a model in a headless test. A
  harness that measured `AttributedString` construction and called it frame time would pass
  against a renderer that janks, which is the failure §17.7 names.
- The verdict is recorded in the Outcomes section with the p50, p99 and worst frame, the number
  of frames sampled, and the number of dropped intervals.

### G2 — the fixtures render as items, in order, with the overlay live (required)

Replaying `compact-boundary`, `nested-depth-2`, `background-shell` and `session-mirror-resume`

equals the set the `ChannelTimeline` holds, in both directions, **after asserting that set is
non-empty**. Without the floor a failed ingestion compares two empty sets and passes.

### G3 — item 24's link emission (required)

A path in a `Read` row emits `WorkspaceLink.file(url, line:)` through the channel's
`LinkRouterCapability`, with the line taken from `ReadInput.offset` when the engine sent one and

Model, permission mode, effort and the context meter render from `get_settings` and

### G6 — contract Y6, the composer's three rendering sites (required)

The three sites Y6 names, each asserted through the composer model or C6.2's recording double, no

- An *Edit* action on a past user message calls `ComposerModel.edit(_:)` exactly once with that

## Design

### 1. The app has no wire pipeline, and C6.1 lands it

`WireReducer` — C3's fold of everything the transcript never records — has **no production
consumer at the pin**. Its only callers are `FleetKit/Tests/FleetTimelineTests`.
`ChannelTimelineModel.publish()` builds `ChannelTimeline(durable: await ingestion.projection)`
and nothing else, so `ChannelTimeline.overlay` is `.empty` and `ChannelTimeline.preview` is `nil`
in every running channel on the machine.

Every part of C6.1 that the composite names by its wire source depends on that: cluster labels
from `tool_use_summary`, thinking's live estimate, streaming at all, turn summaries, hook runs,
notifications, banners. So does C6.2's queue chip (`Overlay.queue`) and C6.3's card state
(`Overlay.decisions`). It is not an oversight in C3 — `StreamIngestion`'s own comment says so:
"every other event belongs to the channel's `WireReducer`, which holds its own subscription of
C4's per-subscriber fan-out". The subscription was never taken.

**Superseded 2026-09-08 by the architect's ruling from the C3 corrective in flight.** The design
below described an app-side `WireReducer` in `ChannelTimelineModel`. That is not what lands:
**the channel gets one wire fold and it lives in C3's `StreamIngestion`.** The corrective
(`fix/main-host-signal`) gives the ingestion the reducer — it needed one to apply a `HostSignal`
to a current overlay — and extends it to publish overlay and preview changes on `effects` and to
expose `overlay` and `preview` on the snapshot the app reads. One fold, one subscription, in the
layer that already owns the tap.

C6.1's pipeline is therefore: on each effect, build `ChannelTimeline(durable:overlay:preview:)`
from the ingestion's halves and publish. No reducer in the app, no second `events(of:)`
subscription. The thirty-hertz coalescing stays here, in the renderer, where it belongs — it is a
rendering concern and not a reduction one. `ChannelTimelineModel.signal(_:)` becomes a true
forwarder with nothing to apply locally.

This is the better shape and it costs C6.1 nothing it wanted. It does cost two things C6.1
*needs*, and both are findings rather than workarounds: with no app-side fold, **the agent run
tree and the live thinking-token estimate have no route to the app at all** — `AgentRunTree` is a
property of `WireReducer` and no projection carries it, and `system/thinking_tokens` has a field
on neither `Overlay` nor `StreamingPreview`.

The composite's Ordering shows C6.1, C6.2 and C6.3 as three independent wave-1 leaves. They
still are — each leaf's own gates run on doubles and replays and can drive a `WireReducer`
directly, as FleetKit's tests do. What changes is that the *app's* overlay only becomes real at
C6.1's merge. That is a finding for the architect, below, not a re-cut.

### 2. `TimelineRow` carries its item — contract Y1, amended

Y1's builder is `@MainActor (TimelineRow) -> AnyView`, and `TimelineRow` carries `id`,
`category`, `timestamp` and a one-line `summary`. That is C5's placeholder projection: it is
everything the placeholder row draws and nothing a real row needs. No builder can render an
assistant message's blocks, a tool call's input, a cluster's members or an agent chip's status
from a hundred-and-forty-character string.

**The amendment is one field.** `TimelineRow` gains `item: TimelineItem`; `category`, `timestamp`
and `summary` stay, derived from it as they are today, so `PlaceholderRowView`, the closed
category switch and `RowRegistryTests` are all unchanged. `TimelineItem` is `Hashable` and
`Sendable`, so `TimelineRow`'s conformances hold.

The builder's arity stays at one. Everything else a row needs that is not the item — the channel
key, the link capability, the agent-navigation seam, the collapse state of clusters and thinking,
the streaming preview — reaches it through one SwiftUI environment value,
`TimelineRenderContext`, rather than through a wider signature. That keeps Y1's shape stable for
C6.3, which is writing `decision` and `sentFile` builders against it in parallel right now: a
second parameter would be a signature change in a file two leaves both build against, where a
new field on the value they already receive is not.

`RowRegistry.shared` is claimed in `AppModel.init`, beside the `panels.register(PlaceholderTab())`
block the composite calls Y1's other one-line touch point, and that registration is what lets
`Tools/c5/check-app-wiring.py`'s `"register"` allowlist entry (lines 56–59) be dropped.

### 3. The list

An `NSViewRepresentable` over `NSTableView` in a `NSScrollView`, one row per `ItemID`, with row
heights cached per id and invalidated only for the ids a `TimelineChange` names. Not SwiftUI's
`List`, although `List` on macOS is itself `NSTableView`-backed and would satisfy §8.3's letter:

- A streaming delta must reload **one row**, not diff a list. SwiftUI's `List` re-evaluates its
  content closure over the whole collection on every change to the array it was given, and the
  array C5 hands it is rebuilt whole on every publish.
- Bottom anchoring, sticky-to-bottom with silent re-pin, and scroll anchoring (remember the item
  nearest the viewport top and correct `scrollTop` by however far it moved after a commit) need
  the scroll view directly. Parity §41.8 names all three as behaviours a GUI must copy, and the
  third is what stops streaming content shoving the view.
- S7 has to measure something we control.

Row content is SwiftUI, hosted per visible row, because Y1's builder returns `AnyView` and that
contract binds four leaves. The cost is bounded: hosting is per *visible* row, roughly twenty of
them, and the streaming path re-evaluates one row's body at thirty hertz — cheap, as long as the
expensive work (markdown parsing, highlighting, attributed-string construction) is not in the
body. It is not: §4 and §6 put all of it behind caches keyed by content.

Should S7 refute that, the verdict has three branches and not the composite's two — see §11.

A jump-to-bottom affordance showing the unseen count, per parity §41.8; `autoScrollEnabled` is
readable from `get_settings` and is honoured.

**Only the list branch changes.** `App/Views/ChannelColumnView.swift` sits in no leaf's
directory, and the architect's fence for it is that C6.1 owns the list and the row path while
C6.2 owns exactly two call sites — mounting its header above the list and its composer below it.
So `ChannelTimelineColumn`'s outer body keeps the shape C5 left it in: a header slot, then the
list, then the composer slot C6.2 adds; the `failure`, `!hasOpened` and empty branches stay as
they are; `onChange(of: ChannelHeader(row:))` and `task(id: row.key)` stay exactly where and how
they are, because C5's plan records that folding them together cancelled an in-flight read and
half-closed the ingestion actor. C6.1 replaces the `List(model.rows) { TimelineRowSlot(row: $0) }`
expression and nothing around it, and injects `TimelineRenderContext` on that subtree rather than
on the outer `VStack`, so C6.2's two edits and C6.1's one edit touch disjoint lines whichever
lands first. If execution finds the outer body must be restructured, it stops and says so rather
than doing it.

### 4. Streaming

`StreamingPreview` is the source: an assistant message reaches the screen as a preview built from
`stream_event` deltas, and becomes a durable `AssistantMessageItem` when the record lands. The
handover is by `messageID`, so the preview is dropped the moment the durable item carrying the
same `message.id` appears and the row does not blink through an empty state.

**Coalescing.** Deltas arrive as fast as the engine writes them. The model accumulates into the
preview and publishes on a thirty-hertz trailing edge, so one publish can carry many deltas and a
quiet stream still publishes within 33 ms of its last delta.

**Frozen prefix, live tail.** Only the settled prefix of the streaming text is parsed as
markdown; the tail renders as plain text in the same font. The split point is the last block
boundary the delta stream has closed. Two rules from parity §41.17 are copied because they are
not obvious:

- **Open-fence re-prepend.** When the split falls inside an open fenced block, the fence's
  opening line is re-prepended to the fragment so it still lexes as code. Without it a streaming
  code block flickers between code and prose mid-stream.
- **`wrap-stream`.** The last partial line is not laid out as a settled row, or it jitters on
  every delta.

**Nothing expensive runs per delta.** Markdown is parsed for the prefix only when the prefix
grows past a block boundary; code is not highlighted at all until its closing fence arrives
(§6). The tail is a plain-text set on an existing text layer.

### 5. Markdown

`swift-markdown` (Apple, Apache-2.0, already named in the root spec's §11 dependency list and
present in no manifest at the pin) parses a settled block range into an `AttributedString`, and
the result is cached by content hash on the row model.

The engine renders markdown with a vendored `marked`, GFM on and `breaks` **off**, plus three
tokenizer overrides (parity §41.17): `del` matches only `~~x~~`; **link reference definitions are
disabled entirely**, so `[text][id]` renders literally; a table escapes `\|` inside backticks and
bails to a paragraph when a row has more cells than its header. `swift-markdown` is CommonMark
with GFM extensions and expresses none of the three. Two of them are cheap to reproduce as
post-parse adjustments over the parsed tree (single-tilde emphasis is not strikethrough; a table
whose row is wider than its header renders as a paragraph); link reference definitions are not,
because the parser resolves them before we see the tree. The divergence is recorded, not papered
over: a message using `[text][id]` renders as a link in afleet and as literal text in the
terminal, which is a difference in afleet's favour and is stated so nobody reads a bug report as
a regression.

**Raw HTML is escaped, never passed through.** The terminal passes it through unsanitised and
parity §41.17 names that as the one row a GUI must not copy: it is a rendering-injection hazard.

**Untrusted text is sanitised before layout.** Parity §41.7 is explicit that the CLI sanitises at
paint time and the host receives raw text: control characters (`Cc`, `Cf`, `Cs`, `Co`, `Cn`),
U+2028/29, default-ignorables, U+2800, bidi overrides, zero-width marks, U+FEFF and private-use
codepoints are stripped before any model text or tool output is laid out. This is
security-relevant and it is nobody else's in this cut — a bidi-override attack in tool output
renders in afleet if C6.1 does not do it.

Tables are native. Lists nest with real glyphs rather than the terminal's ASCII `-` at every
depth. Links are real and clickable, resolved through §9.

### 6. The highlighter — **PhraseHQ/HighlightKit**, pinned exactly

The human gate ruled the highlighter is pure Swift and left the choice here. It is
**[PhraseHQ/HighlightKit](https://github.com/PhraseHQ/HighlightKit)**, MIT, zero dependencies,
`swift-tools-version:6.1`, `platforms: [.macOS(.v15) …]` (verified against its `Package.swift`),
pinned to an exact tag the way `Workbench/Package.swift` pins libghostty.

**The decisive reason is fidelity, not speed.** §15's S7 promotes the native path when "fidelity
matches the terminal renderer". The terminal renderer's highlighter A *is* highlight.js
(parity §41.17: 180 grammars, a 34-entry scope map, right-to-left dotted-scope fallback).
HighlightKit is a ground-up Swift port of **highlight.js 11.11.1** whose token-exactness is
pinned by 375 differential fixtures generated from that pinned JS source. Choosing it makes S7's
fidelity criterion a property of the library rather than an argument at review time. Its 65
grammars cover what arbitrary model output actually contains, and its alias table is
highlight.js's, so parity §41.17's advice to keep `sh`/`zsh` → bash, `ts`/`tsx` → typescript,
`html`/`svg`/`plist` → xml and `toml` → ini comes for free.

Rejected, with reasons: **Highlightr**, **HighlightSwift**, **HighlighterSwift** and
**ZeeZide/CodeEditor** all run highlight.js inside JavaScriptCore, which is the exact thing S7
exists to keep out; **STTextView** is GPLv3-or-commercial and §12 forbids copying GPL;
**Runestone** declares iOS only; **CodeEditLanguages** ships no license file at all, which is
all-rights-reserved by default and the same class of problem as the SDK typings; **Splash** is
MIT and emits `NSAttributedString` but ships exactly one grammar (Swift), its last release is
2021 and no fork adds languages; **swift-syntax** parses Swift alone; **rork-highlighter** is a
credible Apache-2.0 tree-sitter alternative, roughly four times faster per block, but ships 36
web-and-mobile-skewed grammars and measured **+39.4 MiB** on a release arm64 bundle — too much
for a coverage loss, in an app that also ships Monaco; **atacan/swift-highlight** ships eleven
languages under an unrecognised license.

**The risk, stated plainly.** HighlightKit was created 2026-07-10, has one release, two stars and
one vendor behind it. Three things bound it. It is MIT, pure Swift and dependency-free, so a fork
is a real escape hatch rather than a theoretical one. It sits behind a one-method
`CodeHighlighting` protocol in `App/Timeline/Rendering/`, and the fallback implementation —
unhighlighted monospaced text — is not dead code kept for a rainy day: it is what a fenced block
with an unknown language already renders, so it is exercised on the ordinary path. And the
plan's first highlighter deliverable is a test asserting the grammar set actually contains a
named list of languages, so the README's "65 languages" is a claim this repository checks rather
than repeats.

**Never on the main thread, never per delta.** Highlighting runs off-main and is cached by
(content hash, language, theme); an open fenced block renders unhighlighted until its closing
fence arrives. At three to five milliseconds a block that is a background cost paid once, and it
is what actually protects the 99th percentile.

`syntaxHighlightingDisabled` from `get_settings` is honoured — parity §41.17 notes it is an
accessibility choice for some users.

### 7. Diagrams

Parity §41.17 is unambiguous: mermaid is never drawn in the terminal, and the only mermaid
transform in the bundle is the artifact publisher's markdown-to-HTML, rendered by mermaid.js
**11.16.1** in a browser. A GUI drawing it inline strictly exceeds the terminal, and the
composite allows one lazily created `WKWebView` per diagram block.

**C6.1 renders a ` ```mermaid ` fence as a code block and defers the diagram**, behind the same
`TimelineRendering` seam that carries S7's fallback, with a tracker entry naming 11.16.1 as the
version to match. Vendoring a JavaScript diagram renderer and its assets is a dependency decision
of the same weight as libghostty's pin and Monaco's committed build output; it is not tested by
any of this leaf's gates; and the terminal's own behaviour for the same fence is exactly what

### 8. The rows

### 9. Clusters, thinking and agent chips

**Clusters.** `Overlay.clusters` gives the label from `tool_use_summary`; with no summary the row
shows the count and the elapsed span of the calls it names, and expands to one row per call. The
corpus carries no `tool_use_summary` frame — `ProjectionEqualityTests` asserts as much — so G2's
labelled arm injects one through the replay and says so in the test's own comment.

**Thinking.** A collapsible reading "Thought for N seconds" from the thinking blocks' span. While
the message streams it also shows the live estimate from `system/thinking_tokens`
(`estimated_tokens`, `cli.pretty.js:811445`). That frame has **no home in C3's model**: the
`WireReducer`'s `route(_ system:)` sends it to the `default:` arm, and neither `Overlay` nor
`StreamingPreview` carries a field for it. Under the original design C6.1 read it off its own
event subscription into ephemeral view state; the architect's ruling removes that subscription,
so **the estimate now has no route to the app at all**. That is a finding on the corrective and
not a tracker entry, because no amount of work on this side reaches a frame this side never
sees. Until it is resolved the thinking disclosure renders its duration and not its live
estimate, which is G2's clause minus one word.

**Agent chips, and the tree they resolve against.** C3's corrective (`2dc57ba`) gives the app its
route: `StreamIngestion.agents: AgentRunTree?`, `ChannelTimeline.agents` defaulted nil so C6.1's
one `timeline` read carries the tree beside the items its nodes point at, and
`TimelineChange.agentsChanged` on `effects`, appended once per reducer apply when the tree moved
by value. Finding 1 is answered.

**But the tree is wire-fed only, and that is the ordinary case here, not the edge.** Tracker 187
on `main` records that the file-side `agentMetadata` reading never reaches a tree and that two of
the tree's three parent sources have no production caller: a channel opened from its files — every
archived channel, every foreign session, which is most of what this app lists — has **no tree at
all**, and `agents` is nil. C3 owns the closer and C6.1 does not synthesise one in the app.

So the chip is designed for a nil tree rather than surprised by one. It renders from what the
`toolCall` item itself carries — the agent type and description are in the `Agent` call's own
input, the status follows the unmatched-`tool_use` rule of §8, the elapsed span comes from the
call's and result's timestamps — and it consults the tree only to resolve a run id. **With no tree
the chip renders and does not navigate**, because `AgentNavigation.show(run:in:)` takes a run id
and there is none to give; a chip that navigated to a fabricated id would land C6.4 on a node that
does not exist. G2 replays through the wire path and therefore has a tree; G5 opens a foreign
session from its files and therefore does not, and both arms are asserted rather than one.

**The tool is named `Agent`**, not `Task` — worth stating because §8.8 and the
composite both speak of "`Agent` calls" while the parity map's tool tables and the fixtures name
the tool `Agent`, and a chip keyed on the wrong string renders nothing. A `toolCall` whose name
is `Agent` renders as a compact chip with the agent type, status and locally ticked elapsed time;
clicking it calls `AgentNavigation.show(run:in:)` with the run id resolved through
`AgentRunTree.node(withToolUse:)`, which maps the spawning call's `tool_use_id` to the task id
C6.4 keys its nodes by. Parallel `Agent` calls sharing one `message.id` render as one
"Running N agents" group (§7.3's reducer rule).

### 10. The header's readbacks

The composite splits the header: readbacks here, menus in C6.2. C6.2 owns `App/Header/`.

**C6.1 owns `App/Timeline/Header/`**, which produces a `ChannelHeaderReadout` value and the view
that draws it; C6.2's header bar hosts that view, which is the same mounting edit the architect
has already authorised C6.2 to make in the channel column. Neither leaf edits the other's directory, there
is one derivation of each readback, and the readout is a value a test can assert on without
rendering. C5's existing `ChannelHeader` (title, origin, presence, banner, system item) stays
what it is and the readout sits beside it.

The five readbacks and where each actually comes from:

- **Branch** — `ChannelRow.gitBranch`, which C3's index reads from the transcript's own
  `gitBranch` field. No control request.
- **Model**, **mode**, **effort** — `get_settings`, issued through
  `LifecycleAPI.send(AnyControlRequest(subtype: "get_settings", payload: .object([:])), on:)`.
  Constructing `AnyControlRequest` by subtype rather than from `GetSettings()` is deliberate:
  `GetSettings` is a ClaudeWire type and Y5 forbids a leaf constructing one, while
  `AnyControlRequest` is FleetSessions'. `applied` and `effective` are the readback; a picker's
  last click is never displayed.
- **Context meter** — `get_context_usage`, which returns `percentage`, `totalTokens`, `maxTokens`,
  `autoCompactThreshold`, `isAutoCompactEnabled` and a per-category breakdown. **Nothing pushes
  it** (parity §41.15.4: `autocompact_state` frames are emitted only under `CLAUDE_CODE_REMOTE`),
  so the header polls it after each `result` frame — which is the one place a turn is known to
  have ended — and not on a timer.

Both requests go out only for a channel with a live process, and a `LifecycleError.busy` refusal
leaves the last readback standing rather than blanking it; the surface never retries on its own
(X5's rule).

### 11. `TimelineRendering` and the S7 verdict

One protocol between the model and the view, so a fallback swaps the view and not the model:
the item list, the streaming preview and the change set go in, a view comes out.
`NativeTimelineRenderer` implements it. The `WKWebView` fallback implements it only if S7 says so.

The composite's risk section gives S7 two branches. There is a third, and the plan's first task
is where it is decided:

1. **Native passes** — promote, record the numbers, done.
2. **Native passes only with an AppKit fast path for message rows** — i.e. the p99 is blown by
   `NSHostingView` and not by markdown or highlighting. The fix is a second, optional builder in
   `RowRegistry` returning an `NSView` for the two hot kinds, with the `AnyView` builder as every
   kind's default. That is a Y1 amendment and a `[parent-impact]`, filed then, not now.
3. **Native fails outright** — the `WKWebView` timeline behind this protocol, with a Revision
   Note on §15's S7 and on the composite, as both already provide for.

Branch 2 is named up front because a spike that can only report "pass" or "the fallback" will
report the fallback for a cause the fallback does not fix. Hosting cost and markdown cost are
different failures and the harness separates them with `os_signpost` intervals.

### 15. Contract Y7 — the render context, and the third value written for a reader that did not exist

**[binding, named on the composite at C6.3's merge]** Y1's skeleton paragraph promised a per-row
capability environment value and no leaf built one; four doc comments under `App/` name its absence
and five mounts wait on it. C6.1 owns it.

`TimelineRenderContext` carries two capabilities that matter beyond layout:

- **The link capability**, `ChannelContext.links`, so a card's paths render as links without a
  second registry. C6.1 reads it from `PanelHostModel.links` (§9), never from `context(for:cwd:)`.
- **The channel fold's `signal(_:)`**, so an answering object constructed from a row can raise
  `HostSignal.decisionAnswered` and a card leaves `pending` on screen.

The consumers are another leaf's and arrive later: the decision row's actions, the sent-file row's

mounted on C6.1's `taskRun` row. Activity's and the Thread tab's raises are closed on that leaf's
own branch through the app-scoped `ChannelTimelineRegistry` and are not C6.1's.

**This is the third value in this cut written faithfully for a reader that did not exist** — after
`HostSignal`, constructed nowhere, and `editNote`, written in eight places and read by no view. The
pattern is now worth naming rather than fixing three times: a leaf that owns a behaviour writes the
state for it and has no structural way to notice that nothing renders it, because its own gates
pass on the state and the renderer's gates pass on the rows. The two directions of a seam get
specified separately and only one gets built. Y4 and Y6 are the same shape read from opposite ends.

So the capabilities are wired from the real objects at construction, and the environment default is
**not** a silent no-op: a default that nobody assigns is exactly the failure this contract exists to
prevent, and it has now happened three times in one composite.

## `[parent-impact]` — Y1's row payload cannot render a row

**The claim.** Contract Y1 is binding on four leaves. Its builder signature is
`@MainActor (TimelineRow) -> AnyView`, and `TimelineRow` — C5's type, carried into the skeleton
unchanged — holds `id: ItemID`, `category: TimelineCategory`, `timestamp: Date?` and
`summary: String`, where `summary` is a flattened, 140-character, single-line projection. No
builder can draw an assistant message's blocks, a tool call's typed input, a cluster's member
ids, an agent chip's status or a turn summary's cost from those four fields. Y1's registry is
correct in every respect except that what it hands a builder is the placeholder's data.

**Why it is a parent-impact and not a design choice.** C6.3 is writing builders against this
signature in a parallel worktree at this moment, and C6.4 will reuse the view. A leaf that
widened the type silently would hand the other two a merge conflict in a file the composite
placed on `main` specifically so that could not happen.

**The filing.** `TimelineRow` gains `item: TimelineItem`; the four existing fields stay and stay
derived; the builder's arity does not change; per-row capabilities travel in a SwiftUI
environment value rather than a second parameter. `PlaceholderRowView`, the closed category
switch, `RowRegistryTests` and C6.3's in-flight builders all keep compiling. Filed against the
composite's "The skeleton the orchestrator lands before dispatch" and contract Y1, for the
architect to apply at merge — and to **tell C6.3 now**, because the value of a shared skeleton is
that both leaves build against the same one.

## Decision Log

- **C6.1 lands the app's wire pipeline.** The alternative was to render the durable half only and
  let C6.2 or C6.3 take it, which would have made three of C6.1's own gates unreachable.
- **The wire reducer's durable half is discarded.** §7.3 makes the record reducer primary; keeping
  both would be two derivations of one thing in the app, which is what the differential test
  exists to compare and not what a renderer should hold.
- **`TimelineRow` widens; the builder signature does not.** One field on a value both leaves
  already receive costs C6.3 nothing; a second parameter is a signature change in a shared file.
- **`NSTableView` directly, not SwiftUI's `List`.** One-row reloads, scroll anchoring and a
  measurable surface, against more code. `List` would satisfy §8.3's letter and lose all three.
- **Row *content* stays SwiftUI.** Y1 binds four leaves and an `AnyView` builder is what it says;
  the cost is bounded to visible rows and is what S7 measures.
- **HighlightKit over rork-highlighter.** Coverage and fidelity over per-block speed, and 39 MiB
  of parser tables is too much to pay for a coverage loss. Both clear the frame budget.
- **Highlighting is off-main, cached, and never runs per delta.** The single decision most likely
  to decide S7.
- **The thinking estimate is view state, not an overlay field.** FleetKit is outside the fence;
  a `[parent-impact]` on X4 mid-wave costs an orchestrator corrective for a scalar that is gone
  when the message settles.
- **Raw HTML is escaped and untrusted text is sanitised.** The terminal does neither; parity
  §41.7 and §41.17 both name it as a rebuild a GUI owns, and nobody else in this cut does it.
- **The S7 corpus is invented.** Stated as a `[parent-impact]` rather than absorbed quietly,
  because "recorded" was a word the composite chose on purpose.

## Outcomes & Retrospective

### S7 — settled 2026-09-08, **branch 1: promote the native path**

Two independent runs, the executing worker's and the leaf owner's re-run:

| | p50 | p99 | worst | samples | dropped | rows |
|---|---|---|---|---|---|---|
| run 1 | 0.28 ms | **1.47 ms** | 4.54 ms | 1,770 | 7 | 68 |
| run 2 | 0.29 ms | **1.62 ms** | 3.17 ms | 1,780 | 7 | 69 |

Bound is 16 ms at the 99th percentile; measured about 1.5, an order of magnitude of margin.
Phase totals across the minute: hosting 349–389 ms, markdown 180–192 ms, highlighting 0.4–0.6 ms.
**Hosting dominates, and at ~0.2 ms per update it dominates nothing that matters** — `NSHostingView`
per visible row is nowhere near the cost branch 2 exists to name, so Y1's builder type stands
unamended and the `WKWebView` fallback is not adopted. Highlighting is invisible in the profile
because it never runs on the main thread and never runs per delta, which was the design's central
bet and is the one number that most vindicates it.

The root spec's §15 S7 and the composite's risk row are discharged as *promoted*.

### What the spike caught about itself, which is the part worth keeping

Both of these were caught before a number was reported, and both are the failure modes §17.7 names
rather than new ones:

- **The gate under-drove itself.** A bare `>= 1/rate` wait on a 60 Hz display link lands exactly on
  a callback boundary: the callback at one period reads a hair early, the update waits for the
  next, and thirty hertz collapses to about twenty-three. The first run took 1,367 samples in sixty
  seconds and called itself thirty hertz. Allowing half a refresh period fixed it to ~1,775. A gate
  quietly running at three-quarters of its stated load passes renderers that should fail it.
- **`AFLEET_S7=1` never reaches the test host; the spelling is `TEST_RUNNER_AFLEET_S7=1`.** The
  first gate run skipped and exited zero — a gate reporting green having never run. C5's spec
  records this trap in three places and it cost a run here anyway, so the skip message now names
  the working spelling and the reason sits beside it in the test.
- **The instrument's own two-sided self-test is what makes the verdict mean anything.** Blocking a
  fortieth of a second every tenth update reads p99 41.1 ms; an empty closure reads 0.24 ms. Timing
  the display-link *interval* would pass the first and fail the second — it is pinned near 16.7 ms
  on a 60 Hz panel, so green would be unreachable. Timing an `AttributedString` build would pass
  the second and fail the first. Only the span from an update's start to a laid-out hierarchy
  passes both.
