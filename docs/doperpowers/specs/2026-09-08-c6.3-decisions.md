## Purpose

At the pin, every decision the engine raises reaches the user as one line of text. C5's
Activity lists a row for each; a plain permission ask carries *Allow once* and *Deny*, and
every other kind — a question, a plan, an elicitation, either dialog — carries *Go to
channel*, where nothing is waiting, because the channel column draws a category name, a
timestamp and a one-line summary and has no cards at all.

C6.3 makes the decision the thing the user acts on. Six card kinds and two dialog cards,
rendered from what C3 reduced and answered through the one mapping §8.4 states: a permission
card that shows the diff a `Write` would make and the scope an *Always allow* would take; a
question card with its options side by side; a plan card; an elicitation form; a task card
that can send its work to the background; a refusal-fallback dialog that retracts the messages
it concerns when it is settled and not before; an overage dialog that renders the engine's own
fallback frame as its outcome. Beside them, the Thread tab: one thread at a time, Slack-style,
over §7.5's five kinds, where replying to a card is a way of answering it and *Ask on the
side* asks without touching the transcript. And the two things that stop a channel before it
starts — the project-server consent sheet of §6.12 and the trust banner of §6.11 — become
surfaces with actions rather than states with words.

One component serves both hosts. Activity stops constructing a card of its own and renders
this one, so the mapping from a click to an `InboundAnswer` exists once in the tree.

## Grounding baseline

What is on `main` at the pin, read rather than taken on report. Each line is a fact this
child's design stands on; the file and symbol are named so a reviewer can check the claim.

## Residue

### D1 — [ruled 2026-09-08 from C6.1's gate] The Y1 row payload carries its item

As cut, `RowBuilder` took a `TimelineRow` of four scalars — `id`, `category`, `timestamp` and
a one-line `summary` — and a decision card needs `DecisionItem.payload`, `.state`, `.kind`,
`.toolUseID` and `.agentID` while the sent-file item needs `SentFileItem.files`, `.caption`
and `.delivered`. Neither survives that projection. Filed at the grill with three ways out.

**Ruled:** `TimelineRow` gains **`item: TimelineItem`**. The four existing fields stay and
stay derived, so nothing that reads a summary changes, and the **builder arity is unchanged** —
it is still `@MainActor (TimelineRow) -> AnyView`. **Per-row capabilities travel in a SwiftUI
environment value**, not in the row and not in the builder's signature, so the row stays a
plain value and a card reaches its answering object and its link router the way SwiftUI
already passes ambient context down a tree.

This child's `decision` and `sentFile` builders therefore read `row.item` and switch on it;
neither reads `row.summary`. The rest of the D1 analysis is superseded. It changes nothing
before Task 8: the component is built and tested against `DecisionItem` values directly, which
is what the composite's Ordering already intends.

### D1b — [ruled 2026-09-08 from C6.1's gate] The app has no wire pipeline yet, and C6.1 lands it

A fact not visible from the reducer, and stated here because the Grounding baseline above
would otherwise mislead: C5's `ChannelTimelineModel` publishes only the **durable projection**.
The `WireReducer` runs nowhere in the app, so `Overlay.decisions` is empty in every running
channel today — not stale, not partial, empty. Every decision a user has seen in afleet so far
came from `ChannelState.pendingDecisions` and the Activity pump's live `InboundRequest`s, and
never from the timeline.

**C6.1 lands the `WireReducer` subscription in the same seam commit as D1's row payload.** The
architect lands that commit range on `main` as the second skeleton commit and names the hash;
this child **takes `main` at its next task boundary after that message**, never mid-task.

Three consequences this document depends on:

- **Nothing in Tasks 1 through 7 waits on it.** The card, its mapping, the four remaining card
  kinds, the dialogs, the Thread tab, consent and trust are driven from `DecisionItem` values
  and a lifecycle double. Activity's adoption (Task 2, G3) is driven from the pump's live
  requests through D14's surfacing initialiser — the path Activity already takes, which does
  not read the overlay at all. G3 is green before the pipeline exists, and that is not luck of
  ordering: it is why Y2's second host was the reachable one first.
- **Task 8 is where it starts mattering**, because that is where a decision reaches the
  channel column and the column's decisions come from the overlay the subscription fills.
  Task 8 already waits on C6.1's merge; this is the same wait with a named cause.
- **It sharpens D2 rather than closing it.** The subscription makes `Overlay.decisions`
  *populate*; it does not move an entry out of `pending`, because that transition belongs to
  `HostSignal.decisionAnswered` alone and nothing raises one. Two gaps in one pipeline, and
  only the first is being closed. D2 stands as filed.

### D2 — [ruled 2026-09-08; corrective dispatched] `HostSignal` has no delivery path

Y2 is explicit: "A card's *state* … is C3's `DecisionItem.state`; the view renders it and
never keeps its own." That cannot hold at the pin. The only transition into
`.answered(outcome:)` is `HostSignal.decisionAnswered`, `HostSignal` is constructed nowhere in
the tree, and `StreamIngestion` — the app-side owner of the wire reducer — exposes no member
that accepts one. A user who answers a card in the timeline today would see it stay `pending`
for ever.

This is not this child's to fix and it is not only this child's problem: C6.2's composer needs
`promptSent` for `TurnSummaryItem`'s `.prompted` attribution and `rewound` for item 13.
**Recommendation: a C3 corrective on `main`, in the same shape as the tracker-74 and -77
correctives the composite's Risks section already schedules —** `StreamIngestion` gains
`public func signal(_ HostSignal) async -> Effect`, routed to `WireReducer.apply(_:at:)`, which
is already public and already correct. The app-side caller is one line after a successful
`perform(.answer)`. Filed below as a `[parent-impact]` against X4 and X5 because the two
contracts disagree about who closes the loop, and X5's `perform(.answer)` returning a
`ChannelState` is the shape that made the gap easy to miss.

**Ruled, dispatched, and landed on `main` at `2e85ac0`** (fold `01eb7a7`; X4/X5 wording
`2e85ac0`), in the shape recommended: `StreamIngestion.signal(_ HostSignal) async -> Effect`
forwarding to `WireReducer.apply(_:at:)` and publishing through the same effects path every
other mutation uses. FleetKit after it: 440 executed, 10 skipped, 0 failures. C6.1's seam
commit adds the one-line `signal(_:)` forwarder on `ChannelTimelineModel` and lands separately
as skeleton 2. C6.2 raises `promptSent` and `rewound` the same way. X4 names the delivery path
and X5 names the app as the raiser, both at merge.

What Task 8 consumes: after `perform(.answer)` **succeeds**, the host raises
`.decisionAnswered(id, outcome)` through the forwarder, and the card leaves `.pending` **on the
host's own evidence rather than waiting for the engine's next frame** — which matters, because
the engine sends no frame back for an answer at all. The returned `Effect` carries the overlay
change in `changes` (`.updated` / `.removed(ItemID)`, plus `.overlayChanged`), and
`StreamIngestion.timeline` is the one-read view a test asserts the resulting state through. The
ingestion holds the channel's only `WireReducer`; nothing else in the app folds the wire.

**The fallback is retired, and the distinction it leaves behind is load-bearing.** With the
corrective on `main` there is no branch in which a view holds decision state, so the earlier
fallback is struck rather than kept as an option. What remains, and what must not be confused
with it: `DecisionAnswering` tracks **which request ids have an answer in flight**, to disable
the buttons and refuse a double-send between the click and the `perform` returning. That is
request-in-flight bookkeeping about a network call, not a second copy of
`DecisionItem.state` — the card's rendered **outcome** is only ever C3's state, and the
in-flight set can say nothing about what the answer was, only that one is on the wire. A
reviewer should check exactly that: the set is keyed by `RequestID` and holds no outcome.

### D4 — [ruled 2026-09-08] Y2 versus C5's human-gate ruling 4

Y2 says the timeline and Activity "both host that one view". C5's human-gate ruling 4

### D5 — The destination picker belongs to rule suggestions, not to every suggestion

§8.4 reads "*Always allow* … with `updatedPermissions` at the chosen `destination` (user,
project or local settings)", which suggests a picker on every *Always allow*. The evidence
says otherwise, and the correction matters because it is the difference between offering the
user a choice and offering them a wrong one.

`permission_suggestions` and `updatedPermissions` are the same six-variant union
(`cli.pretty.js:94590`, 2.1.263), and the variants divide cleanly:

- **`addRules` / `replaceRules` / `removeRules` / `addDirectories` / `removeDirectories`** —
  these persist a rule or a directory into a settings file, and *where* is a real user choice.
  `Fixtures/send-user-file` witnesses one: `addRules` for
  `mcp__afleet__send_user_file`, `behavior: allow`, `destination: localSettings`.
- **`setMode`** — this switches the session's permission mode. Its destination is
  **`session`**, and the engine's own `ExitPlanMode` row constructs exactly
  `{type:"setMode", destination:"session", mode:<chosen>}` (`cli.pretty.js:14602`).
  `Fixtures/permission-allow` and `Fixtures/notification-hook` both carry a `Write` ask whose
  only suggestion is `{"type":"setMode","mode":"acceptEdits","destination":"session"}` — which
  is exactly what root item 5 means by "the request carries a `setMode` suggestion", and what
  makes item 5's third file write with no card. A destination picker over a `setMode` would
  offer to write a mode into a settings file, which is not what the suggestion says and not
  what the engine would do with it.

**Decided:** *Always allow* re-encodes the engine's suggestions and changes **only** the
`destination` of the rule- and directory-carrying variants, over the three §8.4 names —
`userSettings`, `projectSettings`, `localSettings` — preselecting the suggestion's own when it
is one of the three and `localSettings` otherwise. A `setMode` suggestion is sent **verbatim**
and shows no picker. A card whose suggestions are all `setMode` therefore offers *Always
allow* with no destination choice at all, and that is the shape the two live arms of G5 hit.
A `.unknown` suggestion is sent verbatim too — it re-encodes losslessly and rewriting a field
of an opaque value is guessing — and a card whose suggestions are *all* `.unknown` offers no
*Always allow*, because nothing there can be described to the user.

### D6 — A denial does not interrupt

`PermissionResult.deny(message:interrupt:classification:)` carries an `interrupt` flag §8.4
never mentions. **Decided:** `interrupt: false` everywhere in this child. A denial is
feedback the model reads and works around — item 41 requires exactly that ("Claude's next
message reflects the reason") — and stopping the turn is a separate affordance the user
already has (Esc, §8.7). Activity's landed path already spells it this way.

### D7 — The billing route degrades through the link fallback

Item 62 wants *Set up usage credits…* to open the Anthropic billing page "in the Browser tab".
C7.6 is not on `main`, and the composite names conditional edges to C7.2 and C7.4 but not to
C7.6. **Decided:** the action emits `WorkspaceLink.url` through `ChannelContext.links` and
asserts nothing about the destination; with no Browser target registered, `HostLinkRouter`'s
fallback opens it externally, which is the parent's item 62 degraded rather than skipped —
the same bargain the composite struck for item 47. Recorded as a third conditional edge, on
C7.6, in the Parent revisions below.

**Settled by the bundle reading, and it is the second of the two branches.** The overage
dialog's payload is `{overagesEnabled, modelName?, balanceCents?, currency?}`
(`cli.pretty.js:725659`) and carries **no URL**. So the card does not invent one and does not
hard-code an Anthropic console address — that would be afleet asserting a first-party fact it
has no evidence for, and the address is exactly the kind of thing that moves. *Set up usage
credits…* opens the billing page **only** if a URL is available from a source afleet already
trusts; with none, the action reads *Set up usage credits in your browser* and explains that
credits are set up outside the session, and the card stays pending exactly as §8.4 requires
until *Switch to the default model* or *Not now*. Filed as a `[parent-impact]` note below,
because §8.4 describes an action ("opens the Anthropic billing page in the Browser tab") the
payload cannot source.

### D8 — Elicitation has two modes, and the form implements a stated subset

The bundle corrects the shape this document first assumed. `elicitation` carries
`mode?: "form" | "url"` (`cli.pretty.js:94598`, `:141932`), and the two modes are different
surfaces:

- **`mode: "url"`** — the payload carries `url` and `elicitation_id` and there is no schema to
  fill in. The card renders the server name, the message and one action that opens the URL
  through `ChannelContext.links` as a `WorkspaceLink.url`, plus `decline` and `cancel`. Not a
  form at all. This mode was missing from this document's first draft and would have shipped
  as an empty form with an ignored URL.
- **`mode: "form"` or absent** — `requested_schema` is a JSON Schema object.

**Decided for the form mode:** render `type: object` with `properties` of `string` (text
field; `enum` becomes a picker), `number`/`integer` (numeric field), and `boolean` (toggle),
honouring `required`, `title`, `description` and `default`. An array of strings is a
multi-select, because the engine's own result type is
`Record<string, string | number | boolean | string[]>` (`cli.pretty.js:141932`) — so a string
array is in the contract and not an extension. Anything else — a nested object, a `oneOf`, an
array of non-strings — renders as a raw JSON text field for that property with its schema
shown, and the card says the form is partial.

`content` is a **sibling of `action`**, not nested under a result or a behavior, which is what
`InboundAnswer.elicitation` already encodes. `decline` and `cancel` are available whatever the
mode and whatever the schema, because §6.4 makes an unanswerable request the one failure mode
that must not exist. The subset and its boundary are a tracker entry so the next widening has
a place to start.

**No fixture carries an elicitation.** The corpus has none; the evidence is
`ClaudeWire/Tests/Support/Samples/control_request_elicitation.json` and
`FixtureRunner.elicitation(id:)`, both invented. G1d therefore runs on invented requests, and
says so rather than implying a recording exists.

### D9 — The diff is `CollectionDifference` over lines, behind `DiffRendering`

**Decided:** `protocol DiffRendering { func view(before: String, after: String, path: String)
-> AnyView }`, with `AttributedDiffRenderer` computing a line-level
`CollectionDifference` and drawing added, removed and context lines. `Write` diffs against the
file's current contents when it exists and against empty when it does not — read with
`String(contentsOf:)` and no descriptor held open on a user-content directory (the C5 TCC
finding). `Edit` diffs `old_string` against `new_string` in place, with the surrounding lines
from the file for context. When C7.2's `MonacoEditorView` is on `main`, a second conformer
replaces the renderer and no card changes. A file the app cannot read renders the tool input
verbatim rather than a diff, and says so.

**Absent is not unreadable, and an `Edit` against an absent file is not the verbatim fallback**
(ruled at Task 3, which found this unstated). *Unreadable* means afleet could not determine
what the file says, so any diff it drew would be fiction — hence verbatim. *Absent* is a fact:
there is no file, so a `Write` is all additions, and an `Edit` shows `old_string` against
`new_string` with no context, because context is the thing the missing file would have
supplied and nothing else about the request is unknown. The card is drawn **before** the tool
runs — it is a permission ask — so rendering what the model proposed is honest even where the
engine would go on to reject the edit.

### D10 — Reply-to-card and *Ask on the side* send through X5 directly

§7.5's Decision thread replies *are* answers: a reply to a permission card is
`perform(.answer(id, .permission(.deny(message: <the text>, …))))`, to a plan card the
rejection with the text as feedback, to a question card *Other* with the text. Those need no
composer. The tool-detail and sent-file threads post to the main session with a `Re: <tool>
<short id>:` prefix, which is `perform(.send(UserInput(text:)))` — a plain text send.
**Decided:** the Thread tab calls `perform(.send)` for those two kinds with a one-line field

### D12 — Four inert readings, read from the code and not from the prose

| *left to the binary — unrecognised dialog* | `.inert` and **not** stale — `.unansweredDialog`, a `dialog_kind` afleet did not declare (§6.3) | 62's last clause |

### D18 — *Move to background* is refused for a run already in the background

Raised at Task 4 as a judgement call between two clauses of §8.4 that read differently. The
action clause says "only on a running Bash call or agent run present in the registry mirror";
the trigger row says "running **foreground** Bash calls and agent runs the registry mirror
knows". The worker read the placement word as load-bearing and refused the action for a run
already backgrounded.

**Ratified, and not on the strength of the prose.** The engine's own eligibility predicate
(`cli.pretty.js:771372`) is `!e.isBackgrounded && Boolean(e.shellCommand)` for a local bash
task, and `… && !e.isBackgrounded && …` for the rest; `Ode` refuses a targeted
`background_tasks` outright when that predicate fails. So a card offering the action on an
already-backgrounded run would be offering a button whose only possible answer is
`{backgrounded: false}` — an affordance that cannot succeed. The guard is the engine's rule
restated in the surface, which is exactly what §8.4's *never on Read, Edit, WebSearch* clause
is doing for the other half of the same predicate.

The consequence is worth recording because it shapes a test: `Fixtures/background-shell`'s
recorded run carries `is_backgrounded: true`, so it cannot drive the *offered* arm. The test
uses that recorded shape with the one flag flipped and says so, rather than pretending a
fixture witnesses an arm it does not.

### D17 — Activity's inline eligibility is the kind **and** the flag, not the flag alone

Raised at Task 2. D4 says Activity answers inline for "a plain permission ask"; the rule C5
actually shipped is "a `can_use_tool` without `requires_user_interaction`". Today the two
coincide, because the engine sets that flag on `AskUserQuestion` and `ExitPlanMode`
(`cli.pretty.js:283001`) and both fixtures carry it. They diverge on a request that is a
question or a plan and does **not** carry the flag — and C5's own floor test constructs exactly
that shape, by clearing the flag on `ask-user-question`.

That shape is harmless while no question card exists. From Task 4 it stops being harmless: the
one rule would let Activity render a question card's actions inline, which is C5's human-gate
ruling 4 widened by accident rather than by decision. The flag and the kind are two different
protections — the flag is the engine saying *this tool's own card is the surface*, the kind is
the human's ruling about *what Activity may answer* — and neither implies the other.

**Decided:** Activity's inline affordance requires **both** — `DecisionCard.kind == .permission`
**and** `requires_user_interaction` unset. Strictly narrower than what shipped, so no ruled
behaviour changes.

The cost is real and is paid rather than hidden: C5's floor test would become vacuous, passing
because the kind excluded the request rather than because the flag did. So it moves onto a
`permission-allow` request with the flag **set** by override, where the flag is the only thing
that can exclude it, and a second test asserts a flag-cleared question is still refused inline —
the clause that catches the kind guard. Two tests, one condition each, each able to fail alone.
A single test over both conditions could not tell which one was doing the work, which is how the
gap arrived in the first place.

### D16 — afleet sets `decisionClassification` on every decision it prompts for

Raised at Task 1: §8.4 names a classification for each of the three *permission* actions and
names none for the question and plan rows, so a literal reading sends none there. The literal
reading is wrong, and the bundle says so in a sentence written for exactly this host
(`cli.pretty.js:94590`, schema `LU`):

> "Classification of this permission decision for telemetry. **SDK hosts that prompt users
> (desktop apps, IDEs) should set this to reflect what actually happened**: `user_temporary`
> for allow-once, `user_permanent` for always-allow (both the click and later cache hits),
> `user_reject` for deny. **If unset, the CLI infers conservatively** (temporary for allow,
> reject for deny)."

afleet is that host. Two things follow, and the second is why this is not merely tidy:

- The obligation is on the **host that prompts a person**, not on the particular §8.4 row. A
  question and a plan approval are both decisions a person made, so both carry one.
- **The inference the engine falls back to is not a constant.** At `cli.pretty.js:735273` an
  absent classification is replaced by
  `(updatedPermissions ?? []).some(d => <destination is persistent>)`. So an unset answer's
  meaning depends on the destination of whatever updates it happens to carry — which for the
  plan card's `setMode` at `session` reads as not-permanent today, and would flip if a future
  card ever attached a persistent update alongside. Sending the classification explicitly
  makes the value afleet's statement about what the user did, rather than a value the engine
  derives from a field chosen for another purpose.

**Decided:** every answer this child sends carries a classification — *Allow once* and the
question answer `.userTemporary`; *Always allow* `.userPermanent`, whatever the suggestion's
destination, because item 5 requires exactly that; *Deny…* and *Reject with feedback*
`.userReject`; plan *Approve* and *Approve and auto-accept edits* `.userTemporary`, since
neither persists a rule. On today's engine this agrees with the inference in every case, so it
changes no behaviour and cannot regress; what it buys is that the meaning stops depending on a
derivation the host does not control. Elicitation and dialog answers carry none — the field
does not exist on their response schemas.

## Design

### One value, one view, one function

```
DecisionItem  ──decode──►  DecisionCard  ──►  DecisionCardView(.full | .compact)
 (C3, overlay)              (a value)              │
                                                   ▼  DecisionAction (a closed set)
                                                   │
                                            answer(_:) -> InboundAnswer?
                                                   │
                                          DecisionAnswering
                                                   │
                                   perform(.answer(id, answer), on: key)
```

`DecisionCard` is decoded from `DecisionItem` and holds no reference to a channel, a
lifecycle or a view. Its payload case is typed with C2's own `Codable` fields — the whole
point of `DecisionItem.payload` being `request.raw` is that no second source is needed. A
payload this build cannot type becomes `.unmodelled(JSONValue)` and renders as a read-only
card with no answer actions, because §6.3's rule for an unknown *inbound request* is an
immediate error answer at the transport, not a guess at the surface; a card only exists at
all for a subtype the reducer opened one for.

`DecisionAction` is closed. `answer(_:)` is a pure function from an action to an
`InboundAnswer?`, and it is the **only** place in this child that constructs one. That is
what makes Y2 checkable rather than aspirational: two hosts render one view, one view emits
one action set, one function turns an action into an answer, and one object performs it.
`answer(_:)` returns nil for the two actions that are not answers — the overage card's
billing link and the task card's *Move to background*, which is a control request — so
"every answer comes from here" is an assertion a test can make about the shape of the code
and not only about its behaviour.

`DecisionAnswering` is the object both hosts hold. It performs `.answer`, renders a
`LifecycleError` through C5's `RowBanner`, and tells the channel's pump to forget the id —
the seam C5 already installed, because the engine sends no frame back for an answer.

### The two presentations

`.full` is the timeline's card: title, consent line, the tool's input formatted per §8.4
(shell in monospace, `Edit` and `Write` as diffs, paths as links through
`ChannelContext.links`), the actions as buttons, the outcome when it is inert. `.compact` is
Activity's row affordance: the tool's display name and the same action buttons, without the
input rendering, because Activity is a list of everything waiting across the fleet and a
full card per row is a different surface. Both draw from the same `DecisionCard` and emit
the same `DecisionAction`. The presentation changes the layout and nothing else — no action
exists in one and not the other for the kinds Activity answers, which is the invariant G3's
byte-identical-answer test holds.

### The state is C3's, and where that is not yet true

The card renders `DecisionItem.state` and keeps none of its own. The five states map to five
readings: `.pending` (actions live), `.answered(outcome:)` (inert, the outcome shown),
`.cancelled` (inert, *answered elsewhere*), `.policyAnswered(error:)` (inert, the error),
`.inert`. The sixth reading is not a state: a `.pending` card in an overlay C3 has marked
`stale` reads *session ended*, which is item 44. Until D2's corrective lands, `.answered` is
unreachable and `DecisionAnswering` shows the answer as *sent* from its own in-flight set for
the duration of the round trip; the tracker entry names the corrective as its closer.

### The permission card

`display_name` or `tool_name` as the title; `description` as the consent line;
`ToolInput.parse` for the input, so `Bash` renders its command in monospace, `Read` and
`Write` render their path as a link, and `Edit`/`Write` render a diff (D9). `decision_reason`
is stripped of ANSI and, when empty, rebuilt from `decision_reason_type` and
`matched_ask_rule` (*A-24*). `agent_id` joins to the run's type and description as C3 already
joins them, which is item 52's card half and the same label the Agents tab will draw through
Y2.

Three actions, and which of them exist is data: *Allow once* always; *Always allow* only when
`permission_suggestions` is non-empty, `suppress_always_allow_rule` is not set, and at least
one suggestion can be described to the user (D5); *Deny…* always, opening a text field. The
destination picker appears only alongside a rule- or directory-carrying suggestion; a
`setMode` suggestion is sent verbatim at `session`. `default_to_no` focuses decline and
unbinds the approve shortcut. `requires_user_interaction` removes the one-tap approve and deny
entirely: the tool's own card — the question card, in the one case the engine ships — is the
surface, and this is why `AskUserQuestion` arrives as a `can_use_tool` and is nonetheless a
different card. All three flags are **omitted when false**, so absent means false.

### The two dialog cards

`UserDialogFields.dialogKind` selects the card; the two kinds afleet declares in the
handshake are the two it renders, and any other kind is left unanswered by design (§6.3) and
produces no card. The refusal card's actions send their result inside `{behavior:
"completed", result: <string>}`; closing sends `{behavior: "cancelled"}`, which is also the
binary's own default at its **five-minute** deadline (anchor 4), which a pending card shows.
The overage card offers `consent` only when `overagesEnabled` is true, because a bare wire
reply never enables billing; with it false the first action leaves the card **pending** — the
only action in this child that resolves nothing — and the card resolves on *Switch to the
default model* or *Not now*. It carries no billing link, because the payload carries no URL
(D7). On the balance, this document's first wording — "shows no balance, because `balanceCents` and
`currency` are declared but unfed" — read two ways against "renders what arrives", and the reading
ruled at Task 5 is **no defaulting, either direction**: absent or `null` draws no balance line; a value
that arrives is drawn, **including `0`**. `Fixtures/dialog-fable-overage` records both shapes (three
frames at `balanceCents: 0`, two at `null`), so both are real. Suppressing a literal zero would hide
the single most relevant case this card exists for — a user with no credits being asked to buy some —
and inventing a zero where the engine sent nothing would assert a fact afleet does not have. "Unfed"
describes today's engine, which sends neither field; it is not licence to discard one that arrives.
A following `system/model_consent_fallback` renders its `content` as the card's outcome
whatever the answer was — **and its absence is equally correct**, because the engine emits
nothing when provisioning succeeded, so nothing here waits for it.

`retractedMessageUuids` are held by `RetractionRegistry` and applied at render time by the
channel's list, never by a reducer (D11). They enter the registry on *resolution* — any
answer, or a `control_cancel_request` that retires the dialog — and never on receipt, which
is the clause item 62 asserts in both directions.

### The Thread tab

A `PanelTab` for `.thread`, taken from C5's placeholder by `unregister` then `register`
(Y3). One thread open at a time, Slack-style, in a `PanelTabSession` the host retains per
(tab, channel) so a channel switch does not lose it. Five kinds, five anchors, five reply
behaviours as §7.5's table states them. The three answerable kinds reply through
`answer(_:)` — a reply *is* the card's textual outcome, so the same function produces it and
G2's assertion is on the emitted answer. The two posting kinds send a plain
`perform(.send(UserInput))` with the `Re: <tool> <short id>:` prefix and no composer
machinery (D10). *Ask on the side* is `SideQuestion` through
`LifecycleAPI.send(AnyControlRequest, on:)` with history accumulated in the thread's own
state.

### Consent and trust

One `ChannelDecorations` view over `LifecycleAPI.preconditions(for:)`. `consentNeeded`
presents the sheet: each server's name and transport summary, *Accept* →
`acceptProjectServers` (which writes nothing; the store remembers the acceptance per project
and server hash), *Decline* → `declineProjectServers` (the one Claude Code-owned file afleet

and `PanelHostError.noPaneRunner` surfaced as a banner naming the terminal. That is item 47
degraded exactly as far as C7.4's absence forces and no further.

### The sent-file item

`SentFileItem` renders its caption, its file list and a preview of the first file, with
*Open in Files* as a `WorkspaceLink.file(url, line: nil)` through the context's `links`

**Eight consequences this design takes, each of which the first draft got wrong or left open:**

- **The overage card cannot show a balance.** `balanceCents` and `currency` are declared but
  **currently unfed** — the sole runtime construction sends `{overagesEnabled, modelName}`
  only (`cli.pretty.js:770104`). §8.4 says the card renders "the model name, balance and
  currency"; two of the three will be absent in practice. The card renders what arrives and
  says nothing about a balance it does not have.
- **`consent` can be followed by `model_consent_fallback` with `choice: "consent"`** — the
  engine emits it when the entitlement check *fails* after a consenting reply, and emits
  **nothing** when provisioning succeeds (`cli.pretty.js:770089–770155`). So the card must
  neither wait for the frame nor treat its absence as a failure. §8.4's "may arrive even after
  `consent`" is exactly right and the reason is now on the record.
- **The dialog has a real deadline: five minutes.** §8.4 says "cancelled by the binary at its
  dialog deadline" without naming one. A pending dialog card carries that, so the user is not
  looking at a control that has silently expired.
- **An error-subtype response leaves a dialog pending** rather than settling it
  (`cli.pretty.js:283320`). §6.3's rule to answer everything at once must not be read as
  licence to answer a *declared* dialog with an error and consider it closed.
- **`background_tasks`'s disabled reply is an error, not a success body**, so the banner is
  raised off the control-error path, not off a `{backgrounded: false}`. The two arms of item
  61 are read from two different places and a card that read only the success body would never
  raise the banner.
- **`suppress_always_allow_rule`, `default_to_no` and `requires_user_interaction` are omitted
  when false** (`|| void 0`, `cli.pretty.js:283001`), so `nil` means false and the card must
  not treat absence as unknown.
- **`annotations` is real**, keyed by question text like `answers`, values
  `{preview?, notes?}`. `Fixtures/ask-user-question` records an answer with `answers` and *no*
  `annotations`, which is legal — the key is optional — so G1b asserts the fixture's recorded
  shape and asserts `annotations` only where the card produces one.
- **`AskUserQuestion` has an extended variant** behind `extendedQuestionsEnabled()`, adding
  per-question `kind: "choice" | "text" | "number"`, `placeholder`, `min`/`max`/`step`/
  `defaultValue`/`unit`, and a top-level `title` (`cli.pretty.js:758385–758461`). The card
  honours `kind` when present and falls back to the choice rendering when absent; an
  unrecognised `kind` renders a text field. This is a widening §8.4 does not mention and would
  otherwise have shipped as a broken card the day the flag turns on.

## `[parent-impact]` — X4 and X5 leave `HostSignal` unreachable

**Where.** Root §17.5's X4 makes the timeline model C3's and names the overlay; X5 makes
`perform(.answer)` the one answer path and returns a `ChannelState`. Neither says who tells
the reducer that an answer was sent, and at `5e24f1a` nobody does: `HostSignal` is constructed
in no source file, and `StreamIngestion` has no member that takes one. Five host facts —
`promptSent`, `decisionAnswered`, `rewound`, `processReplaced`, `relocated` — are modelled,
reduced (`Reduce/WireReducer.swift:74–95`) and unreachable. Only `relocated` has an alternate
route, through `StreamIngestion.relocated(mainPath:)`.

**Why it is the parent's.** It spans two contracts and three children. C6.3's cards cannot
leave `pending`; C6.2's turn attribution and item 13 need `promptSent` and `rewound`; C3 owns
the type and C4 owns the action that should raise it. No leaf can close it inside its fence.

**Recommended fix.** A C3 corrective on `main`, the shape the composite's Risks section
already uses for tracker 74 and 77: `StreamIngestion` gains
`public func signal(_ HostSignal) async -> Effect`, forwarding to `WireReducer.apply(_:at:)`
and publishing the resulting changes through the same effects stream every other mutation
uses; the app raises it after a successful `perform(.answer)`. X4 gains one sentence naming
the delivery path; X5 gains one naming the app as the raiser.

## Surprises & Discoveries

- `HostSignal` is fully modelled, fully reduced, and constructed nowhere. It was found by
  asking who moves a `DecisionItem` out of `pending` — a question the composite's Y2 answers
  ("C3's state") in a way that reads as settled and is not.
- `DecisionItem.payload` is the *whole* raw request, which is what makes one card component
  for two hosts cheap: the component needs no second source and no FleetKit addition.
- `PanelHostModel.run` already throws `noPaneRunner`, so item 47's degraded path needed no new
  seam — the composite's fallback was already implementable at the pin.
- **The two permission fixtures' only suggestion is a `setMode` at `session`.** §8.4's
  *Always allow* sentence describes a destination choice that the common case does not have,
  and a picker built from the prose would have offered to write a permission *mode* into a
  settings file. Found by reading a fixture rather than the table it is supposed to witness.
- **`.exited` rewrites pending decisions to `.inert`**, which this document's own first draft
  denied. The draft's reading was taken from the C3 spec's prose ("the overlay is kept for
  display and marked stale"), which is true and incomplete. Two sentences of code settled it.
- **Elicitation has a `url` mode**, and a form-only card would have rendered an empty form and
  dropped the URL. Nothing in §8.4, §6.4 or the fixtures says so; only the bundle does — and
  there is no elicitation fixture at all, so no gate would have caught it either.
- **`AskUserQuestion` has a flagged extended variant** with `kind`, `placeholder` and numeric
  bounds. A card built to the base schema breaks the day the flag turns on, silently.
- **The dialog deadline is five minutes and configurable** — §8.4 refers to "its dialog
  deadline" as though it were a constant of the protocol rather than a setting.
- **`make synthetic` would destroy the evidence for G1f.** Both dialog fixtures are synthetic
  and rebuilding them replaces the signed review block; the command is one word away from a
  plausible-looking "refresh the fixtures" step.
