## Purpose / Big Picture

After this leaf, a Swift module named `SourceControlCore` inside the `Workbench` package
can answer, for any git repository on the machine and without any user interface existing
yet: what the commit graph looks like with each commit placed in a drawable lane, what the
working tree currently differs by, which files a commit or a working tree changed, and what
pull requests, checks and issues GitHub holds for the repository. It answers by running the
user's own `git` and `gh` binaries — the ones the login shell's `PATH` resolves — in the
repository directory with the environment afleet captured at launch, so hooks, credential
helpers, worktrees and `gh`'s stored token all behave exactly as they do in the user's
terminal.

Nothing here draws anything. The panel that draws it is C7.7 and lands two waves later;
this leaf's entire observable surface is `swift test --package-path Workbench`. That is a
deliberate cut by the composite (its "two axes, seven leaves"): the core is testable now
against real repositories the tests build themselves, while the panel waits for the panel
host.

How to see it working, from a clean checkout of this branch:

    cd /Users/new/Developer/GitHub/afleet-c7/scm-core
    swift test --package-path Workbench

Expect every suite to pass. The `SourceControlCoreTests` suite builds real git
repositories in temporary directories with the `git` binary — a repository with a merge, one
with an octopus merge, one with a detached tag, one with a dirty working tree — parses the
output of real `git` invocations, asserts the exact lanes, and decodes committed `gh` JSON
samples. One test, the live GitHub check (G3), talks to the network and skips itself with a
named reason when `gh` is not logged in or the network is unavailable; the rest never leave
the machine.

**Terms of art, defined once.**

- *Resolved environment*: the environment variables afleet captured once at launch by
  running the user's login shell (`$SHELL -l -i -c 'env -0'`). It is carried as
  `AfleetCore.ResolvedEnvironment` (`variables: [String: String]`, `shell`, `capturedAt`,
  `mode`, and a computed `path: [String]` splitting `PATH` on `:`). Root-spec contract
  **X11** says every `git`, `gh`, shell and `claude` process afleet spawns runs with it. This
  leaf takes it as a plain `[String: String]`, because that is what the panel host hands a
  panel and it keeps `SourceControlCore` free of any opinion about where it came from.
- *Lane*: a horizontal slot, numbered from zero, in which a commit's dot is drawn in a
  commit-graph view; the vertical lines connecting dots are *edges*. Assigning lanes is the
  work of turning a list of commits and their parents into something drawable.
- *Topological order*: `git log --topo-order` guarantees that no commit is listed before all
  of its children have been listed, and that commits on different lines of history are not
  intermixed. Lane assignment depends on that guarantee and on nothing about how git draws.
- *Porcelain v2*: `git status --porcelain=v2`, a stable, documented, machine-readable
  listing of the working tree's differences from the index and from `HEAD`.
- *`gh`*: GitHub's official command-line client. `gh <command> --json <fields>` prints a JSON
  document with exactly the requested fields. afleet never holds a GitHub token; `gh` does.
- *Panel-local error state*: root spec §10 — "Git and PTY failures: panel-local error states
  that never take the channel down". A `git` failure becomes a value the panel renders in
  its own area; it never propagates as an exception into the conversation.

## Residue, grilled

The composite's C7.3 section is a *brief*, not a plan: it fixes the acceptance and the data
types and leaves the mechanics open. Everything the brief leaves open is listed here with
the answer this ledger commits to. Routine mechanical questions are decided here and marked
*decided*; nothing in this list was escalated, because nothing in it is a product, taste or
scope decision — the scope is binding from root spec §9.2 and unambiguous.

**Q1. Which process layer runs `git` and `gh`, given X1?** *Decided (D1):* a small runner
written inside `SourceControlCore`, modelled on C2's `FoundationProcessRunner` but not
importing it, setting `Process.currentDirectoryURL` directly. The duplication is real and is
filed as tech debt (entry 112), not hidden.

**Q2. How is a binary "resolved through the resolved environment"?** *Decided (D2):* by
scanning the `PATH` entries of the environment dictionary the caller passed, in order, for
an executable regular file of that name; absolute entries only; no fallback to `/usr/bin`,
`/opt/homebrew/bin` or `Process`'s own environment, ever. A different binary would mean
different hooks and credential helpers (the composite's own risk bullet). Failure is the
typed error `.binaryNotFound(tool:)`.

**Q3. Is a non-zero exit an error?** *Decided (D3):* not at the runner. The runner returns
stdout, stderr, exit code and a timed-out flag and throws only when it could not run the
process at all. Each command wrapper declares which exit codes it accepts, because the
composite's own discovery is that `gh pr checks` exits **8** while checks are pending and
that is not a failure. A wrapper's unacceptable exit becomes `.commandFailed`, a value the
panel renders (§10), never an exception crossing into the channel.

**Q4. What timeout?** *Decided (D4):* per-call, defaulted per command class —
`GitCommands` reads at 30 s, `GhCommands` network calls at 30 s — as named constants
carrying their rationale, overridable by the caller. C7.7 may retune with a Revision Note;
the numbers are advisory under W7 ("refresh cadence and pagination: advisory").

**Q5. `git log` over a large repository — how much is read?** *Decided (D5):* a window.
`GitLog.commits(root:limit:skip:)` adds `-n <limit>` (default 2,000) and `--skip <n>` to the
W7 format string. Lane assignment therefore must tolerate a parent hash that is not in the
window: the edge to such a parent is marked truncated. ~~Such a parent terminates its
lane.~~ **Corrected at R2 (2026-09-08, D38):** it does *not* terminate the lane. The parent
is never read, so its reservation is never released; the lane stays occupied to the bottom
of the window and repeats a truncated straight-down edge on every row below the one that
named it. That is the better rendering — a line leaving a viewport does continue — so the
wording was amended and the code left alone. That tolerance is required by windowing, so it
is tested, not assumed.

**Q6. Does the working-tree row always exist?** *Decided (D6):* only when the working tree
is not clean, matching the composite's G1 wording ("a repository with the working tree dirty
(row zero present)"). When present it is row 0, lane 0, with a single edge down to `HEAD`'s
row.

**Q7. `-z` or not, for `status` and `diff`?** *Decided (D7):* `-z` everywhere a path is
printed. Without it git C-quotes paths containing spaces, quotes, backslashes or non-ASCII
bytes, and the parser would have to implement git's quoting rules to be correct for a
perfectly ordinary macOS path. With `-z` the fields are NUL-separated and paths are raw
bytes. The `git log` call keeps W7's exact `%x1f`/`%x1e` format, which has the same property
for the fields it prints.

**Q8. What does "the parser for `git diff`" mean, concretely?** *Decided (D8):* the
**changed-file list**, not a unified-diff hunk parser. The panel renders diffs through
Monaco's diff editor (contract W4), which takes two whole texts — original and modified —
not a patch. So what C7.7 needs from this leaf is (a) the list of changed files with their
status, rename information and line counts, and (b) a way to fetch either side's text.
Both are provided: `GitDiff.changes(root:base:)` over `DiffRef.Base`, and
`GitDiff.blob(root:rev:path:)` / working-tree read. A unified-diff parser is explicitly not
built; if C7.7 later wants an inline patch view it is a Revision Note, and the case that
would need it (binary files) is flagged rather than diffed.

**Q9. Which `gh` fields, and how strictly are they decoded?** *Decided (D9):* fixed subsets
of the fields the composite's Grounding Baseline verified against `cli.github.com/manual`;
pull-request checks come from `gh pr checks --json`, **not** from `statusCheckRollup` on the
PR object, because the former is a documented flat shape and the latter is a nested union
this leaf has no evidence for. Fields that are always present decode as non-optional, so a
missing key is a decode error — otherwise G3 could not fail. Fields `gh` documents as
possibly empty (`reviewDecision`, `mergeStateStatus`, `mergeable`) decode as a required
`String` mapped into an enum with an `.unknown(String)` case, so an unfamiliar value is
carried rather than fatal. Samples live as committed JSON files under
`Workbench/Tests/SourceControlCoreTests/Samples/`, authored with real field names and
invented values, loaded through a `resources: [.copy("Samples")]` clause inside this leaf's
manifest fence.

**Q10. How is G3 kept out of the offline run?** *Decided (D10):* the live test first runs
`gh auth status`. In `gh` 2.96 that verb validates the token against the API, so it exits
non-zero both when the user is logged out and when there is no network — exactly the two
cases in which G3 must not run. Non-zero exit produces `XCTSkip` with a named reason, which
the suite reports as a skip and this ledger reports as a count. The parent's acceptance item
6 ("passes from a clean checkout with no network") therefore holds. G3 never prompts for a
login and never writes to `gh`'s configuration.

**Q11. Does this leaf log anything?** *Decided (D11):* no. Root spec §11's table of files
afleet owns has four log domains — `diagnostics.log`, `fleet.log`, `timeline.log`,
`app.log` — and no Workbench domain exists. Inventing a fifth here would be a packaging
decision this leaf does not own. Every failure is a typed, `Sendable` value the panel
renders. Filed as tracker entry 113 so C7.7 or C5 can open the domain deliberately.

**Q12. Who proves that `SourceControlCore` does not import `ClaudeWire`?** *Decided (D12):*
this leaf adds its own `ImportGraphTests` over `Workbench/Sources/SourceControlCore`, in the
same shape as C5's existing test over `Sources/PanelHostAPI`, because C5 owns that file and
its fence. A package-wide walk covering every Workbench module belongs to whichever leaf
owns the manifest; a recommendation to name that owner is in *Parent revisions* below.

**Q13. Where does the repository root come from?** *Decided (D13):* the panel gives a
channel cwd, which may be any subdirectory. `GitCommands.repositoryRoot(cwd:)` runs
`git rev-parse --show-toplevel` and returns a typed `.notARepository` when git says so, which
is the panel's empty state. Every other command runs at that root.

**Q14. Do fixture repositories inherit the machine's git configuration?** *Decided (D14):*
no, and this is a correctness requirement rather than hygiene. A developer's global
`~/.gitconfig` can set `init.defaultBranch`, `commit.gpgsign`, `log.date`, `diff.renames`,
`core.hooksPath` or a merge driver, any of which would change the bytes a fixture test
parses and make the suite pass or fail by accident of the machine. Every fixture repository
therefore runs `git` with `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`,
`GIT_TERMINAL_PROMPT=0`, `HOME` pointed at the temporary tree, fixed `GIT_AUTHOR_DATE` and
`GIT_COMMITTER_DATE`, and an explicit invented `user.name` / `user.email` set per repository
(never read from the machine, per the dispatch brief and §11). The initial branch is set
with `-b main` at `init`.

**Q15. Is a temporary directory safe to write in?** *Decided (D15):* yes with the check
tracker entry 24 already prescribes and C5's `TempTree` already implements: canonicalise
`FileManager.default.temporaryDirectory`, and throw a fixed `XCTSkip` if it resolves inside
`~/.claude`, `$CLAUDE_CONFIG_DIR` or `/tmp/afleet-fixtures/config-home`. Root spec X9 —
nothing afleet ships or tests writes under a Claude Code config home — is binding and
absolute.

The interfaces that must exist at the end of this milestone:

    public enum Tool: String, Sendable, CaseIterable { case git, gh }

    public struct ToolOutput: Sendable, Equatable {
        public var stdout: Data
        public var stderr: Data
        public var exitCode: Int32
        public var timedOut: Bool
        public var stdoutText: String          // UTF-8, invalid bytes replaced
        public var stderrTail: String          // last 512 bytes, UTF-8 lossy
    }

    public enum ToolError: Error, Equatable, Sendable {
        case binaryNotFound(tool: Tool)
        case spawnFailed(tool: Tool, message: String)
        case timedOut(tool: Tool, afterMs: Int)
        case commandFailed(tool: Tool, exitCode: Int32, stderrTail: String)
        case notARepository
        case decodeFailed(subject: String, message: String)
    }

    public protocol ToolRunning: Sendable {
        func run(_ tool: Tool, arguments: [String], cwd: URL,
                 environment: [String: String], timeout: Duration) async throws -> ToolOutput
    }

    public struct ToolRunner: ToolRunning {
        public init()
        public static func resolve(_ tool: Tool, in environment: [String: String]) -> URL?
    }

`ToolRunner.run` resolves the binary with `resolve`, throws `.binaryNotFound` when it cannot,
constructs a `Process` with `executableURL` set to the resolved path, `arguments` as given,
`environment` set to **exactly** the dictionary passed (never merged with the parent
process's), `currentDirectoryURL` set to `cwd`, `standardInput` at `FileHandle.nullDevice`,
and pipes for stdout and stderr. Exit is learned from `terminationHandler` and never from
`waitUntilExit()`; both pipes are drained with non-blocking `DispatchSourceRead`s on one
serial queue; settlement is keyed to the child's exit rather than to end-of-file on the
pipes; the timeout fires on that same queue, sets `timedOut`, terminates, and after a
500 ms grace sends `SIGKILL` and settles anyway. Each of those five sentences is a defect
C2 already paid for and documented in `ClaudeWire/Sources/WireEnvironment/ProcessRunner.swift`;
read that file before writing this one and carry its reasoning across in comments, because
the reasons do not survive as code.

`resolve` splits `environment["PATH"]` on `:`, drops empty components and any component
that is not an absolute path, and returns the first `<component>/<tool>` for which
`FileManager.isExecutableFile(atPath:)` is true. No other candidate is ever considered.

`TempTree` is C5's shape, re-created here because a test target cannot import another
target's test bundle: canonicalised root under `FileManager.default.temporaryDirectory`,
`XCTSkip` when the root resolves inside a config home (Q15), `file(_:_:)` and
`directory(_:)` helpers, and removal on teardown.

`GitFixture` builds repositories: `init(_ tree: TempTree) throws`, a `run(_ args: [String])`
that invokes the resolved `git` with the hermetic environment of Q14, and the shorthands
`commit(message:files:)`, `branch(_:)`, `tag(_:)`, `merge(_ refs: [String], message:)` and
`detach(_:)`. It is used by every later milestone.

Acceptance for milestone 1, which is the composite's **gate G2**:

1. A test spawns `git --version` through `ToolRunner` in a temporary directory and asserts
   the exit code is 0 and stdout begins `git version`.
2. A test asserts the runner passes the cwd it was given: it runs `git rev-parse
   --show-toplevel` in a fixture repository's subdirectory and compares the result to the
   fixture's own root — as a boolean with a written message, never `XCTAssertEqual` over two
   runtime paths, because `XCTAssertEqual` prints both operands and a temporary path contains
   the machine account's hash (root spec §6.3 and §11 reach into assertion choice).
3. A test asserts the runner passes exactly the environment it was given, **by names**:
   it runs `/usr/bin/env`-free — specifically `git var GIT_AUTHOR_IDENT` with an invented
   `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL` in the passed environment — and asserts the invented
   name appears in the output, then runs the same command with a marker variable set in the
   *test process's* environment but absent from the passed dictionary and asserts, by name,
   that git reports no such value. No environment is ever dumped into an assertion message.
4. A test asserts `.binaryNotFound(tool: .gh)` is thrown when the passed environment's `PATH`
   contains only a directory that holds no `gh`.
5. A test asserts the timeout against a child that provably blocks. The timeout is a
   property of the process layer rather than of `git`, so `ToolRunner` exposes its
   executable-taking form as `internal func run(executable: URL, …)` — the public
   `run(_ tool:…)` is a thin wrapper that resolves and calls it — and the test uses
   `@testable import SourceControlCore` with `/bin/sleep 30` and a 300 ms budget. Assert
   `timedOut == true`, that the call returns inside the budget plus the 500 ms grace plus a
   margin, and that the child is gone afterwards. (If the internal seam is judged unwanted at
   review R1, the fallback with no new seam is
   `git -c core.editor='/bin/sleep 30' commit --allow-empty` in a fixture repository, which
   blocks in git's own editor step; it is slower and noisier, which is why it is second.)
6. `.commandFailed` is *not* produced by the runner: a test asserts that `git rev-parse
   --verify nonexistent-ref` returns a non-zero `ToolOutput` rather than throwing.
7. `ImportGraphTests` walks `Workbench/Sources/SourceControlCore`, asserts the walk found
   Swift files (a floor: an empty walk is a subset of anything), asserts every imported
   module is in `{Foundation, AfleetCore}`, and asserts `AfleetCore` is among them (a second
   floor: a grep that matched nothing must not pass).

### Milestone 2 — `git log` parsing: `GitCommit` and `GitRef`

At the end of this milestone, a real repository's history is a `[GitCommit]`.

Files: `Workbench/Sources/SourceControlCore/GitCommit.swift`,
`Workbench/Sources/SourceControlCore/GitLog.swift`,
`Workbench/Tests/SourceControlCoreTests/GitLogTests.swift`.

Interfaces:

    public struct GitRef: Hashable, Sendable {
        public enum Kind: Hashable, Sendable { case head, branch, remoteBranch(remote: String), tag }
        public var kind: Kind
        public var name: String                // "main", "v0.1", "HEAD"; for remoteBranch, the branch part
    }

    public struct GitCommit: Hashable, Sendable, Identifiable {
        public var hash: String
        public var parents: [String]
        public var refs: [GitRef]
        public var authorName: String
        public var authorTimestamp: Date
        public var subject: String
        public var id: String { hash }
    }

    public enum GitLog {
        public static let format = "%H%x1f%P%x1f%D%x1f%an%x1f%at%x1f%s%x1e"
        public static func parse(_ text: String) throws -> [GitCommit]
        public static func commits(root: URL, environment: [String: String],
                                   runner: any ToolRunning, limit: Int = 2000, skip: Int = 0)
            async throws -> [GitCommit]
    }

The command is exactly W7's, plus the window: `git log --topo-order --all --parents
--format=<format> -n <limit> --skip <skip>`. `--parents` is in W7's command line and is
redundant with `%P` in the format; it is kept because W7 is binding and it costs nothing.

Parsing: split on `\u{1e}`, trim leading newlines from each record (git emits one after each
record separator), drop an empty trailing record, split each record on `\u{1f}` into exactly
six fields, and fail with `.decodeFailed` on any record with a different field count rather
than skipping it — a parser that silently skips the record the test exists to compare is
root spec §17.7's seventh named instance and must not be rebuilt here. `%D` is decorations,
comma-and-space separated: `HEAD -> main` yields both a `.head` and a `.branch`;
`tag: v0.1` yields a `.tag`; `origin/main` yields `.remoteBranch(remote: "origin")`; a bare
`HEAD` (detached) yields `.head` alone. `%at` is a Unix timestamp in seconds.

Acceptance: a fixture repository with two commits, a tag, a branch and a detached `HEAD`
parses to the exact expected hashes, parent lists, ref sets and subjects; the field-count
guard is demonstrated by feeding a truncated record and asserting the thrown error; the
subject of a commit whose message contains a `|`, a tab and a non-ASCII character survives
byte-for-byte. Failing-first: the tests are written before `GitLog` exists and the
transcript recorded.

<name|(detached)>`, `# branch.upstream <name>`, `# branch.ab +<n> -<n>`; ordinary entries
`1 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <path>`; rename and copy entries `2 <XY> <sub> <mH>
<mI> <mW> <hH> <hI> <X><score> <path>` followed by a **separate NUL-terminated field**
holding the original path; untracked `? <path>`; ignored `! <path>`; unmerged `u …`. `X` is
the index status and `Y` the working-tree status; `.` means unchanged.

Acceptance, which is half of the composite's **G1**: one fixture repository is put into a
state carrying all five of modified, added, deleted, renamed and untracked simultaneously,
and the parse is asserted entry by entry as a set comparison in both directions with a
non-emptiness floor. The rename entry's `from` path is asserted, because that is the field
whose position the probe had to establish. A clean repository parses to `isClean == true`
with a branch name. A detached `HEAD` parses to `branch == nil`. Failing-first as before.

### Milestone 4 — lane assignment (the core of gate G1)

The algorithm, stated so it can be implemented without inventing anything. Keep an array
`lanes: [String?]` where `lanes[i]` is the commit hash that lane `i` is currently reserved
for, or `nil` when the lane is free. Walk the commits in the order `git log --topo-order`
gave them. For each commit: its lane is the leftmost lane reserved for its hash; if no lane
is reserved for it — a branch tip, or a commit reachable only from a tag — it takes the
leftmost free lane, appending a new lane when none is free. Free that lane's reservation,
then release every *other* lane also reserved for this hash (a commit reached by two
children closes the extra lanes at that row). Now place the parents: the first parent
reserves the commit's own lane; each further parent reserves the leftmost free lane, unless
some lane already holds a reservation for that parent's hash, in which case no new lane is
taken and the edge points at the existing one. ~~Edges leaving the row are, for every lane
reserved after the update, an edge from the lane the commit or the pass-through occupied to
the lane the reservation now sits in~~ **Corrected at R3 (2026-09-08, D43):** one edge per
*lane* cannot draw the graph. The edges leaving a row are the **union** of one pass-through
`i → i` for every lane holding a reservation before this row's parents are assigned, and one
`lane → p` for every lane this commit's parents occupy — several edges may therefore arrive
in the same destination lane, and where a merge reaches into a lane another child already
reserved both are drawn. In the same correction, the released duplicate reservations at a
shared parent's row redirect the edges arriving in them into the lane the parent was read at,
so the lines converge on the commit rather than beside it. An edge whose target hash is not
among the commits in the window is marked `truncated`. `laneCount` is the high-water mark of
`lanes.count`.

When `workingTreeIsDirty` is true a `.workingTree` row is prepended at lane 0 ~~with one edge
to the lane of the row carrying a `.head` ref~~; the row makes no other claim. **Corrected at
R3 (2026-09-08, D44):** a single prepended edge does not reach a `HEAD` that is not the row
below, because an `Edge` connects adjacent rows only. The row is instead placed **before** the
loop and *reserves* lane 0 for `HEAD`'s hash, the same rule 3 a commit follows for its first
parent, so the lane is carried down through every intervening row and `HEAD` is read in it. ~~That commit is
`HEAD` because `--topo-order` lists it first among reachable tips.~~ **Corrected at R2
(2026-09-08, D39):** it is not. `--topo-order --all` orders the tips by date, so a tag-only
commit newer than `HEAD` is listed ahead of it (measured on `git` 2.55.0), and the edge must
find `HEAD`'s row rather than row zero. Row zero is the fallback only when `HEAD` fell
outside the window.

Acceptance — the composite's **G1** in full, on four fixture repositories the test builds:

1. **A merge**: `main` and `feature` diverge by one commit each and are merged with
   `--no-ff`. Assert that at least two distinct lanes are occupied, that the merge commit has
   two parents, that each parent sits in a different lane, and that the merge row carries an
   edge into each. Assert the exact lane numbers, not that "some lanes exist" — the
   composite's own risk bullet.
2. **An octopus merge**: three branches merged in one commit. Assert three parents, three
   distinct parent lanes and three edges from the merge row.
3. **A detached tag**: a commit on no branch, reachable only through a tag, produced by
   committing on a detached `HEAD`, tagging, and returning to `main`. Assert the commit
   appears (which is what `--all` buys), that it opens its own lane, and that its `refs`
   carry the tag.
4. **A dirty working tree**: row 0 is `.workingTree` at lane 0 with an edge to `HEAD`'s row;
   the same repository clean has no such row. Both directions are asserted, because a row
   that always appears would pass the first assertion alone.

Additionally: a window test builds a repository with more commits than the limit, reads with
`limit: 3`, and asserts that the oldest row's edge to its unread parent is `truncated`.

Failing-first: every one of these is written before `LaneAssignment` exists. The
discriminating check the reviewer applies is not "does it pass" but "what would this
assertion have to see in order to fail" — an assertion on lane *counts* alone passes for a
wrong assignment, so each test names the lane of each commit.

**Review point R2** after this milestone: an independent reviewer checks the four lane tests
against the algorithm for exactly that property, and checks that a deliberately wrong
assignment (swap the first-parent rule for "always take a free lane") makes at least two of
them fail. That mutation is run and its transcript recorded.

`DiffRef` is `AfleetCore`'s type from root spec §9.6 and its `Base` has three cases, mapped
here and nowhere else: `.workingTreeAgainstHEAD` runs `git diff HEAD`; `.commit(h)` runs
`git diff <h>` (the working tree against that commit); `.commitAgainstParent(h)` runs
`git show --format= --first-parent <h>`, which is correct for a root commit where `<h>^` does
not exist. ~~It also follows git's own convention of showing nothing for a merge commit.~~
**Corrected at R3 (2026-09-08, D41):** `git show`'s default is not usable for a merge commit
at all. Measured on `git` 2.55.0: for an ordinary merge `--name-status` prints nothing while
`--numstat` prints a record per path, so the join of the two listings throws; and for a merge
whose tree differs from both parents — a resolved conflict — the default is git's *combined*
diff, whose status field carries one letter per parent (`MM`), which the name-status parser
rejects. Selecting an ordinary merge row therefore failed outright. `--first-parent` is
passed on **both** invocations: it gives the two listings the same shape, never produces a
combined status code, and answers the question a changed-file panel is asking.

Two invocations per query, not one: the probe established that `--name-status` and
`--numstat` given together do **not** both print — the last one wins. So the status and
rename information come from one `-z --name-status --find-renames` call and the line counts
from one `-z --numstat --find-renames` call, joined by path. Measured `-z` shapes: name-status
is `<status>\0<path>\0`, and for a rename `R<score>\0<old>\0<new>\0`; numstat is
`<adds>\t<dels>\t<path>\0`, and for a rename `<adds>\t<dels>\t\0<old>\0<new>\0` — the path
field is *empty* and two path fields follow. A binary file has `-` for both counts, which is
where `isBinary` comes from.

Acceptance: a fixture repository with, in one commit, an added file, a modified file, a
deleted file, a renamed file and a binary file, asserted as a set in both directions with a
non-emptiness floor; the rename's `from` and score asserted; the binary file's counts
asserted nil with `isBinary` true; a path containing a space and a non-ASCII character
surviving intact (which is what `-z` is for and would fail under C-quoting); each of the
three `DiffRef.Base` cases exercised, including `.commitAgainstParent` on the root commit.
`blob` round-trips a file's bytes at a revision. Failing-first as before.

## Surprises & Discoveries

- Observation (milestone 6, `gh` 2.96.0): `gh pr checks --json` never emits `null` and never
  omits a key. An absent link, workflow, event or description arrives as `""`, and an absent
  timestamp as Go's zero instant `0001-01-01T00:00:00Z`. The obvious model — `String?` decoded
  with `decodeIfPresent` — therefore yields `Optional("")` rather than `nil`, and a `URL?` over
  the empty string *throws*, so the naive shape would fail on the first status context that has
  no workflow.
  Evidence: `pkg/cmd/pr/checks/aggregate.go` declares `check` with `Link`, `Event`, `Workflow`,
  `Description` as `string` and `StartedAt`, `CompletedAt` as `time.Time`; `output.go` branches
  on `o.StartedAt.IsZero()`. Confirmed live over 145 check records from eight open pull requests
  on `cli/cli`: 5 of the 145 carried `"workflow": ""`, none carried a `null`, and every record
  carried all nine requested keys. `CheckRun` maps both absent shapes to `nil` while keeping the
  keys required (D36).

- Observation: **exit code 8 could not be reproduced live** in the time this milestone had.
  Twenty-six open pull requests across four large repositories were polled and every one of them
  had already settled, so `gh pr checks` exited 0 each time. The 8 is documented twice on this
  machine's `gh` — `gh pr checks --help` prints "Additional exit codes: 8: Checks pending" — and
  is implemented as `cmdutil.PendingError` when `counts.Pending > 0` in
  `pkg/cmd/pr/checks/checks.go`, with the checks printed before the error is returned. The
  acceptance is therefore built on the documentation plus the source and is asserted with a stub
  runner, not with a live pending check. Worth one live confirmation whenever a pending run is at
  hand.

- Observation: `gh pr list --json` returns each requested field at the top level and nothing else,
  but the *nested* objects carry more than the models read: an `author` arrives with `id`,
  `is_bot`, `login` and `name`, and a label with `id`, `name`, `description` and `color`. Extra
  keys inside a nested object are ignored by `Decodable`, which is why `GitHubUser` can read
  `login` alone. The samples reproduce the extra keys so that the tolerance is exercised rather
  than assumed.

- Observation: `--name-status` and `--numstat` given to the same `git show`/`git diff` do
  **not** both print. The last option wins, so the changed-file list needs two invocations.
  This was going to be one call in the obvious design.
  Evidence, `git show --format= --numstat --name-status -z --find-renames HEAD | cat -v`:

      M^@a.txt^@R100^@sp ace.txt^@renamed.txt^@

  No numstat section appears at all.

- Observation: under `-z`, a **rename in `--numstat`** puts an *empty* path field between the
  counts and the two paths, so a parser that reads one path per record silently mis-joins
  every rename.
  Evidence, `git show --format= --numstat -z --find-renames HEAD | cat -v` on a commit that
  modifies `a.txt`, renames a binary `b.bin` to `c.bin` and adds `n.txt`:

      1	1	a.txt^@-	-	^@b.bin^@c.bin^@1	0	n.txt^@

  The `^@` immediately after `-\t-\t` is the empty path field; `-` for both counts is how a
  binary file is reported.

- Observation: in `git status --porcelain=v2 -z`, a rename entry's **new** path comes first
  and the original path follows as its own NUL-terminated field.
  Evidence, a tree with a modification, a staged add, a staged rename, a deletion and an
  untracked file:

      # branch.oid <oid>^@# branch.head main^@1 .M N... … a.txt^@1 A. N... … added.txt^@2 R. N... … R100 d.bin^@c.bin^@1 .D N... … n.txt^@? untracked.txt^@

- Observation: `%D` on a detached `HEAD` that also carries a tag and sits on a branch prints
  `HEAD, tag: v9, main` — three decorations, comma-and-space separated, with the tag prefixed
  and `HEAD` bare rather than `HEAD -> …`.
  Evidence: `git log -1 --format='%D'` after `git checkout --detach`.

- Observation (milestone 1): fully fixed `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` across every
  commit in a fixture — the literal reading of D14 — is not merely uninteresting, it is wrong.
  Two commits with the same tree, message, parent, identity *and* timestamps are one git object,
  not two: the second `git commit` produces the hash the first did. A merge fixture with an empty
  commit on each of two branches would then have both branches pointing at the same commit and no
  divergence to lane. `GitFixture` therefore holds the identity and the configuration fixed and
  advances the timestamp by one second per commit from a fixed base, which keeps every byte
  deterministic while keeping the objects distinct. Evidence: the design of
  `GitFixture.commitCount`; the failure it prevents would have surfaced only at milestone 4.

- Observation (milestone 1): the removed-timeout mutation does not hang the suite forever, it
  hangs it for exactly as long as the child lives — 31.6 s for `/bin/sleep 31.415926` — and then
  fails two assertions. That is the desirable shape: a mutation that hung indefinitely would have
  had to be killed by hand and would have produced no transcript.

- Observation: `gh auth status` in 2.96 validates the token against the API, so it fails both
  when logged out and when offline. That makes it the exact gate G3 needs, and it is why G3
  can live in the default suite without breaking the parent's offline-clean-checkout clause.

- Observation (milestone 3): the porcelain-v2 branch headers say "absent" with a **literal
  string**, not by omitting the header. An unborn repository prints `# branch.oid (initial)`
  and a detached `HEAD` prints `# branch.head (detached)`; both headers are always present.
  A parser that took "no commit yet" or "detached" to mean a missing header would carry the
  literal `(initial)` through as an object name and the literal `(detached)` through as a
  branch name — both plausible enough to survive a careless test. Measured on `git` 2.55.0,
  `LC_ALL=C`, global and system configuration disabled:

      # branch.oid (initial)^@# branch.head main^@
      # branch.oid <oid>^@# branch.head (detached)^@

- Observation (milestone 3): an **unmerged** record is three fields wider than an ordinary
  one — `u <XY> <sub> <m1> <m2> <m3> <mW> <h1> <h2> <h3> <path>`, ten space-separated fields
  before the path against an ordinary entry's eight — so a parser that split it with the
  ordinary widths would take a *mode* as the path and report a file named `100644`. Measured
  on `git` 2.55.0 during a conflicting merge:

      # branch.oid <oid>^@# branch.head main^@u UU N... 100644 100644 100644 100644 <h1> <h2> <h3> f.txt^@

- Observation (milestone 3, about probing rather than about git): `git`'s *porcelain* output
  is not localised, but its diagnostics are, and this machine's `git` speaks Korean. A probe
  that reads a subcommand's usage or error text — as the first milestone-3 probe did, after
  passing `-q` to `git add`, which does not accept it — is unreadable and can be mistaken for
  a shape finding. Every probe in this leaf now runs under `LC_ALL=C`. Fixture *tests* are
  unaffected: they assert on exit codes and on porcelain bytes, never on git's prose.

- Observation (milestone 2): a clone's `%D` carries `origin/HEAD` as a decoration of its own,
  beside `origin/main`. A remote-tracking "branch" named `HEAD` is therefore an ordinary case, not
  a malformed one, and a parser that special-cased the bare token `HEAD` before splitting on the
  slash would have mis-kinded it as the local `HEAD`. Measured with `git` 2.55.0 in a throwaway
  clone, `git log --topo-order --all --parents --format=<W7 format> -n 5 --skip 0 | cat -v`
  (`^_` is `%x1f`, `^^` is `%x1e`), with the hash and identity from the fixture's invented
  identity:

      <hash>^_^_HEAD -> main, tag: v9, origin/main, origin/HEAD^_Wren Alcove^_<seconds>^_first commit^^

  The same transcript confirms the record framing the parser depends on: six `^_`-separated
  fields, a `^^`, and a newline git emits after it.

- Observation (milestone 2): the shortened decoration form is *lossy*, not merely terse.
  `origin/main` and a local branch literally named `origin/main` print identically, so no parser
  of `%D` can be correct about the distinction. This is a property of W7's chosen command line
  rather than of the parser, which is why it became a decision (D22) and a tech-debt entry (115)
  instead of a cleverer regular expression.

- Observation (milestone 2, process): milestones that are *independent by design* are still
  *coupled by the test target*. Milestone 3 was running in parallel in the same worktree, and
  during its own failing-first window its test file did not compile, which made the whole
  `SourceControlCoreTests` module — including this milestone's finished tests — unbuildable.
  Neither worker had done anything wrong. Milestone 2 was therefore verified against a throwaway
  package built under the system temporary directory holding copies of the same sources and the
  same tests and nothing else, and re-verified in the real package once milestone 3 landed; both
  runs report the same 7 passes. Worth knowing before milestones 5 and 6 run in parallel: the
  isolated re-run is cheap, because `SourceControlCore` imports only Foundation and so needs no
  package dependencies at all.

- Observation (milestone 5): both facts this milestone turns on **re-measured identically** on
  `git` 2.55.0 on 2026-09-08, in throwaway repositories with the global and system configuration
  disabled. `--name-status` and `--numstat` given together still print only the last one, and a
  rename's `--numstat -z` record still carries an empty path field before its two paths. The
  measurement was widened from the 2026-09-07 probe to a commit carrying all five change kinds
  at once, and the wider output is what the parsers are written against (NULs as `^@`):

      $ git show --format= --numstat --name-status -z --find-renames HEAD
      M^@a.txt^@M^@b.bin^@D^@d.txt^@R100^@r.txt^@moved.txt^@A^@n.txt^@

      $ git show --format= --numstat -z --find-renames HEAD
      1	0	a.txt^@-	-	b.bin^@0	1	d.txt^@0	0	^@r.txt^@moved.txt^@1	0	n.txt^@

- Observation (milestone 5): the empty numstat path field appears for a **rename or a copy
  only**, not for a binary file as such. A binary that is merely modified prints
  `-\t-\t<path>\0` — one path field, no empty one — and a binary that is *renamed* prints
  `-\t-\t\0<old>\0<new>\0`, both facts at once. The two conditions are independent, which is why
  `isBinary` is derived from the counts and the extra path fields from the empty path field, and
  why `testABinaryRenameJoinsTheEmptyNumstatPathField` exists as the case where they meet.

- Observation (milestone 5): `git diff HEAD --name-status -z` reports a path with an
  **unresolved merge conflict** as an ordinary `M`, never as `U`. Measured on `git` 2.55.0 in a
  repository left mid-conflict by `git merge`. This settles a strictness question rather than a
  parse: `FileChange.Status` needs no unmerged case for the three `DiffRef.Base` commands, so an
  unfamiliar status letter can be rejected outright instead of silently skipped (D32). The
  conflicted-path case that *does* need an unmerged status is `git status --porcelain=v2`, and
  milestone 3 already carries it there.

- Observation (milestone 5, process): the parallel-worker hazard milestone 2 recorded did not
  bite. The test target compiled throughout, so the failing-first transcript and the green run
  were both taken in the real package and the throwaway-package workaround was not needed.

- Observation (milestone 4): the discriminating mutation R2 prescribes — swapping the first-parent
  rule for "always take a free lane" — does **not** move a single commit's lane in two of the four
  fixture repositories. In the detached-tag repository every lane number is identical under the
  mutation and only the *edges* differ; in the dirty-tree and window repositories nothing differs
  at all, because a linear history occupies one lane either way. A test suite that asserted lanes
  alone, exactly as G1's wording invites, would therefore have caught the mutation in two tests
  rather than three, and a suite over the linear fixtures alone would have caught it in none. The
  lane of each commit is a necessary assertion and not a sufficient one; the edges of the row where
  two lines converge on one parent are what actually pin the rule. Evidence: the mutation
  transcript below, where `testACommitReachableOnlyThroughATagAppearsAndOpensItsOwnLane` fails on
  its edge assertion alone while its three lane assertions all hold.

- Observation (milestone 4): the first-parent rule deliberately creates a *duplicate* reservation.
  When a commit's first parent is already reserved in another lane, the rule still reserves the
  commit's own lane for it, so the parent's hash sits in two lanes until its own row releases the
  extras. That reads like a bug and is the shape the graph needs: it is what makes both lines run
  straight down and converge visibly at the shared parent's row, instead of one line jumping
  sideways one row early. The mutation is precisely the "obvious" fix, and it is what moves the
  shared root of the merge fixture from lane 0 to lane 1 and the shared root of the octopus fixture
  from lane 0 to lane 2.

- Observation (milestone 4): `GitFixture` as milestone 1 left it already builds both shapes the
  dispatch expected to need new helpers for. `merge(_ refs:message:)` takes an array, so an octopus
  is `merge(["b1", "b2"], …)`, and `detach`/`tag`/`checkout` compose into the detached-tag sequence.
  The one thing to know is that `branch(_:)` is `checkout -b` from wherever `HEAD` is, so branching
  a second time from `main` is `checkout("main")` then `branch("b2")`. No edit to the shared support
  file was needed, which also removed this milestone's only source of contention with the two
  workers running beside it.

## Decision Log

- **D1.** `SourceControlCore` gets its own process runner rather than reusing C2's.
  Rationale: X1 forbids Workbench from importing `ClaudeWire`, where
  `FoundationProcessRunner` lives, and the prohibition is structural — it is what keeps the
  panel layer from speaking the engine protocol. Moving the runner down into `AfleetCore` was
  rejected because X2 makes `AfleetCore` value types only and C2 owns it; a leaf may not
  re-cut a parent contract. The duplication is filed as tech debt (112) so the next child
  that needs a third copy has a place to argue for extraction instead.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D2.** Binary resolution scans the passed environment's `PATH` and nothing else — no
  `/usr/bin` fallback, no `Process` default, no absolute-path guessing.
  Rationale: the composite's risk list says it outright: a different `git` means different
  hooks and credential helpers, and a silent fallback would make the panel disagree with the
  user's own terminal. Rejected: `/usr/bin/env git`, which resolves through whatever `PATH`
  the *child* sees and hides the failure one level down.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D3.** The runner is exit-code-neutral; command wrappers declare acceptable exits.
  Rationale: `gh pr checks` exits 8 while checks are pending, `git diff --exit-code` uses 1
  as data, and a runner that threw on non-zero would force every wrapper to catch and unwrap.
  §10 wants a panel-local value in either case.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D4.** Timeouts are per call with named per-class defaults (git reads 30 s, `gh` network
  calls 30 s) rather than one constant.
  Rationale: W7 grades refresh cadence and pagination advisory, and the two classes have
  different failure costs; naming them as constants with their reasoning lets C7.7 retune one
  without touching the other. Rejected: a single hard-coded timeout inside the runner, which
  the panel could not adjust.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D5.** `git log` is read in a window (`-n`, `--skip`, default 2,000) and lane assignment
  tolerates parents outside it, marking those edges `truncated`.
  Rationale: `--all` on a large repository is unbounded, the panel draws a viewport, and
  pagination is explicitly advisory under W7. The tolerance is not optional once windowing
  exists, so it is tested rather than assumed.
  **Corrected in place at R2 (2026-09-08), see D38:** this decision was first written as "a
  parent outside the window terminates its lane". It does not. The parent is never read, so
  its reservation is never released and the lane runs to the bottom of the window, emitting a
  truncated straight-down edge on every row below the one that named it. The behaviour is
  right and only the wording was wrong; nothing about the decision itself changes.
  Date/Author: 2026-09-07 / C7.3 executor; corrected 2026-09-08 / C7.3 R2 fix wave.

- **D6.** The working-tree row exists only when the tree is dirty.
  Rationale: the composite's G1 says "a repository with the working tree dirty (row zero
  present)", and a row that always appeared could not fail that assertion. Both directions —
  present when dirty, absent when clean — are asserted.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D7.** Every path-printing git invocation uses `-z`.
  Rationale: without it git C-quotes any path with a space, quote, backslash or non-ASCII
  byte, and the parser would have to reimplement git's quoting to be correct on an ordinary
  macOS path. Rejected: implementing the unquoting, which is a parser with its own defect
  surface for no gain.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D8.** "The `git diff` parser" is the changed-file list plus blob access, not a
  unified-diff hunk parser.
  Rationale: contract W4's Monaco bridge takes `showDiff {original, modified}` — two whole
  texts — so a patch parser would produce something no consumer in C7 reads. Rejected:
  building it speculatively; deferred to a Revision Note if C7.7 ever wants an inline patch
  view.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D9.** PR check status comes from `gh pr checks --json`, not from `statusCheckRollup` on
  the pull-request object; required fields decode non-optionally; samples are authored with
  invented values.
  Rationale: the composite verified the flat `gh pr checks` field list against the manual and
  did not verify the nested rollup's shape, and this leaf takes protocol facts from evidence
  rather than guesses. Optional-everything decoding would make G3 unfalsifiable, which is
  §17.7's binding failure mode. Recorded real `gh` output would publish a real login and
  repository — §11's rule is about the byte's origin, not its directory.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D10.** G3 gates on `gh auth status` exiting zero and skips with a named reason otherwise.
  Rationale: it is simultaneously the login check the composite asks for and the network
  check the parent's offline clause needs, because 2.96's `auth status` validates against the
  API. Rejected: an opt-in environment variable, which would make G3 skip silently on a
  machine that could have run it.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D11.** No diagnostics sink in this leaf; failures are typed values.
  Rationale: §11's table has four log domains and none is Workbench's; opening a fifth is a
  packaging decision this leaf does not own. Filed as tracker entry 113.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D12.** This leaf ships its own `ImportGraphTests` over `Sources/SourceControlCore`
  rather than extending C5's over `Sources/PanelHostAPI`.
  Rationale: W1 fences each leaf to its own region and C5 owns that target and its tests; a
  local walk is inside the fence and composes with the others. The package-wide walk parent
  acceptance item 6 wants has no named owner, which is *Parent revisions* item 1.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D13.** The repository root is discovered with `git rev-parse --show-toplevel` from the
  channel's cwd, and "not a repository" is a typed value.
  Rationale: a channel's cwd is any directory the user opened, commonly a subdirectory; every
  other command in this module runs at the root so that `--all` and status mean what the
  panel shows. §10 wants the not-a-repository case as a panel-local state, not an exception.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D14.** Fixture repositories run git with the global and system configuration disabled,
  `HOME` inside the temporary tree, fixed author and committer dates, and an invented
  identity set per repository.
  Rationale: a developer's `~/.gitconfig` can change `init.defaultBranch`, rename detection,
  signing or hooks, any of which changes the bytes the parsers read — the suite would then
  pass or fail by accident of the machine. It also keeps the author's real identity out of
  every fixture, which the dispatch brief and §11 both require.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D15.** Scratch trees canonicalise the system temporary directory and skip when it
  resolves inside a Claude Code config home.
  Rationale: X9 is absolute — nothing afleet ships or tests writes under `~/.claude` or
  `$CLAUDE_CONFIG_DIR` — and tracker entry 24 already prescribes this guard, which C5's
  `TempTree` implements. A test target cannot import another target's test bundle, so the
  guard is re-created here rather than shared.
  Date/Author: 2026-09-07 / C7.3 executor.

- **D16.** `ToolOutput.stdoutText` and `.stderrTail` are computed views over the stored `Data`,
  and `ToolOutput`'s `Equatable` conformance is over the bytes and the exit facts alone.
  Rationale: the milestone's interface listing writes all six as `var`, which a computed property
  satisfies, and storing two derived strings would let a caller construct a `ToolOutput` whose
  text disagrees with its bytes. Under `-z` (D7) the bytes are the parseable form and the text is
  only for banners and messages.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D17.** The internal executable-taking `run` carries a `tool:` parameter defaulted to `.git`,
  used only to label `.spawnFailed`.
  Rationale: `ToolError`'s spawn case names a `Tool`, and the internal seam exists precisely to
  run a child that is not a `Tool` (`/bin/sleep`, `/usr/bin/pgrep`). A default keeps the test's
  call site exactly the shape the milestone specifies while the public wrapper still attributes
  its own failures correctly. Rejected: making the case's tool optional, which would widen a
  public error type for a test-only seam.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D18.** `ToolRunner.resolve` drops `PATH` components that are not absolute paths, not merely
  empty ones.
  Rationale: a relative component resolves against the *child's* working directory, which in this
  module is a repository the user opened; a `git` found there would be the repository executing
  code with the user's credential helpers. The milestone's wording ("absolute entries only")
  is a security property, so it is stated as one here.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D19.** The timeout test uses the ledger's *first* form — the internal `run(executable:)` seam
  with `/bin/sleep` — and identifies the child by an unusual sleep duration.
  Rationale: the fallback (`git -c core.editor='/bin/sleep 30' commit --allow-empty`) blocks
  inside git's editor step, which is slower, noisier and tests git's behaviour as much as the
  runner's; the seam tests the process layer directly, which is where the timeout lives. The
  liveness check afterwards is `pgrep -f` over the duration string, so it names this child and no
  other sleeping process on the machine, and it asserts on `pgrep`'s exit code (1 = no match)
  rather than on any output.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D20.** `WorkingTreeStatus.read` takes `includeIgnored: Bool = false` rather than fixing the
  command, and an unmerged path sets *both* sides of its entry to `.unmerged`.
  Rationale: the milestone's `Change` enum has an `.ignored` case, and `git status` prints `!`
  records only when asked with `--ignored`, so without the parameter that case could only be
  covered by a hand-written transcript — which is exactly the evidence the architect's ruling
  refuses. The default keeps the working-tree row's meaning intact (D6: a tree carrying nothing
  but ignored files is clean). On the second half: porcelain v2's `XY` on a `u` record are the
  two *sides of the conflict* (`UU`, `AA`, `DU`), not an index status and a working-tree status,
  so translating them through the ordinary code table would invent a distinction the bytes do not
  carry. Both sides say the path is unresolved and neither claims more.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D21.** An unfamiliar *header* is ignored; an unfamiliar *entry record* throws.
  Rationale: git adds headers to this format between versions (`# stash <n>` is one), and a
  parser that refused them would break the panel on a git newer than the one it was written
  against, for a line no consumer reads. An entry record is the opposite case: it is what the
  panel renders, so a kind this parser does not understand is a file the panel would silently
  omit — §17.7's named failure mode, and the reason nothing here is ever skipped.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D22.** `%D`'s shortened decoration form is read with a slash as the remote separator, and the
  ambiguity that leaves is filed rather than removed.
  Rationale: `git log --format=%D` prints `origin/main` for a remote-tracking branch and
  `feature/x` for a local branch, and the two are byte-identical in shape — the shortened form
  simply cannot express the difference. The unambiguous fix is `--decorate=full`, which prints
  `refs/heads/…` and `refs/remotes/…`, but that changes W7's command line, and W7 is binding on
  this leaf; a leaf may not re-cut a parent contract. So a slash means remote, a local branch with
  a slash is mis-kinded, and the case is tech-debt entry 115 for whoever may amend W7. The arrow
  form is exempt: `HEAD -> feature/x` names a local branch by construction and is read as one.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D23.** `GitLog.commits` accepts exit code 0 alone, and the W7 argument vector is asserted
  through a recording `ToolRunning` stub rather than inferred from a passing parse.
  Rationale: D3 puts the acceptable-exit decision in the wrapper, and `git log` has no
  exit-code-as-data convention to accommodate. The argument vector is the only place contract W7
  is observable, and a test that only parses real output would pass for a command line missing
  `--all` or `--topo-order` — the two flags the whole graph depends on. Rejected: asserting W7 by
  reading the source, which is not a test.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D24.** A failed `process.run()` nils the termination handler and closes all four pipe
  handles before rethrowing.
  Rationale: the handler installed at construction closes a `ToolJob → process → handler →
  ToolJob` cycle, and on the failure path nothing ever breaks it — Foundation clears the handler
  only after it fires, which for a child that never started is never. Foundation also leaves the
  descriptors it opened for the pipes open on that path, whatever happens to the objects.
  Measured before the fix: 20 failed spawns leaked exactly 80 descriptors; after, the delta is 0.
  The path is not exotic — a panel polling `git` in a directory the user deleted takes it on every
  refresh, so the leak is per-refresh. Rejected: relying on `deinit`, which the cycle prevents.
  Date/Author: 2026-09-08 / C7.3 R1 fix wave.

- **D25.** `resolve` requires an executable **regular file**, and follows the symlink before
  asking.
  Rationale: every directory carries the execute bit, so `isExecutableFile(atPath:)` alone accepts
  a `PATH` component holding a *directory* named `git`; the call then fails at spawn with
  `.spawnFailed` where the honest answer is `.binaryNotFound`. The symlink half is not
  embellishment: `URLResourceKey.isRegularFileKey` is lstat-shaped and reports a symlink to a
  regular file as not regular, and this machine's `git` is a Homebrew symlink — the check applied
  to the unresolved candidate refuses the machine's own git and takes every fixture test with it
  (measured before writing the fix). The URL *returned* is the unresolved one, so the child is
  still spawned at the path the passed `PATH` names (D2). Both directions are tested.
  Date/Author: 2026-09-08 / C7.3 R1 fix wave.

- **D26.** `spawnFailed`'s message is the error's domain **and code**, never its
  `localizedDescription`.
  Rationale: the domain alone is almost always `NSCocoaErrorDomain` and carries no information;
  the localized description carries the executable path, and this message rides in a `ToolError`
  that a panel may render or a future log may write (root spec §6.3, §11). Domain plus code is
  diagnosable and path-free.
  Date/Author: 2026-09-08 / C7.3 R1 fix wave.

- **D27.** The hermetic fixture environment adds `GIT_ATTR_NOSYSTEM=1`, `TZ=UTC` and `LC_ALL=C`
  (amends D14).
  Rationale: `GIT_CONFIG_SYSTEM` disables the system *config* tier and not the system
  *gitattributes* tier, which is a separate file — a machine-wide `/etc/gitattributes` marking a
  pattern `-text` or naming a diff driver changes the bytes milestone 5's parser reads, which is
  the accident D14 exists to prevent. `TZ` and `LC_ALL` close the same door on date rendering and
  on localised diagnostics; this machine's git speaks Korean by default, which the milestone 3
  worker hit.
  Date/Author: 2026-09-08 / C7.3 R1 fix wave.

- **D28.** The exit path's final pass over each pipe (`drainRemaining`) stays, is asserted by
  shape, and is filed as tech debt rather than claimed as tested.
  Rationale: R1 asked for a test that fails when the pass is deleted, and no such black-box test
  exists on this platform. The readable event goes from the kernel straight to the runner's queue
  while the exit travels through Foundation's reaper first, so the read is always enqueued ahead
  of the exit and the final pass finds the pipe already empty. Four constructions were tried and
  all four pass with the pass deleted. Keeping unfalsifiable code and saying so beats either
  deleting a real defence or writing a test whose green means nothing. Tracker entry 117.
  Date/Author: 2026-09-08 / C7.3 R1 fix wave.

- **D29.** A row's `edges` carry one entry per lane reserved *after* the row's update, including
  lanes merely passing through, which appear as a straight-down edge with `fromLane == toLane`.
  Rationale: the ledger's algorithm says "for every lane reserved after the update", and making the
  pass-throughs explicit is what lets the panel draw a row without re-deriving the lane state that
  produced it — a renderer that received only the edges a row *creates* would have to run the
  assignment a second time to know which lines continue past it. It is also what makes the row a
  falsifiable unit: the pass-through entries are exactly the assertions the first-parent mutation
  breaks. Edges are ordered by the lane they arrive in, so two equal assignments compare equal.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D30.** Every expected lane and edge in `LaneAssignmentTests` was derived by hand-simulating the
  ledger's algorithm over a *probed* topological order, before the implementation existed, and not
  read back from a run.
  Rationale: §17.7's failure mode is a test that passes for the wrong reason, and the cheapest way
  to build one is to run the code, copy its output into the assertion and call it green. The
  ordering `git log --topo-order --all` produces for each of the four fixture shapes is a fact
  about `git` 2.55.0, so it was measured in throwaway repositories under the system temporary
  directory (transcript below); everything downstream of it is a derivation the test comments
  spell out row by row. The derivation was correct in all five tests on first run, which is itself
  the evidence that the algorithm as the ledger states it is implementable without invention.
  Date/Author: 2026-09-08 / C7.3 executor.

- **D31.** The join of the two diff listings is **strict**: a path in one and not the other
  throws `.decodeFailed` rather than producing a change with unknown counts.
  Rationale: a change carrying no counts is exactly how a *binary* file is represented, so
  inventing one for a path `--numstat` did not mention would make every mis-join look like a
  legitimate binary and be invisible in the panel. The two invocations read the same repository
  microseconds apart, so a disagreement is a defect or a concurrent write, and §10 wants either
  rendered as a panel-local error rather than drawn as a plausible wrong list. `join` is
  internal rather than private so the case is testable without a repository that can produce it.
  Rejected: filling the missing side with zeroes, and dropping the path.
  Date/Author: 2026-09-08 / C7.3 milestone 5.

- **D32.** `parseNameStatus` rejects an unfamiliar status letter instead of carrying it.
  Rationale: measured on `git` 2.55.0, the only letters the three `DiffRef.Base` commands print
  are `A`, `M`, `D`, `T`, `R<score>` and `C<score>` — a path with an unresolved merge conflict is
  reported as an ordinary `M`, not as `U`. So there is no known letter `FileChange.Status` cannot
  express, and an unknown one means the format moved, which §17.7 says must fail a named test
  rather than be skipped into silence. This is the opposite of `WorkingTreeStatus`'s treatment of
  unfamiliar *headers*, and deliberately: a header the parser ignores costs a panel nothing,
  while an entry it ignores is a file the panel does not draw.
  Date/Author: 2026-09-08 / C7.3 milestone 5.

- **D33.** `blob` runs `git cat-file blob <rev>:<path>`, not `git show <rev>:<path>`.
  Rationale: `git show` applies a repository's `textconv` filter and would hand contract W4's
  Monaco bridge a *rendering* of the file rather than the file; `cat-file blob` is the stored
  object. A revision that does not carry the path exits non-zero and becomes `.commandFailed`,
  never empty `Data` a panel would draw as an empty file — which is tested. The working-tree side
  is read straight from disk (`workingTreeFile`), because git has nothing to add to reading a
  file that is already there.
  Date/Author: 2026-09-08 / C7.3 milestone 5.

- **D34.** `ImportGraphTests`'s anti-empty-grep floor names `AfleetCore` rather than `Foundation`,
  from milestone 5 onward.
  Rationale: the executor's ruling at dispatch, and the reason is that milestone 5 is where the
  dependency this target's manifest region declares first genuinely arrives — `GitDiff` maps
  `DiffRef.Base`. A floor on `Foundation` would still hold in a target that had quietly stopped
  depending on anything, so the tighter floor also proves the manifest region is doing something.
  The allowed set is unchanged, and the subset assertion that is the test's actual subject is
  untouched.
  Date/Author: 2026-09-08 / C7.3 milestone 5.

- **D35.** `mergeStateStatus` and `mergeable` ship as enums (`MergeStateStatus`, `Mergeability`),
  not as the `String` the milestone's interface block spells.
  Rationale: Q9/D9 says all three open-ended fields "decode as a required `String` mapped into an
  enum with an `.unknown(String)` case", and the milestone's interface block had carried the enum
  through for `reviewDecision` only. The enum is strictly the richer of the two — every case
  exposes `rawValue`, so a caller that wanted the string still has it — and it is what makes the
  live gate able to assert "GitHub returned nothing this model has no case for". GitHub's own
  `UNKNOWN` (the merge state has not been computed yet) is a *different statement* from "this
  model has no case for the value", so it is `.reportedUnknown` and the carrier is `.unknown(_:)`;
  collapsing them would have made a freshly opened pull request look like a protocol drift.
  Date/Author: 2026-09-08 / C7.3 milestone 6.

- **D36.** `CheckRun`'s optional properties decode from **required** keys.
  Rationale: `gh` never omits a requested key and never emits `null`; absence is `""` for a string
  and Go's zero instant for a timestamp (see the observation above). Mapping those two shapes to
  `nil` inside a custom `init(from:)` keeps the strict-decode rule intact — a missing key is still
  a decode error, so `testRemovingARequiredKeyFromACheckMakesTheDecodeThrow` covers all nine keys
  — while giving the panel `nil` rather than an empty string to render. A non-empty `link` that is
  not a URL is a decode failure rather than a silent `nil`: a check whose link is dropped is a
  check the panel cannot open.
  Date/Author: 2026-09-08 / C7.3 milestone 6.

- **D37.** G3's gate is a value (`LiveGate.Verdict`), not a bare `XCTSkip` inside the test.
  Rationale: D10 requires a skip with a named reason, and a skip that only happens on a logged-out
  machine is a branch nobody ever runs. Factoring the verdict out makes both branches assertable
  from a logged-in machine: one test drives the gate with a `PATH` holding no `gh` at all, another
  with a stub runner returning exit 1 and exit 0. The `.unavailable` reason carries the exit code
  and names G3, and is asserted to contain no `/` so that a skip line in a log cannot publish a
  path (§6.3). G3 itself builds its `gh pr list` argument vector in the test rather than calling
  `GhCommands.pullRequests`, because that function's signature — fixed by this milestone's
  interface block — has no repository parameter, and `--repo cli/cli` is what makes the gate
  independent of whatever repository the suite happens to run in. The field list and the decoder
  it exercises are the shipped ones, which is what G3 is for.
  Date/Author: 2026-09-08 / C7.3 milestone 6.

- **D38.** A parent outside the read window does **not** end its lane: the lane stays occupied to
  the bottom of the window and repeats a truncated straight-down edge on every row below. D5's
  original wording said "terminates its lane", which is not what the code does; the wording is
  corrected and the code is left alone.
  Rationale: the parent is never read, so nothing ever releases its reservation — the behaviour
  follows from the algorithm rather than being a choice made at the edge. It is also the right
  rendering: a line that leaves a viewport continues past it, and a graph that stopped the line at
  the row that named it would contradict its own lane state. What the flag then means is "this
  edge's target is outside the read window", not "this line ends here", and the second reading
  would make a consumer draw the wrong thing — so the meaning is stated on `Edge.truncated` itself
  and filed as tracker 119 against C7.7, the first consumer. Pinned by a multi-row test; the
  existing window test only covered the linear last-row case, where there is no row below to check.
  Date/Author: 2026-09-08 / C7.3 R2 fix wave.

- **D39.** The working-tree row's edge lands in the lane of the row carrying a `.head` ref, and
  falls back to row zero only when `HEAD` is outside the window.
  Rationale: the original code attached it to `rows.first` on the claim that `--topo-order` lists
  `HEAD` first among the reachable tips. Measured on `git` 2.55.0, it does not: `--topo-order
  --all` orders the tips by date, so a tag-only commit newer than `HEAD` is listed ahead of
  `HEAD -> main` and the panel drew the user's uncommitted changes hanging off an unrelated tip.
  `GitLog`'s decoration parser already emits `.head` for both the attached and the detached form,
  so the row is found without a second `git` invocation. The fallback is the only remaining
  approximation when `HEAD` fell outside the window, and it is honest about being one. The
  previous expression was also *unfalsifiable*: `rows.first?.lane` is always 0, because the first
  commit read sees an empty lane array, so a `toLane: 0` mutant was equivalent to it — which is
  why the new test builds a repository where `HEAD` is not in lane 0 at all.
  Date/Author: 2026-09-08 / C7.3 R2 fix wave.

- **D40.** Lane *reuse* is pinned by two fixtures whose shapes exist for no other reason.
  Rationale: in all four of milestone 4's fixtures a lane is only ever released by the final root
  commit, so no row is ever placed after a lane frees, and three branches of the algorithm — rule
  1's "leftmost free lane", rule 4's "leftmost free lane" and rule 4's "unless already reserved" —
  were never executed by the suite at all. Lane recycling is what keeps the gutter narrow on a real
  repository, so leaving it unpinned meant the widest-visible property of the graph rested on
  nothing. The two shapes are chosen to discriminate rather than merely to reach: the first opens
  **three** side lanes and closes them all at one row, so that a later tip and its further parent
  each choose among several free lanes and "leftmost" is distinguishable from "rightmost"; the
  second has two merges naming the same commit as a non-first parent. Every expectation was
  hand-derived from a probed `--topo-order --all` before it was run, per D30, and the measured
  order is asserted in the test so that a future `git` fails a named assertion instead of silently
  re-deriving the graph.
  Date/Author: 2026-09-08 / C7.3 R2 fix wave.

- **D41.** `.commitAgainstParent` passes `--first-parent` to both `git show` invocations.
  Rationale: without it a **merge** commit cannot be listed at all, in two different ways.
  Measured on `git` 2.55.0 with the global and system configuration disabled: for an ordinary
  merge `git show --format= --name-status -z` prints **nothing** while `--numstat -z` prints a
  record per path, so `GitDiff.join` throws on listings that disagree completely; and for a merge
  whose tree differs from both parents — a resolved conflict — the default is git's *combined*
  diff, whose status field carries one letter per parent (`MM`), which the name-status parser
  rejects by design. The alternative the reviewer offered, treating a merge as an empty change
  list, was rejected: an empty list is a dead end in a panel whose whole purpose is showing what
  changed. `--first-parent` is deterministic, identical in shape across the two listings, never
  produces a combined status code, and answers the question the panel is asking — what the branch
  this merge landed on gained by it. The root-commit behaviour `git show` was chosen for is
  untouched: `--first-parent` changes nothing for a commit with fewer than two parents, which the
  existing root-commit test pins.
  Date/Author: 2026-09-08 / C7.3 R3 fix wave.

- **D42.** `workingTreeFile` returns a **symbolic link's destination**, not the bytes of what it
  points at.
  Rationale: git stores a symlink as a blob holding its destination text, so `blob` returns
  `"a.txt"` where an ordinary read of the working tree follows the link and returns the contents
  of `a.txt`. The two sides handed to Monaco were then different kinds of object: retargeting a
  link drew as a whole-file rewrite, and a **dangling** link — a change git tracks perfectly well
  — threw. Detected with `lstat` and read with `readlink` rather than
  `destinationOfSymbolicLink`, which returns a `String`: a destination is a path and a path on
  macOS need not be valid UTF-8, the same reason the listing parser splits over bytes. The buffer
  is one byte longer than `st_size` so a full read is distinguishable from a truncated one.
  Date/Author: 2026-09-08 / C7.3 R3 fix wave.

- **D43.** A row's edges are a **set of lines**, not one line per destination lane.
  Rationale: three of R3's five findings were the same defect in the edge model, and fixing them
  as one change is what made them disappear together. The model is now the union of (a) a
  pass-through `i → i` for every lane holding a reservation before this row's parents are
  assigned, and (b) one `lane → p` for every lane this commit's parents occupy; the two sets
  overlap in destination and both edges are kept. The old "one edge per lane reserved after the
  update" could not represent the overlap: where a merge reaches into a lane another child
  already reserved, it replaced that lane's pass-through with the merge edge and disconnected the
  older line at that row. The same construction is why a shared parent's convergence was never
  drawn — the extra reservations were released with nothing redirected into the lane the parent
  was read at, so a line ended in the empty lane beside its own target — so step 2 now redirects
  the edges arriving in the released lanes, which is only expressible once a destination lane may
  carry more than one edge. Edges are ordered by `(toLane, fromLane)`; no two edges of a row share
  both endpoints, so the order is total and two assignments of one window compare equal. Filed for
  the first consumer as tracker **121**: a panel that indexes edges by `toLane` silently drops one
  of a pair.
  Date/Author: 2026-09-08 / C7.3 R3 fix wave.

- **D44.** The working-tree row is placed **before** the loop and reserves lane 0 for `HEAD`,
  rather than being prepended with a single edge afterwards.
  Rationale: `GraphRow.Edge` connects adjacent rows only, so an edge synthesised after assignment
  reaches `HEAD` exactly when `HEAD` is the row below — which D39 established it need not be. In
  the newer-tag fixture the edge ended in lane 1 at the tag's row, and that row carried only a
  lane-0 edge, so the connection dangled. Reserving lane 0 for `HEAD`'s hash makes the working
  tree a child of `HEAD` under the algorithm's own rule 3, and the reservation is then carried
  down through every intervening row by the pass-through rule at no extra cost. `HEAD` is
  consequently read in lane 0 and the tips read before it open lanes beside it, so a dirty tree
  can change the lane a commit sits in — deliberate, and the honest rendering: the uncommitted
  changes are the newest thing in the graph and the line down to `HEAD` is a line like any other.
  D39's fallback survives unchanged (the first commit read, when no row carries `.head`), and so
  does its falsifiability argument, relocated: the mutant that reserves the first row's lane
  instead of `HEAD`'s is killed by the lane assertions rather than by the edge's `toLane`.
  Date/Author: 2026-09-08 / C7.3 R3 fix wave.

## Tech debt to file (numbers reserved 112–126)

- **112.** `SourceControlCore.ToolRunner` duplicates the process mechanics of
  `ClaudeWire/Sources/WireEnvironment/ProcessRunner.swift` — termination-handler exit
  observation, non-blocking pipe drains, timeout with grace and `SIGKILL` — because X1
  forbids Workbench from importing `ClaudeWire` and X2 keeps `AfleetCore` to value types. Two
  copies is tolerable; a third is the signal to extract a process package below both. Owner:
  whichever child needs the third copy, or C2 if it revisits the package split.
- **113.** Workbench has no §11 diagnostics domain. §11's table names four log files and none
  is the panel layer's, so this leaf returns typed errors and logs nothing. When a panel wants
  a durable record of a failing `git` or `gh` invocation, the domain has to be opened in §11's
  table with a writer that owns the file. Owner: C7.7, or C5 if it opens it first.
- **114.** The commit graph is read in a fixed window (default 2,000 commits) with no
  paging affordance above it; edges to unread parents are marked truncated but nothing yet
  fetches the next page. Owner: C7.7 when the panel's scroll needs it.

- **115.** `GitLog` reads `%D`'s shortened decorations, which cannot distinguish a
  remote-tracking branch from a local branch whose name contains a slash, so `feature/x` is
  reported as `.remoteBranch(remote: "feature")` named `x`. The remedy is `--decorate=full` on
  the `git log` call, which prints `refs/heads/…` and `refs/remotes/…` unambiguously and would
  simplify the parser rather than complicate it — but it amends contract W7's command line, which
  this leaf does not own (D22). Owner: whoever revises W7, most likely C7.7 when the panel starts
  drawing ref badges and the distinction becomes visible.

- **116.** `ToolRunner` has no `timeoutState`. C2's `ProcessRunner` sampled a
  `describeAtTimeout()` before it signalled the child, which is what let a hung child be told
  apart from a child that exited without the runner observing it; that sampling was not carried
  across, so the only residual tell here is the pair `exitCode == -1 && timedOut`. The pair is
  enough for a panel to render "the tool did not answer", and not enough to say which of the two
  happened when one is diagnosed. Filing rather than fixing: the state is only worth its cost
  once something consumes it, and nothing in Workbench does yet (entry 113 — no diagnostics
  domain). Owner: whoever opens the Workbench diagnostics domain, most likely C7.7.
- **117.** `ToolJob.drainRemaining` — the final non-blocking pass over each pipe on the exit
  path — is not falsifiable by any black-box test on macOS: the readable event reaches the
  runner's queue ahead of the exit in every construction tried, so the pass always finds the pipe
  empty and deleting it changes no observable behaviour (D28). It is kept as defence for the
  ordering that a loaded queue or another platform could produce. Closing this means a seam that
  lets a test hold the queue busy across the child's last write. Owner: whoever next revises the
  process layer, or the extraction that entry 112 anticipates.

- **119.** `GraphRow.Edge.truncated` is easy to misread as "the line ends here". It means only
  that the edge's target is outside the window `GitLog` read; the lane stays occupied and repeats
  the same truncated straight-down edge to the bottom of the window (D38). A consumer that read it
  as a terminator would stop the line at the first row that named it and draw a graph that
  disagrees with its own lane state. Documented on the flag and pinned by a multi-row test; what
  would close it is a name that cannot be misread, or a rendering contract the panel and this type
  share. Owner: **C7.7**, the first consumer, which must not misread the flag.

- **120.** One mutation of rule 3 survives the suite and could not be killed: *the first parent
  takes the leftmost free lane* rather than the commit's own. In every fixture the two coincide,
  because a commit's own lane is released just before rule 3 runs and is the leftmost free one.
  Distinguishing them needs a row read at a **reserved** lane while a lane to its **left** is
  free; a lane is only freed by a parentless commit or by a released duplicate, and three probed
  shapes (two roots with interleaved dates, and an unrelated-history merge in both directions)
  all had `git --topo-order` follow a chain to its end before starting another, which frees lanes
  right-to-left. It may be equivalent under git's ordering rather than merely uncovered, which is
  why it is filed instead of chased. Closing this means either a shape that orders the other way
  or an argument that none exists. Owner: whoever next revises lane assignment.
- **121.** `GraphRow.edges` may contain **several edges arriving in the same `toLane`**, and a
  consumer that indexes them by destination lane silently drops one of each pair and disconnects
  a line at that row (D43). The two ways it happens are a merge reaching into a lane another
  child already reserved, and two lanes converging on one parent. Documented on `GraphRow.Edge`
  and pinned by a connectivity assertion over every lane fixture; what would close it is a
  rendering contract the panel and this type share. Owner: **C7.7**, the first consumer.

### Review point R1 — the process layer (2026-09-08)

An independent reviewer read `ToolRunner.swift` against C2's
`ClaudeWire/Sources/WireEnvironment/ProcessRunner.swift` and against milestone 1's mutation
transcripts, answering "which of C2's five documented process defects could this code still have".
Nine findings were accepted. Eight were applied by a fix wave; the ninth was logged. Suite 32 → 36,
0 failures.

**W1 — the spawn-failure path leaks the job and four descriptors per call.** Applied (D24).
`ToolJob.start()` now nils `process.terminationHandler` and closes all four pipe handles before
rethrowing. Both halves are load-bearing and each was checked separately: Foundation clears the
handler after it fires, so on a spawn that never produced a child it is never cleared and the
`ToolJob → process → handler → ToolJob` cycle stands forever; and Foundation's failure path leaves
the pipe descriptors open regardless of what happens to the objects. Failing first, against the
unfixed runner:

    testAFailedSpawnDoesNotLeakDescriptors: XCTAssertTrue failed —
      20 failed spawns left 80 descriptors open; the failure path does not close the pipes

Exactly four per call, matching the reviewer's own measurement. After the fix the delta is 0. The
count comes from `/dev/fd`, which the kernel synthesises per process; no path is named (§6.3, §11).

**W2 — the negative environment test could pass vacuously.** Applied. Two absence assertions with
no exit-code check and no positive floor are satisfied by a child that never ran: on a machine
whose account has no full name, `git var GIT_AUTHOR_IDENT` with no author name exits 128 with an
empty stdout, which contains no sentinel either. The test now asserts exit 0 and that stdout
carries the invented address that *is* in the passed dictionary — leak-free, and one assertion
that proves both that the child ran and that it read what it was handed. Demonstrated against the
mutation `process.environment = [:]` (a child handed nothing), which is exactly the vacuous case:

    old form (two absence assertions):  passed (0.015 s)
    strengthened form:                  XCTAssertTrue failed — the identity git reported does not
      carry the address named GIT_AUTHOR_EMAIL in the passed environment, so the child did not read it

**W3 — settlement keyed to exit rather than EOF, and the final drain, were certified by code shape
only.** Half applied, half filed (D28). The new test runs `/bin/sh -c 'sleep 5 & echo done'`
through the internal `run(executable:)` seam with a 30 s budget: the grandchild holds the write end
of stdout for five seconds after the child itself is gone. Settlement-versus-EOF is discriminated
outright — mutated so that `settleIfComplete` also required `drains.isEmpty`, with the cancel
handler re-checking:

    XCTAssertTrue failed — the call took 5010 ms for a child that exits at once,
      so settlement is waiting on end-of-file rather than on the exit
    failed (5.213 seconds)

The five-second separation the reviewer measured, reproduced. The final drain is a different
story and the honest record is that **it was not demonstrated**. With `drainRemaining()` emptied
the test still passes, and so does every construction tried: one write, a write after a delay, a
write before the delay, a write landing with the exit. The cause is structural — the readable
event goes from the kernel straight to the runner's own queue, while the exit travels through
Foundation's reaper before it is posted there, so the read is always enqueued first and the final
pass finds the pipe already empty. An intermediate run appeared to show 5/5 discrimination and was
an artifact: the mutated child wrote `x` before `done` while the assertion still expected `done`,
so the failures were the wrong string, not the missing drain. Caught on re-run against the final
test, and recorded here because it is the kind of green-by-accident this review point exists to
find. The pass is kept as defence for the ordering a loaded queue or another platform could
produce, the test says in a comment that it does not cover it, and tracker entry 117 carries the
seam that would.

**M4 — a directory named `git` on `PATH` resolved.** Applied (D25). Failing first:

    testADirectoryNamedLikeTheToolIsNotResolved:
      XCTAssertTrue failed — resolve accepted a directory named git as an executable
      XCTAssertEqual failed: ("spawnFailed(tool: git, message: \"NSPOSIXErrorDomain\")")
        is not equal to ("binaryNotFound(tool: git)") — the wrong ToolError was thrown

The prescribed remedy needed one correction, found before writing it. `URLResourceKey`
`.isRegularFileKey` is lstat-shaped: applied to the candidate as spelled on `PATH` it reports a
symlink to a regular file as *not* regular, and this machine's `git` is `/opt/homebrew/bin/git ->
../Cellar/git/2.55.0/bin/git`. Measured directly before the edit:

    /usr/bin/git           regular: true    symlink: false
    /opt/homebrew/bin/git  regular: false   symlink: true

So the naive form would have refused the machine's own git and failed every fixture test in the
suite. The check follows the symlink and returns the *unresolved* candidate, so the child is still
spawned at the path the passed `PATH` names (D2). A second test,

**M5 — `spawnFailed` carried the domain alone.** Applied (D26): `"\(domain) \(code)"`, with the

### Review point R2 — lane assignment (2026-09-08)

An independent reviewer read `LaneAssignment.swift` against this ledger's statement of the
algorithm, checked that each of milestone 4's lane tests names the lane it expects, ran the
mandatory wrong-lane mutation (first-parent rule replaced by "always take a free lane") and
fifteen others. The mandatory mutation is killed by three of the four lane tests, as milestone 4
recorded. Of the sixteen mutations, **eleven were killed and five survived**, all five for one
reason. Three findings were accepted and two observations dismissed.

**F1 — the working-tree row attached to row zero rather than to `HEAD`'s row.** Accepted, fixed
(D39). The edge was built as `rows.first.map { Edge(fromLane: 0, toLane: $0.lane, …) }`, justified
by a doc comment claiming `--topo-order` lists `HEAD` first among the reachable tips. The claim is
false, and the counterexample reproduces on `git` 2.55.0 — a tag-only commit with a newer commit
date is listed ahead of `HEAD -> main`:

    $ git log --topo-order --all --pretty='%h %d %s'
    <h1>  (tag: v9) detached work
    <h2>  (HEAD -> main) c2 on main
    <h3>  c1 root

In that configuration the panel drew the user's uncommitted changes hanging off an unrelated tip,
which is exactly the clause G1 names ("an edge to `HEAD`'s row"). Two aggravating details, both
the reviewer's: `rows.first?.lane` is *always* 0, because the first commit read sees an empty lane
array, so the old expression was unfalsifiable — a `toLane: 0` mutant is equivalent to it; and the
existing dirty-tree test uses a single-branch repository, where `rows.first` *is* `HEAD`, so it
could not see any of this. The new test therefore builds a repository in which `HEAD` is not in
lane 0 at all, asserts the premise (the first row read carries no `.head` ref) before asserting the
conclusion, and demonstrated failing against the unfixed code on exactly one assertion:

    testTheWorkingTreeRowAttachesToHeadsLaneWhenANewerTagOnlyTipIsReadFirst:
      XCTAssertEqual failed: ("Optional([Edge(fromLane: 0, toLane: 0, truncated: false)])") is not
      equal to ("Optional([Edge(fromLane: 0, toLane: 1, truncated: false)])") — the working-tree
      edge lands in HEAD's lane, not in the first row's lane

Every other assertion in that test — the measured order, both tips' lanes, the shared root's lane
and `laneCount` — held against the unfixed code, so the failure isolates the defect. The refuted
sentence is replaced in the doc comment by the measured fact rather than deleted, and D5's and the
milestone 4 plan's wording are corrected in place above.

**F2 — lane reuse was never exercised; three branches had zero coverage.** Accepted, fixed (D40).
In every one of milestone 4's fixtures a lane is only ever released by the final root commit, so
no row is ever placed after a lane frees, and rule 1's "leftmost free lane", rule 4's "leftmost
free lane" and rule 4's "unless already reserved" were never executed. Two fixtures were added.
Their `--topo-order --all` orders were probed in throwaway repositories before any expectation was
written (D30), and both orders are asserted in the tests; both are worth recording, because
neither is date order:

    (a) octopus, p3, p2, p1, m2, m1, sideMerge, o1, o2, base
        — git emits the octopus's three further parents in reverse, and o1 ahead of the newer o2
    (b) mainMerge, m1, sideMerge, s, x1, base

Fixture (a): `base` has three children — `m1`, `o1`, `o2`. `m1` has four children joined by an
octopus merge, so lanes 1, 2 and 3 all open and all close at `m1`'s row, leaving only lane 0
reserved for `base`. The older `sideMerge` (parents `[o2, o1]`) is then read with three lanes free
and must take the leftmost, lane 1; its further parent `o1` must take the leftmost of the two
still free, lane 2; and `laneCount` must stay 4. Three free lanes rather than one is what makes
"leftmost" distinguishable from "rightmost" — with a single free lane the two mutants agree, and
the fixture would pin only half of what it looks like it pins. Fixture (b): two merges naming the
same commit `s` as a non-first parent, so the second must reach sideways into the lane already
reserved (`edge(2, 1)`) instead of opening a fourth.

Coverage verified directly, by putting `fatalError` in each of the three branches in turn and
running each of the nine lane tests individually — a `fatalError` aborts the whole test process,
so a full-suite run cannot attribute it:

    rule 4, "leftmost free lane"         testAFreedLaneIsReusedByALaterTipAndByAFurtherParent
    rule 4, "unless already reserved"    testASecondMergeNamingTheSameFurtherParentReusesItsReservation

**F3 — `truncated`'s meaning, and D5's wording.** Accepted as a documentation fix (D38); the

**One mutation survives, and it is filed rather than hidden (tracker 120).** Writing rule 3 as
"the first parent takes the leftmost **free** lane" passes the whole suite, because a commit's
own lane is released immediately before rule 3 runs and is the leftmost free lane in every
fixture. Telling them apart needs a row read at a *reserved* lane while a lane to its left is
free. A lane is freed only by a parentless commit or by a released duplicate, and three probed
shapes — two roots with interleaved dates, and an unrelated-history merge in each direction —
all had `git --topo-order --all` follow one chain to its end before starting another, which frees
lanes right to left:

    two roots, dates interleaved:       tipA, rootA, tipB, midB
    unrelated merge, side second:       merge, other tip, other root, solo root
    unrelated merge, trunk second:      merge, side tip, side root, trunk tip, trunk root

judgement R2 made about `laneCount = lanes.count`, but with less certainty, which is why it is
filed with the shapes already ruled out rather than dismissed.
