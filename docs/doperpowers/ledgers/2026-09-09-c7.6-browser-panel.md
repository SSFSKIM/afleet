## Purpose / Big Picture

After this leaf, afleet has a Browser tab: a set of `WKWebView` tabs shared across the
window with a URL bar, back, forward, reload and the Web Inspector; a quick-open list of the
URLs the current channel's tool output has shown; and two `LinkRouter` targets, so a `.url`
a message emitted and a `.pullRequest` a Source Control view emitted both land in that tab
instead of leaving the app. The tab set survives a channel switch because it is not owned by
a channel, and survives a relaunch because it is persisted under contract W6's `browser` key
in the `workbench` namespace.

It is the last blocker of three other pieces of work: C7.7's "opening a PR loads it in the
Browser tab" (root item 28), C6's `/login` automatic URL (item 59) and C6's overage card's
*Set up usage credits…* (item 62's false branch). All three already emit a `WorkspaceLink`
or call `StrategyUI.open(url:)`; today those links reach nobody and W5's fallback sends them
to the system browser. This leaf is what makes them land inside the app.

Nothing here re-implements a browser: WebKit is WebKit, and the panel is chrome around it.
Nothing here parses a timeline: X1 forbids Workbench from reading timeline items, and the
recent-URL feed C5 shipped (`TimelineRecentURLFeed` over X4's `ChannelTimeline.recentURLs`)
is the only way URLs reach quick-open.

How to see it working, from a clean checkout of this branch:

    cd /Users/new/Developer/GitHub/afleet-c7/browser-panel
    swift test --package-path Workbench          # the package floor, including BrowserPanelTests
    make test                                    # the app floor; verdict read from the captured file

The `BrowserPanelTests` suite drives **real** `WKWebView`s — a grounding probe below shows
they load, run JavaScript and honour `isInspectable` inside a bare `swift test` process with
no app bundle — against `loadHTMLString` and against a loopback HTTP server the test itself
starts and stops. No test reaches the network, and no test URL names a real site.

## Residue, grilled

The composite's C7.6 section is a *brief*: four sentences of purpose, four gates, the
contracts and the design inheritance. Everything it leaves open is listed here with the
answer this ledger commits to. Routine mechanical questions are decided here and marked
*decided*. Two are **escalated** to the architect at the gate, because they are a
contradiction between binding statements and a contract seam owned by another leaf.

### Q1 — Cmd-click: the system browser, or an afleet pop-out? **[ESCALATED]**

Four binding-or-near-binding statements disagree, and they disagree about the one gesture
this leaf's G2 names.

- Composite **Parent-Level Acceptance item 3**: "`.url` to a Browser tab, … `.pullRequest`
  to the Browser tab on the PR page; **Cmd-click on any of them opens a new window**."
- Composite **contract W5** (`[binding]`): "Cmd-click maps to `.newWindow`."
- Composite **C7.6's own acceptance G2** (`required`): "a `.url` link from a timeline item
  opens in the tab; **Cmd-click opens the system browser**; a `.pullRequest` link opens the
  PR page."
- Root spec **§9.4**: "links in messages open here, **Cmd-click in the system browser**."
  (§9.4 is advisory except the window-wide clause, so it is the weakest of the four, but it
  is what C7.6's G2 inherits from.)

They are not reconcilable by reading. `.newWindow` on a `.url` cannot both pop the Browser
tab out into an afleet window and hand the URL to Safari.

**Recommended answer.** `.newWindow` keeps its meaning — "not the current panel" — and the
Browser answers it the way a browser panel should: `.url` and `.pullRequest` at `.newWindow`
go to `NSWorkspace.shared.open`, i.e. the user's real browser. Every other case keeps the
afleet pop-out. Reasons: the escape hatch is the useful gesture (the panel already pops out
from its own control, so a pop-out costs the user nothing to reach, while getting a URL into
a real browser with profiles, extensions and a password manager has no other affordance);
it is what both C7.6's own required gate and root §9.4 say; and it is the reading that makes
the leaf's four gates all satisfiable at once.

**The mechanism, and why it needs the architect.** `HostLinkRouter.open` pops the target's
tab out *unconditionally* for `.newWindow`, before the target is delivered to. A Browser
target that opened the system browser under today's host would give the user **both** an
afleet pop-out window and a Safari window. So the recommendation is only implementable with
a one-field amendment to X7, on C5's fence rather than mine:

    public struct LinkTarget: Sendable {
        …
        /// Whether the host pops this target's tab out before delivering `.newWindow`.
        /// A target that answers `.newWindow` by leaving the app has no window to be
        /// popped out into, and a host that popped one anyway would present two.
        public let popsOutForNewWindow: Bool   // default true; Browser registers false
    }

with `HostLinkRouter.open` skipping `prepare` when the resolved target declines it. That is
three lines in `PanelHostAPI`, three in `HostLinkRouter`, and no change to `LinkRouter`
(which already routes with no `prepare` when none is supplied — the path it documents as the
non-suspending one).

**Fallback if the architect rules for item 3 instead.** `.newWindow` navigates the
popped-out Browser tab, and "Cmd-click to the system browser" is honoured only for links
*inside a rendered page* (Q11), which this leaf implements either way. G2's Cmd-click clause
would then be recorded as amended by the architect rather than met as written.

**`[parent-impact]` either way**, filed below: whichever way it goes, two of the four
statements above are wrong on the parent and a leaf must not edit them.

### Q2 — `.pullRequest(Int)` carries no repository. Where does the URL come from? **[ESCALATED, with a recommendation]**

`WorkspaceLink.pullRequest(Int)` is a bare number. Turning it into a page needs the
repository's host and owner, which is `git`/`gh` knowledge; W1's table gives `BrowserPanel`
`LinkRouting`, `PanelHostAPI` and `FleetKit`, and none of them knows a remote.

*Recommended (D2):* add `SourceControlCore` to the `BrowserPanel` target **inside the C7.6
region of the manifest**, and resolve the URL by running `gh pr view <n> --json url` through
C7.3's public `ToolRunner` in the channel's repository root, decoding the one-field document.
`gh` absent, logged out, not a repository, or a number that is not a PR each become a
panel-local error row carrying the `gh auth login` hint C7.7 uses — never an exception that
reaches the channel (§10). Rejected: building `https://<host>/<owner>/<repo>/pull/<n>` from
`git remote get-url` by hand (every remote spelling, SSH aliases, enterprise hosts and
`insteadOf` rewrites are a parser this leaf would own and get wrong); waiting for C7.7 (which
this leaf blocks, precisely on PR opening); a second process runner inside `BrowserPanel`
(tracker 112 already records the price of one duplicate).

The precedent for the manifest edit is exact: C7.2 added `PanelHostAPI` to `LinkRouting` for
the same class of reason and the composite amended W1's row at its merge. This is a
`[parent-impact]` filing, not a local re-cut, and the edge stays acyclic
(`SourceControlCore` depends on `AfleetCore` only). It is escalated rather than merely
decided because it changes a W1 table row, which is binding.

### Q3 — Which channel does a `.pullRequest` resolve against? *Decided (D3).*

The handler receives `(WorkspaceLink, LinkDestination)` and no channel, and the Browser is
shared across channels, so "the repository" has to come from somewhere. The panel shows
exactly one channel at a time, and a PR link comes from what the user is looking at:
resolution uses the **host's currently selected channel**, supplied to the tab at
construction as a `@MainActor () -> ChannelContext?` provider the app fills from
`PanelHostModel.selectedChannel` and `context(for:cwd:)` — the same pair the composer already
uses. No channel selected (the window is on Activity) is the panel's error row, not a guess.
Rejected: caching the last rendered context inside the panel (it goes stale in exactly the
case that matters, a link arriving before the Browser tab has ever been drawn).

### Q4 — Registered once, or once per channel? *Decided (D4).*

Once, when the app registers the tab. `LinkRouter` keys registrations by `PanelTabID` and
`unregister(tab:)` drops all of a tab's registrations together; registering per channel would
put N indistinguishable targets in the registry for one tab, all tying on specificity, and
would make the count in a diagnostic a number about channels. The `LinkRouterCapability` on a
`ChannelContext` is the same object for every channel in the app, so registering through the
first context is registering globally — which is why it is done explicitly at tab
registration instead, where it reads as what it is.

### Q5 — "Shared across the window": how many tab sets exist? *Decided (D5).*

One per app process. Every main window and every popped-out Browser window renders the same
`BrowserModel`, the same tab list and the same `WKWebView` instances. §9.4's window-wide
clause is binding and item 39 tests a channel switch; C5 ships one main window plus pop-outs,
so "window-wide" and "app-wide" name the same set today, and a per-window set would be a
second answer to a question nothing asks.

**The AppKit consequence, decided here because it is forced:** an `NSView` has one superview,
so the same `WKWebView` cannot render in the main panel and a popped-out Browser window at
once. The web views follow the pop-out; the main panel's Browser tab then draws a short
"Showing in the Browser window" state with a button that closes the pop-out and brings them
back. Rejected: one web view per surface sharing only the URL list (two loads of every page,
two sets of scroll and form state, and a "shared browser" that is not one).

### Q6 — What is persisted, and when is it written? *Decided (D6).*

W6 fixes the content: "URLs, titles, order, selected index", `Codable`, with a schema
version. The document:

    struct BrowserTabSetDocument: Codable, Sendable, Equatable {
        var schemaVersion: Int          // 1
        var tabs: [PersistedTab]        // order is the tab strip's order
        var selectedIndex: Int          // clamped into `tabs` on read
    }
    struct PersistedTab: Codable, Sendable, Equatable {
        var id: UUID
        var url: URL
        var title: String
    }

written at key **`browser`** through `ChannelContext.store`, which binds the `workbench`
namespace and passes the key through unchanged (C5's `WorkbenchScopedStore` documents exactly
that). The key is `browser` and not `workbench.browser`: W6 was amended on 2026-09-09 at
C7.5's gate — the host binds the namespace and keys do not restate it. This leaf writes that
one key and no other; it keeps no per-channel document, so no `panel.browser.…` key exists
unless a later decision here creates one, and if it does it takes that spelling.
Structural changes — a tab opened, closed, reordered or selected — write **immediately**,
because those are the changes a user makes and then quits. URL and title commits write
through a 500 ms trailing coalescer, because a single navigation fires several. A document
whose `schemaVersion` is greater than this build's opens **empty and never overwrites**,
matching the app's existing `.newer` convention for a store document written by a newer
build. At most 50 tabs are persisted (the newest 50 by position), so the document stays a
document.

### Q7 — What is deliberately *not* persisted, and how does a restored tab load? *Decided (D7).*

Not persisted: back/forward history, scroll offsets, form state, and any per-page state
WebKit holds. Cookies and site data are not in the document at all — they live in the
`WKWebsiteDataStore` (Q13) and persist on their own.

On relaunch the **selected** tab loads its URL; the others stay unloaded until first
selected, showing their persisted title. A ten-tab restore that fired ten requests at
whatever those hosts are would be a surprising thing for an app to do on launch, and G3
witnesses URLs, titles, order and selection, all of which the lazy path keeps.

### Q8 — Quick-open: what does it list, and what do Enter and Cmd-Enter do? *Decided (D8).*

`ChannelContext.recentURLs` for the **current** channel — `current(limit: 50)` when the sheet
opens, then its `updates` stream while it is up, cancelled when it closes. The tab set is
shared; the URL feed is per channel, which is right: quick-open answers "what did *this*
session just print". Filtering is a case-insensitive substring match over the absolute
string, most recent first, which is the order `recentURLs` already returns. Enter opens the
selected URL in the current tab; Cmd-Enter opens it in a new tab. §9.4's quick-open detail
is advisory; this is the *Parent revisions* entry below.

### Q9 — What does the URL bar do with what the user types? *Decided (D9).*

A pure function with a table test, because it is where a browser panel is usually wrong:

| input | result |
|---|---|
| empty or whitespace | nothing happens |
| a scheme in `http`, `https`, `about` | as typed |
| `localhost`, `localhost:8123`, `127.0.0.1:8123`, `[::1]:8123`, `*.localhost` | `http://` prefixed |
| a bare `host:port` with an all-digit port | `http://` prefixed |
| anything else with a dot and no whitespace | `https://` prefixed |
| anything else | an inline "not a URL" state; nothing loads |

**No web search fallback, ever.** A typed string that is not a URL going to a search engine
is a keystroke leaving the machine, and this panel has no search provider and should not
acquire one. `localhost:8123` gets `http://` and not `https://` because item 26's witness is
`python3 -m http.server 8123` and because `URL(string: "localhost:8123")` otherwise parses
`localhost` as the scheme, which is the specific silent failure this table exists to close.

### Q10 — Which schemes may load in the panel, and what happens to the rest? *Decided (D10), amended at R2 (D38).*

`http`, `https` and `about:blank` load. `file:` is refused with a one-line notice pointing at
the Files tab — reading the user's disk is Files' job, with Files' viewers and Files' rules,
and a browser panel that renders local files from links is a capability nothing here asked
for. Every other scheme (`mailto:`, `x-apple-*`, an arbitrary app scheme) is refused in the
panel, and is handed to `NSWorkspace.shared.open` **only when the user typed it into afleet's
own URL bar**. Anything arriving from inside a rendered page — by link, by form, by form
resubmission, from a subframe, across a server redirect or from a script — is refused with a
diagnostic, so a page cannot make afleet launch an application at all.

**Amended by D38.** The original wording said "only when it came from a user gesture —
`.linkActivated` or the URL bar", and M2 implemented it that way. R2 established that WebKit's
navigation type authenticates no gesture: a script's `requestSubmit()` is reported as
`.formSubmitted`, a subframe's navigation is classified like the main frame's, and a server
redirect reuses the action that triggered it, so a clicked `https:` link can arrive at a
`mailto:` as `.linkActivated`. The URL bar is what survives, because it is the one input page
content cannot reach.

### Q11 — Cmd-click inside a rendered page, `target=_blank`, `window.open`. *Decided (D11).*

- Cmd-click on a link in a page (`.linkActivated` with `.command` in the navigation action's
  modifier flags): cancelled in the panel and handed to `NSWorkspace.shared.open`. This is
  the brief's "Cmd-click leaves the app for the system browser", and it holds regardless of
  how Q1 is ruled. **Narrowed by D38 to `http`, `https` and `about:blank`**, which is all this
  clause ever meant: the modifier flags are real (a synthesised click carries none, probe 3),
  and opening a *web* URL in the user's own browser is not a privileged operation. A non-web
  scheme is refused before this branch is reached, Cmd or no Cmd.
- `target=_blank` and `window.open` (`createWebViewWith`): a **new panel tab**, and `nil`
  returned. That is ordinary browsing, not an escape; making it a Safari window would make
  half the web unusable in the panel.
- Shift-click and Option-click carry no special meaning here.

The decision function is written as a pure `NavigationPolicy.decide(...)` over (URL,
navigation type, modifier flags, whether a target frame exists, and — since D38 — the
navigation's **origin**, `.pageContent` or `.urlBar`), and the `WKNavigationDelegate` is a
five-line adapter onto it that always says `.pageContent`. That is what
makes §17.7 satisfiable: the policy is exhaustively testable, and the grounding probe below
records why driving it through synthesised DOM clicks is not.

### Q12 — What does page content get to talk to? *Decided (D12).*

**Nothing.** No `WKScriptMessageHandler` is registered, no user script is injected, and the
`WKUserContentController` is left empty. The chrome needs `url`, `title`,
`estimatedProgress`, `canGoBack`, `canGoForward` and `isLoading`, every one of which is a
KVO-observable property of `WKWebView` on the app's side of the boundary. A test reads the
configuration back and asserts the handler set is empty, so a later convenience cannot add
one quietly. No engine byte is ever written into a page: the only thing that crosses is a
URL the user or a link chose, as a navigation.

**This is also what makes D39 tolerable.** A page-originated `javascript:` URL runs without
the navigation-policy callback ever being dispatched, so the panel's deny-list cannot see it.
What the page reaches by doing so is nothing it did not already have: its own origin, and no
bridge — `typeof window.webkit === "undefined"` is the assertion, and it is this answer that
makes it true.

### Q13 — Website data: persistent or ephemeral? *Decided (D13).*

`WKWebsiteDataStore.default()`, shared by every tab. Item 28 opens a pull request page, and a
private repository's PR behind an ephemeral data store is a sign-in wall on every click,
forever. The data store lives in the app's own container; nothing about it touches Claude
Code's config home (X9), and afleet holds no token of its own (the composite's own decision
about `gh`).

### Q14 — App Transport Security. *Decided (D14).*

`App/Info.plist` gains `NSAppTransportSecurity` with `NSAllowsLocalNetworking: true` — item
26 is `http://localhost:8123`, and ATS blocks plain-HTTP loads to hosts it cannot evaluate —
and `NSAllowsArbitraryLoadsInWebContent: true`, which is the key Apple provides for exactly
this shape: a web view the user points wherever they like, while the app's own URLSession
traffic stays under ATS. Measured in the grounding probes: a bare `swift test` process has no
Info.plist and loads `http://127.0.0.1:<port>` without either key, so the package suite
cannot witness this and the built app must (G1).

### Q15 — The inspector, in Debug and in Release (G4). *Decided (D15).*

`WKWebView.isInspectable` is set from an injected `@Sendable () -> Bool`. The app passes
`{ true }` under `#if DEBUG` and `{ settings.developer.webInspector }` otherwise.
`DeveloperSettings` gains `var webInspector: Bool` (default `false`) and Settings' Developer
section gains a *Web inspector in the Browser panel* toggle beside the four already there.

**And a decoding trap that has to be closed with it.** `DeveloperSettings` uses Swift's
synthesised `Decodable`; adding a non-optional field makes every settings document written by
an earlier build fail to decode, which the store would treat as malformed. So the same
milestone gives `DeveloperSettings` a hand-written `init(from:)` using `decodeIfPresent` for
**every** field, with a test that decodes a document written before `webInspector` existed
and gets the other four back. If the same shape is found in the other settings types, it is a
tracker entry rather than scope creep.

### Q16 — How the user reaches the inspector. *Decided (D16).*

`isInspectable` alone puts *Inspect Element* in the web view's context menu, which is what
"reachable" means and what Safari's own remote-inspection path expects. No menu item, no
keyboard shortcut, no extra surface.

### Q17 — How is any of this tested without an app and without a network? *Decided (D17).*

Three layers:

1. **Pure logic** — URL normalisation, navigation policy, the persistence codec and its
   coalescer, tab-set operations, the PR-URL decoder — as free functions and value types,
   tested by table. This is where §17.7's "shown failing first" is meaningful.
2. **Real `WKWebView`s in the package suite**, against `loadHTMLString` and a loopback HTTP
   server the test starts and stops (`NWListener` bound to `127.0.0.1:0`, one canned
   response, cancelled on teardown). The probes below show both work in a bare `swift test`
   process. Every wait is fulfilled by a delegate callback; none has a deadline it depends
   on, and a bounded-wait test that fails under load is re-run alone before anything is
   concluded.
3. **The app suite** for the wiring only: the tab is registered under `.browser`, its targets
   resolve through `HostLinkRouter`, the settings document round-trips, `check-wiring` and
   `check-imports` stay clean.

Every URL in every test is invented (`example.invalid`, `.test`, loopback) — §11, and never
the author's own.

### Q18 — What can only a human witness, and what is conditional? *Decided (D18).*

- **G1 item 26** (a real `python3 -m http.server`, its URL in quick-open, the listing
  rendered) and **G1 item 39** (open a page, switch channels and back, unchanged): the built
  app, a human.
- **G4's Release leg**: a Release build with the Developer toggle off, then on. The Debug
  leg is a package assertion.
- **G2's click half**: `App/Timeline/Rendering` is empty at this pin and no timeline item
  renders a link, so "a `.url` link **from a timeline item**" cannot be clicked yet. This
  leaf proves the whole delivery path — `LinkRouterCapability.open(.url, from:)` reaches the
  Browser target with the link intact and the page loads — and C6's `/login` route is a
  second emitter already on `main`. The click itself is witnessed when C6.1's renderer lands;
  it is recorded as conditional, not as passed.
- **G2's PR half** needs a repository with an open pull request and a logged-in `gh`; the
  resolver is proved headlessly against an invented `gh` document, and the live leg is
  conditional and named as such either way (C7.3's G3 convention).

### Q19 — Store keys and namespaces. *Decided (D19).*

`browser` verbatim to `ScopedStore.write(_:key:)`, per W6 as amended 2026-09-09. The panel
never names a namespace — it cannot; the host bound one — never restates it in a key, and
never reads another tab's key. X6 is ridden, not re-interpreted.

### Q20 — Who owns the shared model, given per-channel sessions? *Decided (D20).*

`BrowserModel` is `@MainActor`, `@Observable`, and owned by the single `BrowserTab` instance
the app registers — **not** by a `PanelTabSession`, which X7 creates one of per (tab,
channel). The per-channel session holds only what is per channel: the quick-open sheet's
state and its subscription to that channel's URL feed. This is what makes item 39 structural:
there is no code path on which a channel switch could produce a second web view, because
there is only one place a web view can be created.

### Q21 — Tab strip mechanics. *Decided (D21).*

A horizontal strip above the content: title, favicon-free, a close control, and a `+`.
Cmd-T opens a tab while the panel has focus. **No Cmd-W override** — that closes windows on
macOS and stealing it inside a panel is the kind of surprise a panel does not get to spring.
No hard cap on live tabs; the persisted document keeps 50 (Q6).

## Grounding probes run before authoring (2026-09-09)

Three questions were measured rather than assumed, because the whole test strategy rests on
them. All three ran in a scratch SwiftPM package outside the repository.

1. **Does `WKWebView` work in a bare `swift test` process?** *Yes.* A `swift-tools-version:
   6.2`, `.macOS(.v26)` test target with no app bundle created a `WKWebView`, set
   `isInspectable`, loaded an HTML string, received `didFinish`, and read back a DOM node's
   text through `evaluateJavaScript`. One test, passed in 0.83 s. This is what allows layer 2
   of Q17 to be in the package suite rather than the app suite.
2. **Does a loopback HTTP server work, and does ATS block it there?** *Works; not blocked.*
   An `NWListener` on `127.0.0.1:0` serving one canned response was loaded by a `WKWebView`
   over plain `http://`, its DOM read back, `view.url?.host` confirmed. 0.31 s. No ATS
   exception exists in a test process, which is precisely why Q14's Info.plist keys are the
   built app's business and are witnessed at G1, not here.
3. **Can a Cmd-click be synthesised from JavaScript to drive `decidePolicyFor`?** *No.* Two
   runs, the second with a deadline on every wait. A `MouseEvent` dispatched with
   `metaKey: true` produced no navigation action at all; `element.click()` on a plain link
   produced one whose type was **not** `.linkActivated`; the first probe, which waited on the
   delegate with no deadline, ran to its 400 s kill without a single callback. Modifier flags
   and `.linkActivated` need a real user event, so the Cmd-click rule is a pure function with
   a delegate adapter (Q11): a test driven by a synthetic click would be a test that cannot
   fail.
   The same probe settled the other half positively: `target="_blank"` and `window.open`
   **do** reach `WKUIDelegate.createWebViewWith` headlessly — twice, with the expected URLs
   and no modifier flags — so Q11's new-panel-tab rule is package-testable as written.

## Surprises & Discoveries

- **`WKWebView` needs no app bundle.** It loads, runs JavaScript and honours `isInspectable`
  inside a bare `swift test` process (probe 1). The Browser panel's real behaviour is
  therefore package-testable, which is not what a `WKWebView`-based panel usually gets.
- **A synthesised DOM click carries no modifier flags into `decidePolicyFor`** (probe 3), and
  a test that waits for one waits for ever. The Cmd-click rule is a pure function with an
  adapter for exactly this reason.
- **No timeline item renders a link at this pin.** `App/Timeline/Rendering` holds a README;
  C6.1's renderer has not landed. G2's click half is conditional on it, and the leaf's own
  half is proved through the routing seam and C6's `/login` route.
- **Q9's table and Q10's "or the URL bar" do not agree.** Q9 row 2 takes only `http`, `https` and
  `about` as typed, so a `mailto:` typed into the bar falls to row 5, is handed `https://`, and
  ends as "not a URL" — while Q10 names the URL bar as a user gesture that hands *other* schemes to
  the system opener. M2 implements Q9's table as written and leaves the gesture path reachable
  through `NavigationRequest.urlBarEntry`, which takes a `URL` rather than a typed string, so the
  policy layer has no dead branch. Widening row 2 to "any valid scheme, as typed" would reconcile
  the two and is a one-line change; it is the parent's to rule, and is filed under
  *Parent revisions* rather than taken here.
- **A restore that loses a race loses the document, not only the tab list.** A1 was written up as
  "either the saved tabs are overwritten before being read, or an arriving restore discards the page
  the user just clicked". Measured with the store's read held open, it is both at once and worse:
  the click's structural write reached the store *while the read was suspended*, so when the read
  was released it returned the one-tab document the click had just written. The saved set was gone
  from disk before `load` ever answered. Ordering the two is the fix either way; the measurement is
  why the test asserts the surviving tab count and not only the selection.
- **A page cannot see the registered script message handlers, but it can see `window.webkit`**
  (M3). `Object.getOwnPropertyNames(window.webkit.messageHandlers)` is empty whether a handler is
  registered or not — found when the mutation that registered one failed to redden the test that
  was supposed to catch exactly that. WebKit creates `window.webkit` **at all** only when at least
  one handler exists, so the assertion Q12 wanted is `typeof window.webkit === "undefined"`, which
  is also the stronger claim: page content has nothing in this app to call, not merely nothing to
  enumerate.
- **Nothing the policy refuses is something WebKit would load anyway** (M3). A mutation that told
  WebKit `.allow` for every decision reddened no test: `navigate(to:)` decides before it loads, and
  `javascript:`, `data:`, `file:` and `mailto:` are all schemes WebKit declines by itself, so "the
  tab did not move" cannot tell an allow from a cancel. `WKNavigationAction` **traps** when
  constructed outside WebKit (a subclass standing in for one killed the test process with SIGTRAP),
  so the answer is read instead from a named `BrowserWebTab.answer(to:)`. Two tests exist because of
  this that would not otherwise: that mapping, and two pages that navigate *themselves* to a
  `mailto:` and to a `data:` URL — the delegate's own refusal path, which `navigate(to:)` never
  reaches.
- **`target="_blank"` and `window.open` take different routes** (M3, refining probe 3). With this
  delegate in place a `_blank` link never reaches `createWebViewWith`: `decidePolicyFor` sees no
  target frame first, cancels, and asks for a new panel tab. `window.open` is the only caller of
  `createWebViewWith` left. Both still land on the same callback, which is the contract, but each
  needs its own test — a mutation that gutted `createWebViewWith` reddened only the `window.open`
  one.
- **`didFinish` is not when a page's title is known** (M4). A model that took the URL and the title
  at the settled navigation persisted every page under the previous page's title: WebKit publishes
  `title` some runloop turns after the navigation finishes. The fix is not a longer wait — it is to
  follow the chrome state and commit on every change, which is what Q6's trailing window already
  assumes ("a single navigation fires several"). Found by the coalescing test on its first run,
  which is the only assertion in the leaf that reads a *persisted* title rather than a live one.
- **A mutation that hangs the suite is worse than one that reddens nothing** (M4). Removing that
  chrome tracking produced no failing test and no passing one: the model stopped committing edits
  at all, and the coalescing test's `waitForSleep` — an M1 seam with no deadline — waited for a
  window that was never going to open. The suite ran to a 900-second kill. M1's continuation-shaped
  waits were given expectation-shaped twins (`expectWriteAttempts`, `expectSleep`) so every M4 wait
  carries the deadline the ledger's *Idempotence* section requires, and the mutation then named its
  test.
- **A request count is not an assertion about a request that has not been issued yet** (M4). The
  mutation that let `restore()` run twice reddened nothing: the second restore rebuilds the tab set
  and re-navigates, but the reload is asynchronous and the count read on the next line is still one.
  The tab list's *length* is identical either way too, so the only synchronous difference is object
  identity — `XCTAssertIdentical` on the live tab and on its web view. The test was the bug.
- **`ChannelContext.store` is namespace-scoped, not channel-scoped.** C5's
  `WorkbenchScopedStore` passes keys through unchanged and pins only the namespace, so W6's
  window-wide `workbench.browser` key needs no host change to be genuinely shared.

- **The Q1 ruling's mechanism could not be implemented where it was written.** The gate ruled that
  `HostLinkRouter.open` passes **no** `prepare` for a target that declines the pop-out. The host
  cannot do that: it hands `prepare` in before the registry resolves, so at the moment it decides,
  the target is unknown. The behaviour the ruling names — no pop-out, and the delivery on the path
  that does not suspend — is reachable only from inside `LinkRouter`, which is where it now lives
  (one condition, D40). The ruling's *intent* is met exactly; its *location* was wrong, and the
  correction is a second boundary edit rather than a re-reading.
- **A mutation that reddened less than it should have, and the test that was the bug.** Deleting the
  resolver's exit-code check first reddened only the auth-hint test: with the check gone, a failing
  `gh` prints nothing, the empty document fails to decode, and the row that results is *also*
  hintless — so the "not a pull request" test could not tell the two apart. §17.7 says the test is
  the bug. It now also asserts the row names the exit status, which only the read path can produce,
  and the mutation re-run red on it.

## Decision Log

D1–D21 are the *decided* answers of the Residue section above, in that order; each carries
its rationale and its rejected alternatives there rather than being restated here. New
decisions taken during execution are appended below with a date.

- **D22 (2026-09-09, M1).** A read that *throws* — a corrupt or undecodable document — is not in
  Q6. It opens empty with a `documentUnreadable` error row, and the next write replaces the
  document. The newer-schema case is the only one that refuses writes, because it is the only one
  where the bytes are another build's property.
- **D23 (2026-09-09, M1).** The 50-tab cap is a *persistence* cap and is applied on read as well as
  on write. A selection inside the dropped prefix clamps to the first surviving tab: reopening on a
  page beats reopening on none. Q21's "no hard cap on live tabs" is honoured — `current` keeps all
  sixty.
- **D24 (2026-09-09, M1).** `BrowserTabStore` is an actor with a `settle()` seam that returns once
  the window in flight has reached its decision. Without it, "the superseded window wrote nothing"
  and "the superseded window has not run yet" are the same write count, and the assertion is a
  race. `flushPendingEdits()` exists for the same reason a coalescer needs one: a title typed into
  the last half-second before the panel goes away is exactly the thing a relaunch must not forget.
- **D25 (2026-09-09, M2).** `about:blank` loads; any other `about:` URL is `.refuse(.unsupportedURL)`.
  Q10 names `about:blank` and nothing else, and the rest of the scheme is WebKit's internal surface.
- **D26 (2026-09-09, M2).** `Reason` carries `isDiagnosticOnly`. Q10 distinguishes a `file:` link
  the user clicked (owed an answer) from a page redirecting itself to an app scheme (dropped with a
  diagnostic); without the flag the panel would have to re-derive that distinction at every call
  site, and one of them would get it wrong.
- **D27 (2026-09-09, M2).** `NavigationRequest.urlBarEntry(_:)` is the URL bar's adapter, marking a
  typed URL as user-initiated. Q10 names the URL bar as a gesture alongside `.linkActivated`;
  putting it in one constructor keeps the flags from being assembled by hand at each call site.
- **D28 (2026-09-09, M2).** Q9's row 3 is read as covering bare loopback hosts, not only the
  spellings with a port: `127.0.0.1` and `[::1]` with no port contain dots (or are bracketed) and
  would otherwise fall to row 5 and be handed `https://`, which is the same silent failure the row
  exists to prevent, one hop along.

- **D30 (2026-09-09, M3).** The chrome state is its own `@Observable` type, `BrowserChromeState`,
  rather than observable properties on `BrowserWebTab`. The tab is an `NSObject` because WebKit's
  delegates are `@objc` protocols; keeping the two apart means the SwiftUI chrome depends on six
  values and not on a delegate, and the tests wait on the state rather than on the tab.
- **D31 (2026-09-09, M3).** `isUserInitiated` is read from the navigation type — a link activation
  or a form submission — because WebKit publishes no "a person did this" flag and afleet uses no
  SPI. A URL bar entry never goes through the adapter at all; it is built by
  `NavigationRequest.urlBarEntry`. The redirect tests prove the translation: a page that navigates
  itself to a `mailto:` is dropped, so the gate is genuinely closed for a script.
- **D32 (2026-09-09, M3).** `BrowserWebTab.navigationDidSettle` is a public callback rather than a
  test-only affordance: M4's model commits a URL and title to the persisted tab set from it, and the
  tests use it so that no wait in this leaf is a sleep. It is one closure, not a listener list;
  a second listener is M4's problem if M4 has one.
- **D33 (2026-09-09, M3).** `createWebViewWith` runs the policy too, with `hasTargetFrame` forced to
  `false`, so a `window.open('javascript:…')` is refused by the same branch that refuses a typed
  one, rather than being trusted because WebKit asked politely.

- **D34 (2026-09-09, M4).** A tab with no URL — the `+` control, Cmd-T — is **not** in the persisted
  document. `PersistedTab.url` is not optional and a blank tab has no page to restore; writing
  `about:blank` for it would restore a tab that reopens on nothing. The selection then has to land
  on a tab that survived, so it clamps back onto the last persisted tab before it: the same rule D23
  applies to the dropped prefix, for the same reason.
- **D35 (2026-09-09, M4).** The model commits a URL and title on **every observed change to the
  chrome**, not only at `navigationDidSettle`. WebKit publishes `title` after `didFinish`, so a
  settle-only commit persists the previous page's title (measured; see *Surprises*). D32's callback
  keeps its purpose — it is what a test and a later surface wait on — and is no longer the
  persistence trigger.
- **D36 (2026-09-09, M4).** `BrowserModel` serialises its writes behind one `Task` chain. The store
  is an actor and every commit is a hop, so two commits spawned independently could reach it in
  either order and the loser would become the panel's persisted truth. `persistenceSettled()` is the
  chain's `settle()` seam, for the reason D24 gave the store one: without it "the coalescer is
  holding this edit" and "the edit has not arrived yet" are the same write count.
- **D38 (2026-09-09, R2 fix wave). The navigation type is deleted as an authorisation input.**
  `NavigationRequest.isUserInitiated` is gone — not deprecated, not kept as a diagnostic field a
  later reader might trust — and `NavigationOrigin` (`.pageContent` or `.urlBar`) takes its place as
  the only authorising input in the module. Exactly two things authorise leaving the app:
  1. an `http`/`https` URL through the Cmd-click path, because the modifier flags come from a real
     `NSEvent` (probe 3: a synthetic click produces neither `.linkActivated` nor modifier flags) and
     because opening a web URL in the user's own browser is not a privileged operation; and
  2. any scheme entered in afleet's URL bar — a native action page content cannot reach, carried by
     `NavigationRequest.urlBarEntry`.

  Everything else is `.refuse` and never reaches `NSWorkspace`. `Reason.schemeNeedsAUserGesture` is
  renamed `Reason.externalSchemeFromPageContent`, because there is no gesture being checked for and
  a name that says there is would re-teach the mistake.

  **Why the old rule was wrong, stated as facts rather than as caution.** WebKit classifies a form
  submission as `.formSubmitted` whether a person pressed the button or a script called
  `requestSubmit()` — the tests below drive both, plus `form.submit()`, and all of them reached the
  external opener before this change. The classification is the same inside a subframe. And a server
  redirect reuses the action that triggered it, so a clicked link to a loopback page can arrive at a
  `mailto:` still wearing `.linkActivated`. `isUserInitiated` was therefore not a fact about a user;
  it was a fact about what kind of navigation WebKit thought this was.

  **Rejected alternatives.** *Keeping the type and adding checks* (frame is the main frame, no
  redirect chain, and so on) — every one of those is another thing WebKit reports rather than
  something it authenticates, so it buys defence in depth against an attacker who was never
  constrained. *Prompting the user before opening an external scheme from a page* — a dialog on a
  navigation the user never asked for is a dialog trained to be dismissed, and it puts the decision
  where the least information is; the affordance the review suggested is filed as tracker 248 as
  usability, not correctness. *Keeping `isUserInitiated` as a diagnostic-only field* — rejected on
  the grounds the ruling states: a field named for authority is one a later reader will use for it.
- **D39 (2026-09-09, R2 fix wave). The `javascript:`/`data:` guarantee is narrowed to what is
  enforceable, and the real behaviour is pinned by a test.** D29's wording said both schemes are
  refused "from any source at all". That over-states the seam. What is enforceable, and now written
  where the code says it:
  - the URL bar refuses both — the case that matters, because a `javascript:` URL pasted into an
    address bar runs in the origin of the page the user is *reading*;
  - any navigation WebKit dispatches for policy is refused;
  - a **page-originated** `javascript:` URL is executed by WebKit's policy checker without the
    navigation-policy callback being dispatched at all, so the deny-list never sees it.

  Measured on this runtime, three ways (`location.href =`, `location.assign(...)`, a scripted click
  on an `href="javascript:…"` anchor): all three execute, none reaches the delegate, none reaches
  the opener, and the document's URL does not change. A top-level page-originated `data:`
  navigation goes the other way — it *is* dispatched, and is refused. The contrast is the whole of
  this decision, and both halves are now tests.

  The code is not under-built; the claim was over-written. The page gains nothing by this: the
  script runs in its own origin, which a `<script>` tag already granted it, and there is no bridge
  to reach (Q12's `typeof window.webkit === "undefined"`). **Rejected: disabling content JavaScript**
  (`defaultWebpagePreferences.allowsContentJavaScript = false`), which would close the gap and also
  break every dev server and the pull-request page this panel exists for — the panel would stop
  doing its job to remove a capability the page already had.
- **D37 (2026-09-09, M4).** Q5's pop-out is modelled as one `attachedTo: BrowserSurface` on the
  shared model, and `rendersWebViews(on:)` is what a surface asks. The view renders the web views
  when it is that surface and the short "Showing in the Browser window" state with a *bring them
  back* control when it is not. No handover protocol, no second web view, no per-surface state: an
  `NSView` has one superview, and one field is the whole of what that fact requires.

- **D40 (2026-09-09, M5). X7's `popsOutForNewWindow` is honoured by the registry, not by the host.**
  The field is C5's (`PanelHostAPI`), as ruled. The *skip* is C7.2's (`LinkRouter`), because only
  the registry knows which target a link resolved to — `HostLinkRouter` hands its pop-out in before
  resolution begins. It is expressed as not calling the hook rather than as a hook that returns
  immediately, because calling it is what makes the actor suspend between resolving and delivering,
  and every hazard `open(_:from:prepare:)` documents lives in that suspension. Two boundary edits,
  both declared: C5's fence for the field, C7.2's for the one condition. *Rejected:* a set of
  declining tabs kept on `HostLinkRouter` (a second registry, which that type's own doctrine
  forbids, and still unable to say which target wins); a no-op `prepare` (the thing the ruling
  ruled out).
- **D41 (2026-09-09, M5). The Browser claims `.url` and `.pullRequest` at specificity 10, and both
  targets decline the pop-out.** Low by design: the Browser knows a link is *a page*, and a panel
  that knows more about a particular link should win by registering higher — C7.7's source-control
  panel is the expected case for `.pullRequest`. Two targets rather than one with a compound
  `handles`, so that a later panel can out-bid one of them without inheriting the other.
- **D42 (2026-09-09, M5). A link the panel could not open is a `BrowserLinkError` row with an
  optional hint, and never a message a tool printed.** §10 makes a tool failure panel-local; §11 and
  §6.3 make a rendered error a published byte, and `gh`'s stderr carries hosts, accounts and
  repository paths. The tail is read to *classify* — is this failure about not being signed in? — and
  never quoted; the row names the tool, the exit status and the pull-request number the user just
  clicked. The `gh auth login` hint is attached only to a failure that mentions authentication,
  because `gh pr view` exits 1 both for a missing login and for a number that is not a pull request,
  and offering the login remedy for the second sends the user to re-authenticate over a typo.
- **D43 (2026-09-09, M5). The host is asked to show the Browser tab through an injected closure.**
  `PanelHost.select(_:)` is what makes the tab visible, and a package module cannot hold the host: a
  panel holding its host is a retain path, and X7 hands panels capabilities rather than the host
  itself. `BrowserLinkTargets.make` therefore takes `selectBrowserTab: @MainActor @Sendable () -> Void`,
  which M6 fills with `host.select(.browser)`. It is called for `.currentPanel` and for a failed
  in-panel lookup — the row is worth nothing in a tab nobody is looking at — and never for
  `.newWindow`, which is not going to the panel at all.

- **D44 (2026-09-09, M6). The tab is registered in the initialiser; its link targets are awaited at
  the top of the launch.** `PanelHost.register` is X7's synchronous member and
  `LinkRouterCapability.register` is `async` — the registry is an actor — so the two cannot both be
  taken in `AppModel.init`. A detached `Task` was rejected: it leaves open exactly the window the
  targets exist to close, in which a link resolves to nobody and W5's fallback hands it to the
  system browser. The launch is the earliest awaitable point, and it is *provably* early enough: a
  `WorkspaceLink` can only be opened through a `ChannelContext`, no context exists until
  `bindWorkspace`, and `bindWorkspace` runs inside the same `performLaunch`, after the registration.
  The registration is guarded by a flag because *Check again* runs the launch again and a second
  pass would leave two indistinguishable targets per kind, tying on specificity.
- **D45 (2026-09-09, M6). The Browser's store is bound late, not constructed late.** The tab is
  built in `AppModel.init` (Q4) and the store a launch reaches exists only at `bindWorkspace`, so
  the panel is handed a `DeferredWorkbenchStore` whose backing store is set there. It is
  `WorkbenchScopedStore` with one indirection, so W6's namespace pin stays in the type that owns
  it; before the bind it reads nothing and writes nothing, which loses nothing because the call
  that binds it is the same call that makes the first `ChannelContext` — and a panel renders only
  from one. *Rejected:* registering the tab at `bindWorkspace` instead, which would re-register on
  every *Check again* and make Q4's "once" a property of how many launches happened.
- **D46 (2026-09-09, M6). Q14's ATS keys are declared in `project.yml`, not in `App/Info.plist`.**
  The plist is **generated**: XcodeGen rewrites it whole from `targets.Afleet.info.properties` on
  every `make generate`, so the keys written into the file by hand — and the paragraph explaining
  them — were gone after one build. Measured, not assumed. The keys and their reasoning therefore
  live in `project.yml`, which is a source file and takes comments, and the regenerated plist is
  committed alongside it. This is Q14's own "comment the reasoning where the file allows, or in the
  ledger if it does not", answered by a third place that is better than either.
- **D47 (2026-09-09, M6). The inspector setting is read at launch, not live.** The panel's factory
  asks its policy synchronously inside `makeWebView`, which cannot await a store, so the setting is
  mirrored into a `WebInspectorSwitch` by the launch that read it — the shape `RawCaptureSwitch`
  already has for *Capture raw frames*. It therefore takes effect on the next launch, which is what
  the Developer section says of every setting in it except raw capture, and the toggle carries that
  caption. Making it live would mean handing the switch to `SettingsReadout` as well; nothing asked
  for that, and a Debug build is inspectable regardless.

- **D48 (2026-09-09, fix wave A). A tab remembers only a destination the policy loads in the panel.**
  Everything a tab remembers is dispatched again at restore, through `activate`, as a
  `NavigationRequest.urlBarEntry` — which D38 makes the one origin that authorises handing a
  non-web scheme to the system. So a destination that was refused or opened externally must never
  become a persisted one, or a relaunch mints the strongest authority in this design for a URL
  nobody typed. `BrowserModel.destinationForPanel` is the one gate, read by `openNewTab`, by
  `open(_:in:)` and by the restore itself — the last of those so that a document already holding
  such a URL, written by hand or by a build before this rule, is neutralised on the way in rather
  than dispatched. The tab survives with no URL, which is self-healing: the next snapshot drops it.
  *Rejected:* refusing the navigation outright at the model (the user typing `mailto:` into the bar
  is D38's own accepted case, and the panel is not the place to take it back); dropping the whole
  tab at restore (it moves the selection, and a set that comes back a tab short is a worse answer
  than one tab showing its title).
- **D49 (2026-09-09, fix wave A). One restoration, and every caller joins it.** `restore` is a task
  held on the model rather than a boolean guard, because the two callers are not alike: the panel's
  `.task` asks when it is drawn, and a routed link asks *before* the panel has ever been drawn. A
  guard that returned early let the second caller mutate the tab set in front of a read the first
  was still waiting on — and this method replaces the set whole. Routed mutation goes through
  `openRouted`, which awaits the restoration and then does exactly what `open` does. *Rejected:*
  restoring eagerly at construction (the store is bound at `bindWorkspace`, later than
  `AppModel.init`, so there is nothing to read from yet); making `restore` non-replacing, i.e.
  merging the document into whatever is there (two sources of truth for the tab strip's order, and
  no rule for the selection that is not a guess).
- **D50 (2026-09-09, fix wave A). The store tells the panel what happened; the panel does not ask.**
  `commitEdit` returns as soon as it has opened its window, so a caller sampling `lastError` at the
  commit samples the write *before* it — which is how a document from a newer build could refuse
  every write for the life of the process while the panel drew ordinary editable tabs. The store
  takes one observer, installed by `restore` before the first read, and calls it after every write.
  What the panel shows for it is a quiet row under the URL bar and never an alert: §10 makes this
  panel-local, and the tabs still work — what the user needs to know is that they are not being
  kept. *Rejected:* making `commitEdit` async to its write (that is the coalescer, deleted); polling
  `lastError` from the panel (a row that lags by a poll interval is a row that lies).
- **D51 (2026-09-09, fix wave A). The channel a routed action came from travels with the action,
  as a task-local.** `HostLinkRouter` already states the rule and already takes the capture for its
  pop-out; what was missing is that a *target's handler* needs the same value and runs where the
  host cannot reach it — inside the registry, two suspensions later. `LinkOrigin.channel` is set for
  the whole routed call and read by the Browser's pull-request resolver, so a window that moves
  channels while a link is in flight cannot make one channel's number resolve against another's
  repository. `nil` outside a routed action, which is Q3's row and never a guess. *Rejected:*
  carrying the channel on `LinkTarget.open` (an X7 amendment on C5's fence for a value only one
  target wants); a stored property on `HostLinkRouter` (two links in flight clobber each other).

- **D52 (2026-09-09, fix wave B). The preparation budget belongs to the target that asks for a
  preparation.** `LinkRouter.open` read X7's `popsOutForNewWindow` *after* the
  `maxPreparationsPerOpen` bound and after the prepared-tab equality guard, so a target that needs
  no window at all could be refused by two costs it never incurred: a chain of handovers that spent
  the bound on targets wanting windows, and a prepared target withdrawn under the call leaving a
  different tab's declining target to be found. A `.pullRequest` took W5's diagnostic fallback in
  both, which drops the link. The opt-out is read first; everything below it is unchanged and is
  now, by position, the cost of a preparation. *Rejected:* raising the bound (the bound is what
  stops a tab that hands itself over for ever, and the finding is not about its size); charging the
  declining target and letting it re-resolve (there is nothing to re-resolve to — it is the live
  answer). A **boundary edit on C7.2's fence**, kept to one guard's position.
- **D53 (2026-09-09, fix wave B). The rendering surface is an input to X7's `makeView`.** A panel
  is drawn in two places and could not tell them apart, so `BrowserTab` hard-coded `.panel` and
  both surfaces rendered the same `WKWebView`s — D37's exclusive ownership, the placeholder that
  explains it, and the hand-back on close were all unreachable, and every channel's pop-out shared
  the one model. `PanelSurface` joins `PanelHostAPI`; `PanelTab.makeView` and
  `PanelHost.view(for:context:surface:)` take it, with **no default**, because a caller that may
  omit it is a caller that can claim to be the main panel from inside a window.
  `BrowserPanel`'s own `BrowserSurface` is deleted rather than mapped: it was the same enum one
  module down. `BrowserTab.panelView(session:surface:)` exists so a test can ask which surface a
  view was made for, which an `AnyView` cannot be asked. *Rejected:* a SwiftUI environment value
  (it would work, and it would leave the surface unreadable to the model and untestable — the
  seam would be honest and the guarantee would not be checkable); a stored "which surface is
  frontmost" on the host (two windows, one truth, and nothing to say who writes it).
- **D54 (2026-09-09, fix wave B). The pop-out claims the web views; the main panel never does.**
  Attachment follows the two surfaces' own lifecycle — `surfaceAppeared` and `surfaceDisappeared`,
  called from the view that is being drawn — rather than from the host's pop-out registry, because
  the registry records that a window was *asked for* and the views must move when one is actually
  on screen. The panel is on screen for as long as its window is, so a panel that claimed on
  appearance would take the pages back from a pop-out on the next re-render of the column, which is
  the whole of what a pop-out is for; only the window claims, and a surface that goes away hands
  back what it was holding. `attach(to:)` stays as the one deliberate move, which is what the
  "Bring them back here" control is.
- **D55 (2026-09-09, fix wave B). The address field is a value type outside the view.** Two rules
  live in it and neither is expressible in an `onChange`: a page that moves does not overwrite a
  draft (editing begins at the first keystroke and ends at a submission or at focus leaving), and a
  field drawn over a settled page opens on that page. The second is a consequence of the host's own
  identity rule — `view(for:)` gives every (tab, channel) pair its own SwiftUI identity, so a
  channel switch rebuilds this state while the shared tab set does not change at all, and a field
  that only followed changes opened blank over a page plainly on screen. *Rejected:* holding the
  text on `BrowserModel` (it is per-surface state, and two surfaces would share one caret);
  a two-way binding onto the page's URL (that is the clobbering, spelled differently).
- **D56 (2026-09-09, fix wave B). A failed load is a classification and a row, and a cancellation
  is not a failure.** `didFail` and `didFailProvisionalNavigation` discarded their `Error`, so a
  dropped connection, an unresolved name and a refused certificate all left the panel silent on
  the page before. `BrowserChromeState.failure` records what happened, `BrowserModel` derives one
  line from the *selected* tab's chrome — derived and not stored, so it follows the selection and
  is cleared by that tab's next navigation with nothing having to remember to clear it — and the
  panel draws it quietly (§10: a page that does not load is ordinary). Only the error's **code** is
  read: an `NSError`'s description and user info carry the host and the path, and a rendered line
  is a published byte (§11). Cancellations are dropped, because this panel issues them itself for
  every policy refusal and the stop control is one the user asked for. The stop control's own
  half of B3 lives with it: which of two actions the round control performs is decided in the
  model, where a test can fail on it, and not at the button.
