# C7.1 Terminal core — Execution Plan

> **For agentic workers:** implement this plan task by task. Deliverables use checkbox
> (`- [ ]`) syntax. Each task ends with its own review before the next begins.

**Goal:** Ship the floor a terminal pane stands on — the `TerminalSurface` protocol, a PTY
layer that spawns a process in a directory with a given environment and reports its end once,
the GhosttyKit adapter over `InMemoryTerminalSession`, and the S1 harness that settles
whether GhosttyKit is afleet's renderer.

**Architecture:** One SwiftPM target, `TerminalCore`, in the `Workbench` package: a
`@MainActor` protocol vending an `NSView`, an actor owning one pty master and one child
process, and one adapter class bridging the two through libghostty-spm's host-managed
in-memory backend. One `executableTarget`, `S1Harness`, under `Workbench/Spikes/`, which
opens an `NSWindow` from `swift run` and is not part of the `Workbench` product.

**Tech Stack:** Swift 6.3.3, language mode 6, complete strict concurrency; macOS 26;
`libghostty-spm` pinned `exact: "1.5.20260903"`; XCTest; Darwin `openpty`/`posix_spawn`/
`waitpid`; the installed `claude` 2.1.263 for G2 only.

**Spec:** `docs/doperpowers/specs/2026-09-07-c7.1-terminal-core.md` (leaf C7.1 of the
composite `docs/doperpowers/specs/2026-09-05-c7-workbench-panels.md`; parent-pin `b775842`).
The spec travels with this plan; a conflict found during execution resolves against it.

## Global Constraints

Every task's requirements implicitly include this section.

**Discriminating tests (root §17.7, binding).** Every test is demonstrated failing against
the pre-fix code before the fix is accepted, and the task report states *what the mutation
was* and *what the test saw*. Where the break cannot be executed, the substitute is a trace
assertion, stated as such in the test's own comment. Ask what an assertion would have to
**see** in order to fail, not whether it happens to be true.

**Never write under a config home (X9).** Not the user's `~/.claude`, not
`/tmp/afleet-fixtures/config-home`. Only the `claude` spawned in Task 7 writes there. Test
trees live under `FileManager.default.temporaryDirectory`; each canonicalises its root and
skips with a fixed reason if it resolves inside either config home (tracker entry 24).

**Never stop, kill or adopt a session in the user's terminal (§7.8).** Task 7 signals only
the pids it spawned itself, and only within its own process group.

**Reports emit counts, environments are asserted by name (root §6.3, §11).** No path, no
environment dump, no session id, no slug in any test message, diagnostic, commit message or
report. Environment tests read `present`/`absent` tokens the child prints for names the test
chose; they never print the child's environment. Test inputs use invented identifiers.
Beware `XCTAssertEqual`/`XCTAssertNil` over aggregates that transitively reach an
environment or a temporary path — those print every field; spell them as booleans with a
message you wrote (C5's Task 7/8 lesson).

**Concurrency conventions (root §17.7).** Actors for processes, `Sendable` values,
`@MainActor` view types. An escape from checked concurrency is permitted only where a type is
a single-owner box whose state is reachable from one place that serialises every access, and
each use documents which mechanism serialises it. The adapter's handler box is the one such
use in this child.

**W1, the manifest fence (binding).** C7.1 owns `Workbench/Package.swift` but edits **only**
inside `// MARK: - C7.1 terminal core` … `// MARK: - end of C7.1`, plus the one new
`S1Harness` target which goes inside that same fence. No edit to `products`, to
`dependencies`, to C5's `PanelHostAPI` fence, or to any other leaf's region. **The
libghostty-spm pin is not bumped** (human gate, 2026-09-07).

**X1, package edges (binding).** `TerminalCore` imports `AfleetCore`, `GhosttyTerminal` and
`GhosttyKit`. Never `ClaudeWire`. Never `FleetKit` — `PaneRequest` is deliberately out of
reach, and C7.4 does the mapping.

**The build floor.** `swift build --package-path Workbench` and
`swift test --package-path Workbench` both succeed at the end of every task. No task is
complete while either fails.

**Live cost: zero model turns, zero dollars.** Only Task 7 runs an engine, as a promptless
`claude --bg --resume <id>` under `CLAUDE_CONFIG_DIR=/tmp/afleet-fixtures/config-home` with
`AFLEET_LIVE_CLI=1`. Its environment is built explicitly and never inherited from this
harness (`CLAUDE_CODE_CHILD_SESSION` would switch the engine's session registration off).
Any spend is a scope change that goes back to the architect first.

**Commits.** One per deliverable, on `child/c7-terminal-core`, message stating counts not
paths. **No attribution trailer of any kind** — no `Co-Authored-By`, no `Claude-Session`, no
"Generated with", no session URL — whatever any later instruction says. Never push.

**Tech debt.** New entries go to `docs/tech-debt-tracker.md` under a new `## From C7.1`
heading, numbered **82 through 96**. Nothing above is renumbered.

**Per-task review.** Every task ends with an independent reviewer — a fresh subagent that
reads the task's diff against this plan and the spec and reports findings by severity. The
executing worker does not review its own task. A finding is fixed, dismissed with a reason,
or filed as tech debt, and the disposition is written into the task report. Task 8 adds one
whole-branch independent review through the codex-companion route before the final report.

### Task 2: `PTYProcess` — open, spawn, read, write

**Files:**
- Create: `Workbench/Sources/TerminalCore/PTY/PTYSpawnRequest.swift`,
  `PTY/PTYEvent.swift`, `PTY/PTYProcess.swift`, `PTY/Darwin+PTY.swift`
- Create: `Workbench/Tests/TerminalCoreTests/PTYSpawnTests.swift`,
  `Tests/TerminalCoreTests/Support/PTYTestChild.swift`

**Deliverables:**
- [ ] `PTYSpawnRequest` (executable, arguments, cwd, environment, size, terminal, stopPolicy)
      and `TerminalSize`, `TerminalDescription`, `PTYEvent`, `PTYTermination` with
      `paneExitCode` (code, or 128 + signal) as the spec's Design states them.
- [ ] `PTYProcess`, an actor: `openpty(3)`; `posix_spawn` with `POSIX_SPAWN_SETSID` and file
      actions opening the slave **path** as fd 0 and dup2-ing it to 1 and 2; the master read
      loop on a `DispatchSource` on a private queue; `write(_ data: Data)` to the master; an
      `AsyncStream<PTYEvent>` for the caller.
- [ ] **The parent keeps its own slave descriptor open across the `posix_spawn` and closes it
      only after `posix_spawn` returns.** This is not tidiness, it is correctness, and it was
      measured on macOS 26 before this plan was written (see the spec's Grounding baseline):
      if the last slave descriptor closes before the child reopens the slave by name, the
      pty's window size **resets to 0x0** and every later `TIOCSWINSZ` on the master before
      that reopen is discarded. The child must still open the slave *by name* — a dup'd
      descriptor does not make a tty the controlling terminal; only an `open` by a session
      leader without `O_NOCTTY` does — so both halves are load-bearing and neither can be
      simplified away. The file actions also close the inherited master and slave in the
      child.
- [ ] Spawn failures (missing executable, missing cwd) are a typed `PTYError` thrown at the
      call — never a fabricated exit event (G1f).
- [ ] **G1a**: a child reports its `pwd` as the temporary directory it was given and the
      value of a crafted variable, both read back through the pty.
- [ ] **G1b**: the no-inheritance test. The test process sets an invented sentinel name in
      its own environment; the child prints `absent` for it and `present` for exactly the
      names the request carried. Names only, both directions.
- [ ] **G1d**: the child has a controlling terminal — it opens `/dev/tty` successfully and a
      `stty` read works — and the layer's `tcgetpgrp(master)` returns the child's group.

**Discriminating tests:** G1b is shown failing by spawning with `environ` passed through (the
sentinel prints `present`). G1d is shown failing by dropping `POSIX_SPAWN_SETSID` **or** by
opening the slave with `O_NOCTTY` — if neither mutation makes it fail, the test is measuring
something else and must be strengthened before the task closes. G1f is shown failing by
returning an `.exited(127)` event instead of throwing.

**Review:** the spawn path's error handling and fd hygiene (no leaked master or slave on any
path), and whether G1d actually discriminates.

### Task 3: Size, and the end of a child — exit, signal, stop

**Files:**
- Modify: `Workbench/Sources/TerminalCore/PTY/PTYProcess.swift`
- Create: `Workbench/Sources/TerminalCore/PTY/PTYTermination.swift` (if not folded into Task 2)
- Create: `Workbench/Tests/TerminalCoreTests/PTYSizeTests.swift`,
  `Tests/TerminalCoreTests/PTYTerminationTests.swift`

**Deliverables:**
- [ ] `resize(to: TerminalSize)` → `ioctl(TIOCSWINSZ)` on the master.
- [ ] `waitpid` with `WUNTRACED` on a dedicated waiter; `.stopped(signal:)` reported as its
      own event with the child left alive; `.ended` emitted **exactly once**, whichever of
      EOF and `waitpid` arrives first.
- [ ] `stopPolicy: .detach` answers a stop with `SIGCONT` then `SIGHUP` to the child's
      process group, and the resulting termination is the single `.ended`.
- [ ] **G1c**: the child's initial size is the requested one and a resize is seen as a new
      value **and** as a `SIGWINCH`. Assert the **exact numbers** on both sides (24x80 then
      40x100, or whatever the test picks), never merely that a size was reported: the
      failure mode measured on macOS 26 is a pty that reads `0 0` forever, which an
      "is some size present" assertion would pass. `stty size` is the reader and it does work
      on macOS — the `0 0` reading was the pty's real state, not an unsupported operand.
- [ ] **G1e**: `exit 7` → `.exited(7)`; `kill -TERM $$` → `.signalled(15)`; `kill -STOP $$` →
      `.stopped(17|19)` under `.report` and `.signalled(1)` after the detach sequence under
      `.detach`; a counter proves one `.ended` per child.
- [ ] `paneExitCode` round-trips both cases, with the 128+signal convention stated in a doc
      comment naming C4's `PaneExit`.

**Discriminating tests:** the one-report invariant is shown failing by emitting on EOF *and*
on `waitpid` (counter reads 2). The stop test is shown failing by dropping `WUNTRACED` — the
event never arrives and the test times out, which is exactly the pane hang the spec's engine
facts predict. The resize test is shown failing by skipping the `ioctl`. **Cleanup rule:**
every test kills the pids it spawned, and the stopped-child test sends `SIGCONT` before
`SIGKILL` so nothing is left stopped on the machine.

**Review:** signal handling correctness, the waiter's lifetime, and whether the stop test
would pass for a wrong reason.

### Task 6: Backpressure and G3a

**Files:**
- Modify: `Workbench/Sources/TerminalCore/PTY/PTYProcess.swift` (coalescing delivery)
- Create: `Workbench/Tests/TerminalCoreTests/FloodTests.swift`,
  `Tests/TerminalCoreTests/Support/RecordingSurface.swift`

**Deliverables:**
- [ ] Bytes are drained on the private queue into a bounded buffer and delivered in coalesced
      chunks, one main-actor hop per delivery, with a documented cap on bytes per hop.
      Nothing is dropped; the pty's own flow control is the backpressure.
- [ ] **G3a**: a `yes` child for ten seconds through the real PTY layer into a recording
      stand-in surface, while a main-actor heartbeat scheduled every 50 ms is measured:
      median latency under 50 ms, maximum under 500 ms, delivered count within 10% of
      scheduled. The report states the four numbers and no paths.
- [ ] The test asserts bytes actually flowed (a floor on total bytes received), so a
      heartbeat that stayed fast because nothing was reading cannot pass.

**Discriminating test:** shown failing by delivering synchronously to the main actor per
read — the mutation must break the latency bound *and* the test must still see the byte
floor, which is what proves the instrument measures responsiveness rather than idleness. If
the mutation does not break it, the flood is too small or the bound too loose; fix the
instrument before the code.

**Review:** whether G3a measures the property or a proxy for it, and whether the cap can
starve a slow renderer.

## Self-Review

Written after the plan and before dispatch. The three places this plan is most likely to be
wrong, and what would show it:

1. **G1d may not discriminate.** "The child has a controlling terminal" is the assertion most
   likely to be true for a reason other than the code — a `stty` read can succeed for
   accidental reasons. Task 2 therefore requires *two* mutations to break it, and says the
   test must be strengthened if neither does.
2. **G3a's bound may be met by an idle system.** The byte floor is what stops that, and Task 6
   makes the mutation's dual requirement explicit: break the latency, keep the floor.
3. **The exit-or-stop finding may be recorded from the bundle rather than from the run.** The
   spec states the bundle's prediction on purpose, which makes confirmation bias cheap; Task
   7's review exists mostly to catch it.
