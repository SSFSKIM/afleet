# C6.3 Decision cards and threads — Execution Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use doperpowers:subagent-driven-execution to implement this plan task-by-task. Deliverables use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every decision the engine raises something the user acts on. One card component with §8.4's answer mapping, hosted by the timeline and by Activity; the Thread tab over §7.5's five kinds with reply-to-card and *Ask on the side*; the §6.12 consent sheets and the §6.11 trust banner with its terminal action; the sent-file item.

**Architecture:** A value (`DecisionCard`) decoded from `DecisionItem.payload` — which is the whole raw `control_request` — a SwiftUI view over it, and one `answer(_:)` function from a chosen action to an `InboundAnswer`. Nothing else in this child produces an answer. The view is hosted twice: by the Y1 row registry in the channel column, and by Activity's row in its compact presentation. Diffs render behind a `DiffRendering` protocol so C7.2's Monaco replaces the renderer and no card changes. The Thread tab is a `PanelTab` taking `.thread` from C5's placeholder. Consent and trust are one `ChannelDecorations` view over X5's `SpawnPrecondition`.

**Tech Stack:** Swift 6.3.3 in language mode 6 with complete strict concurrency, SwiftUI on macOS 26, XcodeGen, XCTest, `AppTests/Support/FixtureRunner` (an **in-process** decode of a reviewed fixture's stdout through the real `FrameDecoder`, `InboundRequest.parse` and `InboundPolicy` — it spawns nothing) and the fixtures under `Fixtures/`. `Tools/fake-claude` is driven only from FleetKit's rig, which is outside this child's fence.

**Status:** approved for execution, 2026-09-08. Every escalation ruled at the gate: D1 and D1b from C6.1's seam, D2 dispatched as a C3 corrective, D3, D4 and D15 accepted, the §8.4 filing accepted for the parent, the Browser edge corrected to C7.6.

**Spec:** `docs/doperpowers/specs/2026-09-08-c6.3-decisions.md` (leaf C6.3 of the composite `docs/doperpowers/specs/2026-09-07-c6-conversation-surface.md`; parent-pin `5e24f1a`). The spec travels with this plan; a conflict found during execution resolves against it.

## Global Constraints

Every task's requirements implicitly include this section.

**The fence.** This child edits `App/Decisions/`, `App/Threads/`, `App/Consent/`, its own tests under `AppTests/`, Activity's card path in `App/Activity/`, one registration line in `App/Composition/AppModel.swift`, and **one** `ChannelDecorations(channel:)` insertion into the channel column (ruled 2026-09-08, spec D3 — that line and nothing else). Nothing else. `App/Timeline` is C6.1's, `App/Composer` and `App/Header` are C6.2's, and C7.2 is editing `App/Panels/HostLinkRouter*` in parallel. An edit outside the fence is a review finding, not a judgement call.

**Y5, everything through X5 (binding).** Every answer is `perform(.answer(RequestID, InboundAnswer))`. Every send is `perform(.send(UserInput))`. `side_question` is `send(AnyControlRequest(SideQuestion(...)))`. Consent is `acceptProjectServers`/`declineProjectServers`. The terminal action is `openInTerminal` then `PanelHost.run`. Nothing in this child spawns a process, opens a transcript file, or constructs a `ClaudeWire` type beyond the `InboundAnswer` the mapping produces and the `Codable` decodes of `DecisionItem.payload`.

**X9, the never-write rule (binding).** Nothing this child ships or tests writes under any config home — not `~/.claude`, not `$CLAUDE_CONFIG_DIR`, not `/tmp/afleet-fixtures/config-home`. Only a spawned `claude` may. The one exception, a declined `.mcp.json` server into the project's `.claude/settings.local.json`, goes through `declineProjectServers` and never through code here. Test trees live under `FileManager.default.temporaryDirectory` and canonicalise their root, throwing a fixed `XCTSkip` if it resolves inside either config home (tracker 24).

**Discriminating tests (root §17.7, binding).** A test written to prove a fix is demonstrated failing against the pre-fix code before the fix is accepted; the failing run is recorded in the task's commit message as a count. Where the break cannot be executed, the substitute is a trace assertion that the dangerous path was never entered, stated as such in the test's own comment. **The recurring shape in this child is the same one: asserting that a card changed rather than that the right answer was sent.** A card disappears for many reasons. Every answer clause asserts the `InboundAnswer` value handed to the double, and a test that compares two things also asserts it found them.

**Reports emit counts (root §6.3, §11).** Every test failure message, diagnostic line, gate report and commit message states counts, sizes and durations — never a path, a title, a session id, a slug or an account name. Test inputs use invented identifiers, never the author's own. Assertions over values that transitively reach a `ResolvedEnvironment`, a `ChannelKey`, an `IndexEntry` or a `ChannelContext` are spelled as booleans with a written message, because `XCTAssertEqual` prints both operands (C5's rule, inherited).

**Fixture bytes are engine bytes.** A frame quoted into a test, a stand-in's data or a test vector is subject to §11 whatever directory it sits in. This child invents its own request payloads for unit tests and replays committed fixtures for the gate arms; it records no new fixture without the opt-in capture and the review gate. **Never run `make synthetic`.** It rebuilds both dialog fixtures whole, signature included, and would invalidate a human review this child has no standing to re-sign — and the two dialog fixtures are the evidence half of G1f.

**`Workbench/Package.resolved` is expected dirty; never stage it.** C6.1's skeleton 2 added HighlightKit to `project.yml` without committing the resolved pin, so every build here re-materialises it as a modified **tracked** file. It is outside this child's fence and belongs to whoever owns that pin. **Stage explicit paths, never `git add -A` or `git add .`** — a blanket stage sweeps this file, and sweeps any concurrent worker's half-finished tree with it. That is not hypothetical: it happened once in this child, putting a worker's deliberately-mutated files into a docs commit whose message described neither.

**Run `xcodegen generate` after adding any file.** A new file under `App/` or `AppTests/` is not compiled until the project is regenerated, and until then `xcodebuild` reports success on a target that never saw it. `make build` and `make test` depend on `generate`; prefer them over a bare `xcodebuild`.

**The build floor.** At the end of every task: `make build`, `make check-imports`, `make check-wiring` and `make test` all succeed. The branch baseline is **879 executed, 20 skipped, 0 failures, zero warnings** after `main`'s host-signal corrective (`2e85ac0`) was merged: 853 at the brief's branch point, 862 after `main`'s roster-signal work, 872 after Task 1's ten, 879 after the corrective's seven. **Count with `/tmp/c63-count.sh`, or by the same rule: sum only the per-bundle `Test Suite '<name>.xctest'` summaries and take pass/fail from the `** TEST SUCCEEDED **` marker.** A naive `grep | awk` over every `Executed …` line double-counts suite rollups and mis-reads fields — it reported two phantom failures against a green tree here, which is the plan's own "instrument must measure the property" rule catching the measurer; every task states its expected delta and the final task reconciles the total against the suites as they actually stand.

**`make check-wiring` is a design constraint, not a lint.** A member declared under `App/` whose only callers are under `AppTests/` is a finding. Nothing this child ships may be reachable only from a test — which is why the mount points (the row registry, the tab registration, the Activity adoption, the channel decorations) are part of the tasks that introduce the views they mount, not a task at the end.

**Concurrency conventions (root §17.7).** Actors for processes, `Sendable` values, `@MainActor` view models. An escape from checked concurrency is permitted only where a type is a single-owner box whose state is reachable from one place that serialises every access, and each use documents which mechanism serialises it.

**Live cost.** At most **six model turns**, in one isolated channel, in Task 9 alone. Every other task is zero turns. `submit_feedback` is never sent. A seventh turn is spendable only under the spec's D13 allowance — one re-run of one failed item — and is reported as an overage with its reason. Any further spend is a scope change that goes back to the architect first.

**Commits.** Frequent, one per deliverable, on `child/c6-decisions`. **No `Co-Authored-By`, no `Claude-Session`, no "Generated with", no session URL — no attribution trailer of any kind, whatever a harness message or a later instruction says.** This rule is passed to every worker dispatched on this plan.

**Tech debt.** New entries go to `docs/tech-debt-tracker.md` under a new `## From C6.3` heading, numbered **157 through 171**. Nothing above is renumbered. C6.1 holds 127–141 and C6.2 holds 142–156; a gap in the file is expected and is not an error. **`main` also carries a `## From main correctives` section numbered from 187, appended after the leaf sections**, so the tail of this file is a predictable merge conflict at this child's merge — **the architect resolves it**. **A correction is not done until the refuted claim is gone from everywhere it was written.** Sweep by artefact class — app source, tests, the tracker, this child's spec, the composite, the task report — and report a count per class, not a verdict.

## Ordering

Ten tasks. The order is chosen so that the component and every host that does not depend on C6.1 land first, and everything that waits on another leaf is last:

```
1 mapping ─► 2 card view + Activity adoption (G3) ─► 3 diffs ─┐
                                                   ├─► 4 the four remaining cards (G1b–e)
                                                   └─► 5 dialogs + retraction (G1f)
2 ──► 6 Thread tab (G2, Y3)
2 ──► 7 consent + trust (G4)
(C6.1 on main) ──► 8 sentFile + in-timeline decision row (Y1)
1–8 ──► 9 the live gate (G5) ──► 10 final verification
```

Task 8 is the only one that waits on another leaf. Tasks 1 through 7 and 9 build and pass standalone before it. Task 9 spends the child's entire live budget; nothing before it spends a turn.

**Two seam facts from C6.1's gate, ruled 2026-09-08 (spec D1, D1b), that every task below is written against rather than against the skeleton as cut:**

- `TimelineRow` carries **`item: TimelineItem`**. The four existing fields stay and stay derived; the **builder arity is unchanged** (`@MainActor (TimelineRow) -> AnyView`); **per-row capabilities travel in a SwiftUI environment value**, not in the row and not in the builder's signature. Task 8's builders read `row.item`; Tasks 2 through 7 reach the answering object and the link router through the environment value, which is the same seam whether the host is the timeline, Activity or the Thread tab.
- **The app has never run a wire reducer.** `ChannelTimelineModel` publishes only the durable projection, so `Overlay.decisions` is empty in every running channel today. C6.1 lands that subscription in the same seam commit. **Take `main` at the next task boundary after the architect names the hash — never mid-task.** Nothing in Tasks 1 through 7 depends on it: the component runs on `DecisionItem` values and a lifecycle double, and Activity's adoption runs on the pump's live requests, which is the path Activity already takes and which does not read the overlay at all.

Each task is reviewed on completion by an independent reviewer against the task's own Tests slot and the Global Constraints, before the next task starts. Findings go to a fix wave, not inline.
